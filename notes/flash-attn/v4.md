# FlashAttention v4：SM100 Forward Kernel 导读

FlashAttention v4 在 Blackwell 上让矩阵乘、Softmax、输出修正和数据搬运交错执行。**读懂前向 kernel 的关键，是跟踪一次 KV 更新中，P 和旧输出何时准备好，以及下一次矩阵乘何时能继续。** 本文从 FA2 的 Online Softmax 出发，先跟完一个 Query stage，再看两组 stage 的交错与结果写回。

本文以 [`FlashAttentionForwardSm100`][source] 为入口，源码和辅助函数链接固定到上游提交 `b54df166`。本仓库 `asset/flash-attn/flash_fwd_sm100.py` 保存了带阅读注释的版本。

## 从 FA2 到 Blackwell 的数据路径

[FA2](./v2.md) 已将不同 Query Tile 分给独立工作单元，并把输出归一化推迟到最后。但每轮仍有两条依赖：QK 算出 Score 后，Softmax 才能生成当前权重 P；PV 累加新贡献之前，旧输出必须与 P 使用同一个指数基准。Blackwell 的 Tensor Core 吞吐增长快于指数运算和部分数据通路，这些逐元素计算与搬运更容易让矩阵乘等待。[作者介绍][blog]

FA4 为每个 CTA 保留两份 Query 状态。一份正在计算 Softmax 时，矩阵指令可以推进另一份；专门的 Correction 线程组负责缩放旧输出，Softmax 则继续生成 P。P 的前段写好后，PV 就可以先消费这一段。两份状态、独立修正和分段交付共同增加了可交错执行的工作。

> [FA3](./v3.md) 已将加载与计算分给不同线程组，在寄存器中维护 S/P/O。本文直接解释 Blackwell 的数据路径，FA3 可作为两代实现的对照阅读。

### 执行机制与本文配置

沿用 [Blackwell MatMul](../cuda/blackwell-matmul.md) 中的三个硬件概念：

| 机制 | 在本 kernel 中负责什么 |
| --- | --- |
| TMA | 异步搬运全局显存（GMEM）与共享内存（SMEM）之间的 Q/K/V 和最终输出 |
| UMMA | 在 Tensor Core 上执行 QK、PV，结果写入 TMEM；底层使用 `tcgen05.mma` |
| TMEM | 保存 Score、P 和输出累加器；CUDA 线程通过专门的读写指令与寄存器交换数据 |

线程发出 TMA 或 UMMA 指令后，操作仍可能在进行。消费者必须等到数据可读；生产者再次覆盖缓冲前，则要等旧数据用完。后文的 ready 表示前者，“归还槽位”表示后者；barrier 的 phase 用于区分同一同步对象的连续轮次。

CTA 即 Thread Block。本文选择两个 CTA 组成 cluster，以 2CTA UMMA 联合执行矩阵乘。用 $D$ 表示 Q/K 的 head dimension，$D_v$ 表示 V 的 head dimension：

| 项目 | 本文配置 |
| --- | --- |
| 硬件与类型 | SM100，Q/K/V/O 为 BF16 或 FP16，累加为 FP32 |
| Attention | 定长 dense MHA，非 causal、非 local，无 SplitKV 或自定义 score/mask |
| Tile | `m_block_size=128`，`n_block_size=128`，$D=D_v=128$ |
| Query 状态 | `q_stage=2`，每 CTA 保留两套 Query 状态 |
| CTA 协作 | `use_2cta_instrs=True`，两个 CTA 联合执行 UMMA |
| 搬运与调度 | Q/K/V/O 走 TMA，persistent 调度，关闭 CLC |

这是本文选择的分析路径。[构造函数][init]的 `use_2cta_instrs` 默认值为 `False`，其他参数也会改变线程分工、缓冲布局和写回方式。

### 先跟踪一份 Query 状态

kernel 接收 Q、K、V，输出 Attention 结果。FA2 文中的未归一化累加器 A，在这份源码中命名为 O，保存在 TMEM 中；最终除以累计分母后才写到 GMEM。下文的 P 表示当前指数基准下的未归一化权重。

<FlashAttentionV4Diagram view="storage" />

Q 在当前工作单元内反复使用，K/V 则逐块更换。QK 生成 S，Softmax 在寄存器中读取一行 S、更新统计量并生成 P；Correction 根据同一缩放系数修正旧 O，PV 再累加当前块的贡献。最后一轮结束后，Correction 负责归一化和类型转换，Epilogue 负责从 sO 发起 TMA 写回。

## 一个 work tile 如何分配

一次联合 QK 覆盖 256 行 Query、128 个 Key position，两个 CTA 各得到其中 128 行的完整 Score。每个 CTA 又保留两个 Query stage，因此一个 CTA pair 的 **work tile** 共覆盖同一序列、同一 Head 的 512 行。每个 work tile 遍历所需的 KV；persistent 调度让同一对 CTA 完成后继续处理其他 work tile。

<FlashAttentionV4Diagram view="ownership" />

首个完整 work tile 的精确行号如下。后续 work tile 增加相应行偏移，序列末尾不足的部分由边界 mask 处理：

| Query stage | CTA0 的 Query 行 | CTA1 的 Query 行 |
| --- | --- | --- |
| stage 0 | 0–127 | 128–255 |
| stage 1 | 256–383 | 384–511 |

每个 stage 拥有独立的 S/P/O 状态。**Query stage 标识不同输出行；K/V ring 的 stage 标识可复用的搬运槽位。** 行索引见 [`correction_loop`][row-index]。

### 两个 CTA 如何提供操作数

2CTA UMMA 中，左操作数与结果按 Query 行归属，右操作数沿结果的列维分片。QK 的右操作数是 $K^T$，输出列对应 Key position；PV 的右操作数是 V，输出列对应 Value dimension。因此 K 与 V 分片的轴不同，但两次矩阵乘都让每个 CTA 得到自己 Query 行的完整列宽。

<FlashAttentionV4Diagram view="operands" />

| 每 CTA 保存的数据 | 逻辑形状 | 两个 CTA 如何分工 |
| --- | --- | --- |
| 某个 stage 的 Q | $128\times128$ | 各自的 128 行 Query |
| K | $64\times128$ | 各保存一半 Key position，保留完整 head dimension |
| V | $128\times64$ | 各保存全部 Key position，保留一半 Value dimension |
| 某个 stage 的 S/P/O | 各有 128 行、完整列宽 | 对应本 CTA 的 Query 行 |

只有 leader CTA 的 MMA Warp 发射联合 UMMA。指令使用两边提供的操作数，并把两半结果写入各自 CTA 的 TMEM；Softmax、Correction 和输出处理随后各自在本地执行。[操作数布局][layouts]、[MMA 发射][mma-start]

### 线程分工与缓冲复用

每个 CTA 有 16 个 Warp、512 个线程，长期执行以下角色：

| Warp ID | 角色 | 负责的工作 |
| --- | --- | --- |
| 0–3 | Softmax 0 | 处理本 CTA 的 Query stage 0 |
| 4–7 | Softmax 1 | 处理本 CTA 的 Query stage 1 |
| 8–11 | Correction | 为两个 stage 修正旧 O，最后归一化并写入 sO |
| 12 | MMA | 分配 TMEM；在 leader CTA 中发射联合 QK/PV |
| 13 | Epilogue | 把 sO 搬到 GMEM |
| 14 | Load | 发起 Q/K/V 的 TMA load |
| 15 | Empty | 本文关闭 CLC，该 Warp 不参与数据计算 |

每组 Softmax 的 128 个线程对应本地 stage 的 128 行，TMEM 读取映射使每个线程负责一行运算。这些线程组共用本地 SM 的 CUDA Core/MUFU 等执行资源。[角色定义][roles]、[线程分流][dispatch]

缓冲的复用由最后一个消费者决定：

| 存储 | 内容 | 可以复用的时机 |
| --- | --- | --- |
| SMEM 的两份 Q | 本 CTA 的两个 Query stage | 本 work tile 的相关 QK 全部消费完 |
| SMEM 的 K/V ring | K 或 V 的局部分片 | 当前内容被两个 Query stage 消费后 |
| TMEM 的两个 S/P 工作区 | FP32 Score，随后复用其中空间保存低精度 P | 本 stage 的 PV 消费 P 后，下一轮 QK 可以覆盖 |
| TMEM 的两个 O 区域 | FP32 未归一化累加器 | 完成最终归一化、转换并搬出后 |
| SMEM 的 `sScale` | 中间轮的缩放系数、末轮的最终分母 | Correction 使用完相应数据后，按统计量槽协议交接 |
| SMEM 的两份 sO | 已归一化并转换类型的输出 | 异步 store 已读完该源槽后 |

K 和 V 的 tensor view 共用一片 SMEM ring，按 $K_0,V_0,K_1,V_1,\ldots$ 的搬运事件轮转，每槽容纳一次 K 或 V 搬运。这里及后文的下标表示**访问次序**；dense 路径实际倒序遍历 KV block。[加载与 ring 轮转][load]

S/P 也共用空间：Softmax 读出 S 后，将低精度 P 写到同一工作区内的偏移位置。O 使用独立的 FP32 区域，跨 KV block 累加。[TMEM 布局][tmem-layout]

> 图和表描述逻辑数据。SMEM 的 layout/swizzle、TMEM 的 lane/column 映射决定实际地址；S/P 的复用包含偏移与类型宽度变化。两套 tensor view 可以指向重叠存储，而不具有相同的起始地址和元素布局。

## 一个 Query stage 如何更新 Online Softmax

先跟踪一个有效 Query 行。Softmax 线程保存该行的指数基准和累计分母，Correction 与 Tensor Core 共同更新输出分子。各状态与 FA2 的对应关系如下：

| 数学含义 | kernel 中的名称与位置 | 谁更新 |
| --- | --- | --- |
| 指数基准 $m$ | `row_max`，Softmax 线程寄存器 | Softmax；条件缩放时可暂时沿用旧值 |
| 累计分母 $l$ | `row_sum`，Softmax 线程寄存器 | Softmax |
| 缩放系数 $\alpha$ | `acc_scale`，经 SMEM 的 `sScale` 交接 | Softmax 计算，Correction 读取 |
| 权重 P | 指数计算暂存在寄存器，低精度副本写入 TMEM | Softmax |
| 输出分子 | 源码中的 O，FP32 TMEM 累加器 | Correction 缩放旧值，PV 累加新贡献 |

### 选择基准，让分子与分母按同一尺度更新

QK 完成后，Softmax 线程从 TMEM 读取自己负责的一行 S，处理边界 mask，并求当前候选最大值。源码在这一步还保留未乘 Attention scale 的 Score；`scale_log2` 将缩放与自然指数到 `exp2` 的换底合在一起。下面用 $c$ 表示 `scale_log2`，用 $m'$ 表示本轮实际采用的基准。

**条件缩放决定何时更换基准。** 第一轮直接采用当前最大值。后续轮比较候选最大值相对旧基准的增长：经 $c$ 换算后不超过 8 个 log2 单位，就沿用旧基准；超过阈值才更新。因而 `row_max` 保存的是当前采用的基准，可以暂时落后于真实已见最大值。所有元素仍参与计算，沿用旧基准时 P 可能大于 1。[基准选择][softmax-max]

旧状态乘上换到新基准所需的系数，当前权重也按这个新基准计算。对本行第 $k$ 个 Score $S_k$，两者是：

$$
\alpha=2^{(m-m')c},\qquad p_k=2^{(S_k-m')c}.
$$

沿用旧基准时 $m'=m$，因此 $\alpha=1$。Softmax 将系数写入 `sScale` 并通知 Correction，然后继续计算指数与类型转换。Correction 按 Warp 检查这 32 行是否需要缩放：全部系数为 1 时，直接通知 O 可累加；只要存在需要缩放的行，就读取相应 O 数据，按各行系数缩放后写回 TMEM。[缩放与通知][conditional-correction]

分母和分子必须使用相同尺度。Softmax 把旧分母乘 $\alpha$，再加上当前行的指数和；Correction 把旧输出分子乘 $\alpha$，PV 再加上当前 Value 的加权和。用 $\mathbf{o}$ 表示源码 O 中该行的分子向量，用 $\mathbf{v}_k$ 表示第 $k$ 个 Value 向量：

$$
\begin{aligned}
l'&=\alpha l+\sum_k p_k,\\
\mathbf{o}'&=\alpha\mathbf{o}+\sum_k p_k\mathbf{v}_k.
\end{aligned}
$$

第一轮直接建立分母和分子：Softmax 使用首轮统计路径，PV 采用不累加旧值的模式。之后每轮保存新的 $m',l',\mathbf{o}'$；遍历全部 KV 后，才计算 $\mathbf{o}/l$。这与 FA2 的延迟归一化相承接，只是分子更新被拆给 Correction 和 PV 两个执行者。

> 上式表达共同尺度下的数学关系。实现的 row sum 使用寄存器中的 FP32 指数值，PV 使用转换成 BF16/FP16 的 P；软件指数近似、类型转换和浮点累加还会引入数值误差。条件缩放在精确算术下保持最终比值，实际结果仍需按浮点实现评估。

### P 分段交付，PV 提前开始

上述更新的数学依赖确定后，可以安排实际交接顺序。Softmax 在通知缩放系数后，计算指数并转换类型，再分段写入 TMEM：先发布前 96 列可读的通知，再发布后 32 列可读的通知。P 的列对应当前块的 Key position，也是 PV 的归约维度。

**PV 的前段只需等 V、P 的前 96 列和旧 O 都准备好。** MMA 发射线程先等待 V，再等待 Softmax 与 Correction 共同交接；然后发出前段 PV 指令。到后段指令时，它再等待 P 尾段，继续把剩余 32 项的贡献累加到同一个 O。新 work tile 的首轮无需缩放旧贡献，但仍须确认上一 work tile 已读完同一 TMEM O 区域。分段边界来自 `split_P_arrive=96`。[Softmax 交付顺序][softmax-step]、[PV 等待][pv-wait]、[分段矩阵指令][partial-gemm]

P 全部写出后，Softmax 等到统计量槽允许继续推进，再更新寄存器中的 row sum。因此，当前 PV 可以与 P 尾段写入、后续分母更新交错。分母用于后续迭代及最终归一化，不参与本轮 PV 的输入。

> `pipeline_s_p_o` 承担两个方向的交接：MMA 发布 S-ready；Softmax 和 Correction 共同归还，表示 P 前段及 O 都可供 PV 使用。`consumer_release` 在这个对象上因此有放行 PV 的作用。统计量槽另由 `pipeline_sm_stats` 协调，避免 Softmax 与共享 Correction 之间覆盖尚未消费的状态。[同步对象定义][pipeline-setup]

### 指数计算如何分给 MUFU 与 FMA

每个 Softmax 线程要为一行计算多个指数，MUFU 指数单元可能持续繁忙。FA4 把其中一部分转成普通融合乘加（FMA）运算：将 `exp2` 的输入拆为整数和小数，用多项式近似小数部分，再通过浮点指数位组合整数部分的缩放。这样可以让 FMA 分担 MUFU 的工作，代价是额外的普通运算和近似误差。[软件指数实现][exp-emulation]

本配置的 `ex2_emu_freq=10` 与 fragment 位置共同决定哪些元素采用软件近似；它是选择规则中的参数。硬件 `exp2` 与软件路径的具体分配由 [`apply_exp2_convert`][exp-convert]完成。实际收益取决于 MUFU 与普通运算的负载，以及它们和其他角色的资源竞争。

## 两个 Query stage 如何交错

两份 Query 状态让 MMA 在一组等待 Softmax 或 Correction 时，继续推进另一组。下面仍按访问次序标记 KV block；下标 0、1 表示 Query stage。leader 的联合矩阵指令按以下顺序发射：

| 阶段 | 发射顺序 |
| --- | --- |
| 启动 | $Q_0K_0^T$ → $Q_1K_0^T$ |
| 稳态，第 $j$ 轮 | $P_{0,j}V_j$ → $Q_0K_{j+1}^T$ → $P_{1,j}V_j$ → $Q_1K_{j+1}^T$ |
| 收尾 | 两个 stage 分别执行最后一次 PV |

图中选取稳态的一段：stage 0 算出当前 S 后，Tensor Core 先推进 stage 1 的上一轮 PV 和当前 QK；本地线程同时准备 stage 0 的 P 和 O。等三项输入条件满足，stage 0 的 PV 才能继续。

<FlashAttentionV4Diagram view="pipeline" />

图中将 Correction 排在指数计算之前，是共享 CUDA Core 资源下的一种保守安排；这些操作可交错或部分重叠，实际取决于资源竞争。两组 Softmax 也共享本地 CUDA Core/MUFU。本文版本的 `s0_s1_barrier=False`，没有额外强制两组指数区间交替；它们仍会通过共享 Correction 与统计量槽相互施加反压。[MMA 循环][mma-loop]、[可选 sequence barrier][sequence]

> 作者博客采用显式交替的示意。源码中的可选 sequence barrier 包围 `exp2/convert` 区间，随后才写 P；本文的发射顺序与交接关系以固定提交为准。

**下一轮 S 的完成通知，还能证明旧 O 已可读取。** 在同一个 stage 上，上一轮 PV 后才执行下一轮 QK。下一轮 S-ready 到达后，Softmax 才能计算缩放系数并通知 Correction；借助这份实现的 UMMA 顺序与完成协议，此时上一轮 PV 已完成，Correction 可直接读取旧 O，省去一次独立的 O-ready 等待。前面的 PV 也已消费旧 P，下一轮 QK 因而可以覆盖 S/P 工作区。[源码中的同步省略说明][mma-loop]

## 最后一次更新与跨 work tile 写回

最后一次 PV 后没有下一轮 QK，MMA 因此通过 `pipeline_o_acc` 单独发布最终 O 完成的通知。Softmax 此时将最终 `row_sum` 写入 `sScale` 的对应位置，通知 Correction：同一槽位在中间轮传递缩放系数，在收尾阶段传递最终分母。

Correction 同时等待最终 O、最终分母以及空闲 sO 槽；随后读取 TMEM O，乘以分母的倒数，转换为输出类型并写入 sO。数据搬出后，它归还 TMEM O 区域，允许下一 work tile 的 PV 使用，再通知 Epilogue 写回。[Correction 收尾][correction-final]

Epilogue 对两个 sO 槽分别发起 TMA store，并在异步引擎读完源 SMEM 后归还对应槽位。这里使用 `read=True` 的 bulk-group wait：源槽已可覆盖时，GMEM 的完整写出仍可能进行，因此写回可以跨入下一个 work tile。[输出路径][epilogue]、[PTX read wait 语义][ptx-read]

如果 store 持续落后，Correction 会等待 sO 空闲；旧 O 无法搬出时，TMEM O 的归还也会推迟，进一步阻塞后续 PV。输出双缓冲增加了可以交错的空间，但消费者仍通过槽位复用约束上游进度。

## 资源取舍与配置分支

**2CTA 为 K/V 预取腾出空间。** 本配置中，每 CTA 的两份 Q 共占 64 KiB，两份 sO 也占 64 KiB。源码以 224 KiB 为选槽预算，余下 96 KiB 用于 K/V ring：

| 项目 | 1CTA | 2CTA |
| --- | --- | --- |
| 每 CTA 的 Q 与 sO | 128 KiB | 128 KiB |
| 单个 K 或 V 槽 | 32 KiB | 16 KiB |
| 按预算计算的 `kv_stage` | 3 | 6 |

K/V 分片使单槽大小减半，相同预算便能容纳更多预取事件。224 KiB 是代码的选槽预算；硬件总容量与实际吞吐需要分别判断。吞吐还取决于计算、搬运和同步是否能相互覆盖。[槽数计算][attributes]

**寄存器配额随角色分配。** 两组 Softmax 每线程上限分别为 176、176，Correction 为 88，最后四个轻量 Warp 为 72。四组各有 128 个线程，合计配额为 $128\times(176+176+88+72)=65536$ 个 32 位寄存器。轻量 Warp 通过 `setmaxregister_decrease(72)` 降低上限，供 Softmax 增加寄存器使用。MMA 的大累加器位于 TMEM，发射 Warp 因而可以使用较低配额。[调参表][tuning]、[寄存器分配][dispatch]

<details>
<summary>其他配置会改变哪些路径</summary>

- `q_stage=1` 会调整 Softmax 与 Load/Empty 的角色；非 TMA KV 路径也会增加 Load 线程。
- 非 TMA 输出路径可由 Correction Warp 直接承担 epilogue。
- 某些 head dimension 或 SplitKV 配置会让 sO 与 sQ 复用 SMEM，并关闭 persistence；跨 work tile 的搬运安排随之改变。
- CLC（Cluster Launch Control）使用额外调度角色。Causal/local 路径采用 LPT 调度，优先安排工作量较大的 tile；1CTA/2CTA 的选择需查看同版本 host dispatch。

主 kernel 独立接收 `is_causal` 和 `use_2cta_instrs`，调参表包含 `2CTA + causal + D256`。本文选择非 causal 以固定分析范围，其他配置仍可能使用 2CTA。

</details>
