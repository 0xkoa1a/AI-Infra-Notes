# FlashAttention v4：SM100 Forward Kernel 导读

FlashAttention v4 在 Blackwell 上将矩阵乘、Softmax、输出修正和数据搬运交给不同线程协作，让它们围绕片上数据交错执行。本文沿着一个 work tile 从读入到写回的过程，解释 SM100 前向 kernel 的数据归属、流水线和同步。

源码以 [`FlashAttentionForwardSm100`][source] 为入口，固定到上游提交 `b54df166`。本仓库 `asset/flash-attn/flash_fwd_sm100.py` 带有阅读注释；忽略注释与空白后，其代码 AST 与该提交一致。下文的辅助函数也取自同一提交，源码链接均指向这一版本。

## 背景与分析范围

在 [v2](./v2.md) 中，分块 Attention 已经能够独立处理不同 Query Tile，并把归一化推迟到最后。Blackwell 的 Tensor Core 吞吐增长快于指数运算和部分数据通路，Softmax、输出缩放和搬运因此更容易让矩阵乘等待。[作者介绍][blog]将前向优化集中在这些操作与 MMA 的配合上。

[v3](./v3.md) 已将搬运交给 producer，让 consumer 在寄存器中维护 S/P/O 并推进矩阵乘与 Softmax。本文的 SM100 路径把这些状态移到 TMEM，并进一步分出 MMA、Softmax、Correction 和 Epilogue 角色；接下来要看的是这些角色如何交接数据。

理解这份实现需要三个硬件概念：

- **TMA** 负责异步搬运 GMEM 与 SMEM 之间的数据，GMEM 在这里指输入输出所在的全局显存。
- **UMMA** 是这里使用的 Blackwell Tensor Core 矩阵乘，底层为 `tcgen05.mma`；线程发射指令后，可以通过完成通知协调其他工作。
- **TMEM** 保存 Tensor Core 的中间结果和累加器。CUDA 线程通过专门的读写操作在 TMEM 与寄存器之间交换数据。

kernel 接收 Q、K、V，计算前向 Attention 输出 O。CTA 即 Thread Block；两个 CTA 可以组成 cluster，以 2CTA UMMA 联合执行一次矩阵乘。下文用 $D$ 表示 Q/K 的 head dimension，$D_v$ 表示 V 的 head dimension，选择下面这套配置：

| 项目 | 本文配置 |
| --- | --- |
| 硬件与类型 | SM100，Q/K/V/O 为 BF16 或 FP16，累加为 FP32 |
| Attention | 定长 dense MHA，非 causal、非 local，无 SplitKV 或自定义 score/mask |
| Tile | `m_block_size=128`，`n_block_size=128`，$D=D_v=128$ |
| Query 状态 | `q_stage=2`，每 CTA 保留两套 Query 状态 |
| CTA 协作 | `use_2cta_instrs=True`，两个 CTA 联合执行 UMMA |
| 搬运与调度 | Q/K/V/O 走 TMA，persistent 调度，关闭 CLC |

这是本文选择的分析路径。[构造函数][init]的 `use_2cta_instrs` 默认值为 `False`，不同参数还会改变 Warp 分工、buffer 布局和写回方式。

## 一个 work tile 如何分配

**先区分一次矩阵乘和整个工作单元。** 一次联合 QK 覆盖 256 行 Query、128 个 Key position；两个 CTA 各得到其中 128 行的完整 Score。每个 CTA 又保留两个 Query stage，因此一个 CTA pair 的 work tile 共覆盖同一序列、同一 Head 的 512 行。每个 work tile 都要遍历所需的 KV；persistent 调度让这一对 CTA 完成后继续处理其他 work tile。

<FlashAttentionV4Diagram view="ownership" />

首个完整 work tile 的行归属如下；后续 work tile 在此基础上增加相应的行偏移，序列末尾不足的部分由边界 mask 处理：

| Query stage | CTA0 的 Query 行 | CTA1 的 Query 行 |
| --- | --- | --- |
| stage 0 | 0–127 | 128–255 |
| stage 1 | 256–383 | 384–511 |

同一个 CTA 的两段 Query 并不相邻。它们拥有各自的 S/P/O 状态，由两组 Softmax Warp 分别处理。这里的 Query stage 标识不同的输出行；后文 K/V ring 的 stage 则标识可复用的搬运槽位。行索引可对照 [`correction_loop` 中的 `m_tile_idx`][row-index]。

**Q/P 与结果按 Query 行归属，K/V 按联合矩阵乘的右操作数分片。** QK 的右操作数是 $K^T$，其输出列对应 Key position；PV 的右操作数是 V，其输出列对应 Value dimension。因此，在同一个逻辑 KV block 内：

| 每 CTA 保存的数据 | 逻辑形状 | 两个 CTA 如何分工 |
| --- | --- | --- |
| 某个 stage 的 Q | $128\times128$ | 各自的 128 行 Query |
| K | $64\times128$ | 各保存一半 Key position，保留完整 head dimension |
| V | $128\times64$ | 各保存全部 Key position，保留一半 Value dimension |
| 某个 stage 的 S/P/O | 各有 128 行、完整列宽 | 对应本 CTA 的 Query 行 |

只有 leader CTA 的 MMA Warp 发射联合 UMMA，指令使用两边提供的操作数，并把两半结果写入各自 CTA 的 TMEM。每个 CTA 随后处理本地的 Softmax、Correction 和输出。操作数布局见 [`__call__`][layouts]，leader 判断见 [`mma`][mma-start]。

每个 CTA 有 16 个 Warp、512 个线程，按以下角色长期运行：

| Warp ID | 角色 | 负责的工作 |
| --- | --- | --- |
| 0–3 | Softmax 0 | 处理本 CTA 的 Query stage 0 |
| 4–7 | Softmax 1 | 处理本 CTA 的 Query stage 1 |
| 8–11 | Correction | 为两个 stage 修正旧 O，最后归一化并写入 sO |
| 12 | MMA | 分配 TMEM；在 leader CTA 中发射联合 QK/PV |
| 13 | Epilogue | 把 sO 搬到 GMEM |
| 14 | Load | 发起 Q/K/V 的 TMA load |
| 15 | Empty | 在本文关闭 CLC 的配置下不参与数据计算 |

每组 Softmax 有 128 个线程，对应本地 stage 的 128 行；TMEM 到寄存器的映射让每个线程负责一行的逐行运算。128-thread warpgroup 描述线程分工，不代表它拥有一套独占的计算引擎。角色定义与分流见 [`__init__`][roles]和 [`kernel`][dispatch]。

## 数据存放与复用

前文的未归一化累加器 A，在这份源码中仍命名为 O，并驻留 TMEM；只有最终归一化后的结果才写到 GMEM。P 也是当前指数基准下的未归一化权重，不是整行最终的 Softmax 概率。

<FlashAttentionV4Diagram view="storage" />

各类存储承担不同的生命周期：

| 存储 | 内容 | 可以复用的时机 |
| --- | --- | --- |
| SMEM 的两份 Q | 本 CTA 的两个 Query stage | 本 work tile 的相关 QK 全部消费完 |
| SMEM 的 K/V ring | K 或 V 的局部分片 | 当前内容被两个 Query stage 消费后 |
| TMEM 的两个 S/P 工作区 | FP32 Score，随后复用其中空间保存低精度 P | 本 stage 的 PV 消费 P 后，下一轮 QK 可以覆盖 |
| TMEM 的两个 O 区域 | FP32 未归一化累加器 | 完成最终归一化、转换并搬出后 |
| 寄存器与小块 SMEM | Softmax 行统计、指数计算临时值和 `sScale` | 对应消费者已使用这些状态后 |
| SMEM 的两份 sO | 已归一化并转换类型的输出 | 异步 store 已读完该源槽后 |

**K 和 V 共用一个 ring。** 两套 tensor view 指向同一片 SMEM，按 `K₀, V₀, K₁, V₁, …` 的搬运事件轮转。这里的下标表示处理次序；源码的 dense 路径实际倒序遍历 KV block。一个 ring 槽保存一次 K 或 V 搬运的结果。QK/PV 消费当前内容后才能归还该槽，而且必须等两个 Query stage 都用完。见 [`load`][load]和 [`mma` 的槽位归还][mma-loop]。

**S 与 P 复用空间，O 独立累加。** QK 写入 S；Softmax 将 S 读入寄存器，计算后把低精度 P 写回同一工作区内的偏移位置。S/P 并非两个完整、独立的分配，也不是简单从同一地址开始覆盖。O 的两套 FP32 累加区与它们分开，跨 KV block 保留。布局入口是 [`tmem_s_offset`、`tmem_p_offset` 和 `tmem_o_offset`][tmem-layout]。

> 图中表达的是逻辑区域与生命周期。SMEM 还要按照 TMA/UMMA 的取数方式做 layout 和 swizzle，TMEM 也有硬件规定的 lane/column 映射。代码中的不同 tensor view 用于解释这些坐标，不能直接当成普通 row-major 数组。

## 一次 KV 更新如何推进

先只跟踪一个 Query stage。一次更新需要完成两件相互关联的工作：生成当前 Tile 的 P，以及让旧 O 与 P 使用一致的指数基准。Softmax Warp 负责前者，Correction Warp 负责后者，PV 再把新贡献累加进 O。

[`softmax_step`][softmax-step]按下面的顺序推进：

- 等待 QK 的 S-ready，读出 S，并处理需要的边界 mask。
- 决定本轮采用的指数基准，得到 `acc_scale`；通过 `sScale` 和统计量通知尽早交给 Correction。
- 计算指数并转换类型，分段将 P 写回 TMEM。
- 前 96 列写好并建立可见性后，发布 P-prefix-ready；后 32 列写好后，另发 P-tail-ready。
- 取得可继续使用的统计量槽后，更新累计 row sum。

因此，**PV 可以先使用 P 的前段，Softmax 再完成尾段写入与 row sum 更新。** row sum 留给后续状态和最终归一化，不是本轮 PV 启动必须等待的结果。前段、尾段的划分来自 `split_P_arrive=96`。

MMA 启动 PV 前需要三个条件：V 已经就绪、P 前段可读、旧 O 可以继续累加。[`mma`][pv-wait]先等 `pipeline_kv`，再等 `pipeline_s_p_o` 汇合 Softmax 与 Correction 的通知。第一次累加还没有旧 O，Correction 会处理初始化交接，MMA 使用不累加旧值的模式。

> `pipeline_s_p_o` 同时服务两个方向：MMA 用它发布 S-ready；Softmax 与 Correction 共同归还，表示 P 前段及 O 都已准备好。因此，源码中的 `consumer_release` 在这里还有放行下一次 PV 的含义，不能一律理解为“读取 S 完毕”。对象建立处有[专门的说明][pipeline-setup]。

P 尾段的等待发生在 MMA Warp 发射侧：[`gemm_ptx_partial`][partial-gemm]先发出处理前 96 列的 PV 指令，再等待 tail barrier，随后发出处理后 32 列的指令。P 的列对应当前 KV block 的 Key position，也是 PV 的归约维度；前后两段与 V 的对应行相乘，贡献累加到同一个 O Tile。

**条件缩放减少 O 的重复读写。** [v2](./v2.md)用每轮已见最大值解释指数基准；这里的 [`SoftmaxSm100`][softmax-max]允许在最大值增幅较小时继续沿用旧基准，同时返回 `acc_scale=1`。新权重仍按旧基准计算，累计分子、分母处于同一尺度，因此最终比值保持一致。增幅超过阈值后，再更换基准并缩放旧贡献。

这会让保存的 `row_max` 暂时落后于真实已见最大值。本文 16 位配置传入的阈值为 8 个 log2 单位，比较的是经 `scale_log2` 换算的指数差。它控制基准何时更新，不能理解成直接丢弃小概率项；保留基准时，未归一化的 P 还可能大于 1。Correction 以 Warp 为单位判断是否有行需要缩放；如果全部 `scale=1`，便省去该 Warp 的 O 重缩放，仍然发出 O-safe 通知。对应代码见 [`correction_loop`][conditional-correction]。

**指数计算分配到 MUFU 与 FMA。** MUFU 是执行指数等特殊函数的硬件单元，FMA 指融合乘加运算。本文配置启用 `ex2_emu_freq=10`。部分元素调用硬件 `exp2`，部分元素通过软件近似计算，将一部分指数工作移到 FMA 运算上；它们由 [`apply_exp2_convert`][exp-convert]按 fragment 分配。参数表示选择规律，不应直接读成“十分之一的元素”或某个固定加速比例。

> 条件缩放调整共同基准，在精确算术下不改变最终归一化比值。实际实现还包含软件指数近似、BF16/FP16 转换和浮点累加误差；比较数值结果时需要考虑这些因素。软件指数的整数/小数拆分和多项式实现见 [`ex2_emulation_2`][exp-emulation]。

## 两组 stage 如何交错并完成写回

两份 Query 状态让一组在等待 Softmax 或输出修正时，MMA 可以推进另一组的工作。下面的 `j` 仍表示处理次序，一个 work tile 的主要发射顺序是：

```text
prologue:  QK(stage 0, K₀) → QK(stage 1, K₀)

steady:    PV(stage 0, Vⱼ) → QK(stage 0, Kⱼ₊₁)
        →  PV(stage 1, Vⱼ) → QK(stage 1, Kⱼ₊₁) → repeat

drain:     PV(stage 0, Vlast) → PV(stage 1, Vlast)
```

<FlashAttentionV4Diagram view="pipeline" />

这个顺序描述 [`mma`][mma-start]如何推进联合指令。其他 Warp 和搬运引擎可以穿插工作，实际重叠程度还受资源竞争影响。两组 Softmax 共用本地 CUDA Core/MUFU 资源；QK 与 PV 也消耗同一组 Tensor Core 资源。图中的交错表达依赖允许的安排，不能直接换算成实测耗时。

本文版本的 `s0_s1_barrier=False`，没有额外强制两组 Softmax 的指数区间交替。它们仍会通过共享 Correction 和统计量槽产生反压联系。可选 sequence barrier 包围的是 `exp2/convert` 区间，随后才写 P；这与[作者博客][blog]中采用显式交替的示意有所区别，见 [`softmax_step` 的可选分支][sequence]。

**稳态可以复用后续计算的完成通知。** 在同一个 stage 上，上一轮 PV 后才发射下一轮 QK；下一轮 S-ready 到达后，Softmax 才能算出缩放因子并通知 Correction。由这条完成依赖，Correction 可以确认旧 O 已可读取，省去一次单独的 O-ready 等待。下一轮 QK 也能覆盖 S/P 工作区，因为前面的 PV 已经消费了旧 P。这里依赖的是这份实现的 UMMA 顺序与完成通知，不能仅由“源代码写在后面”推出。见 [`mma` 中的同步省略说明][mma-loop]。

**末轮需要单独完成 O。** 最后一次 PV 后没有下一轮 QK，因此 MMA 通过 `pipeline_o_acc` 发布 final-O-ready。Correction 同时取得最终 row sum，等待 O 完成与 sO 槽可用，归一化、转换类型并写入 sO，然后归还 TMEM O 区域，通知 Epilogue 写回。见 [`correction_loop` 的收尾][correction-final]。

Epilogue 对两个 sO 槽分别发起 TMA store。源码在归还源槽前使用：

```python
cute.arch.cp_async_bulk_wait_group(self.q_stage - 1 - stage, read=True)
pipeline_o_epi.consumer_release_w_index(stage)
```

`read=True` 等待异步引擎不再读取源 SMEM；GMEM 的完整写出可以继续进行。这允许输出搬运跨到下一个 work tile。如果 store 持续落后，Correction 会等 sO 空闲；它无法搬出旧 O 时，也会延迟 TMEM O 的归还，进一步阻塞后续 PV。源码见 [`epilogue_s2g`][epilogue]，指令语义见 [PTX 的 read wait][ptx-read]。

回看同步代码时，可以按以下事件定位。每个循环槽还带有 phase，用来区分不同轮次的 ready：

| 事件 | 谁通知、谁等待 | 对应对象及保证 |
| --- | --- | --- |
| Q/K/V 可读 | TMA 完成后，MMA 等待 | `pipeline_q`、`pipeline_kv`：相应输入已搬入 |
| S 可读 | UMMA 完成后，Softmax 等待 | `pipeline_s_p_o` 的 S-ready 方向 |
| 缩放因子可读 | Softmax 通知，Correction 等待 | `sScale` 与 `sm_stats_barrier`；统计量槽还通过 `pipeline_sm_stats` 回收 |
| P 前段与 O 可用 | Softmax、Correction 共同通知，MMA 等待 | `pipeline_s_p_o` 的返回方向；2CTA 下包括两边的参与者 |
| P 尾段可读 | Softmax 通知，部分 PV 发射过程等待 | `pipeline_p_lastsplit` |
| 最终 O 完成 | UMMA 完成后，Correction 等待 | `pipeline_o_acc` |
| sO 可读／可覆盖 | Correction 通知 Epilogue；store 读完后归还 | `pipeline_o_epi` 的双向交接 |

TMA/UMMA 的生产者可以将完成事件关联到 barrier，无需自己阻塞到操作完成；消费者 wait 成功后才安全读取。普通 SMEM 与 TMEM 写入则要按相应协议建立可见性，再交接。各条 pipeline 的退出方式不同，不能统一补一个 producer tail。TMEM 最终由 MMA、Softmax、Correction 这些使用者汇合后释放，见 [`kernel` 的 TMEM 回收][tmem-free]。

## 资源取舍与配置分支

**2CTA 为 K/V 预取腾出空间。** 在本文配置中，每 CTA 的两份 Q 共占 64 KiB，两份 sO 也占 64 KiB。源码用 224 KiB 预算计算 ring 槽数，因此留下 96 KiB：

| 项目 | 1CTA | 2CTA |
| --- | --- | --- |
| 每 CTA 的 Q 与 sO | 128 KiB | 128 KiB |
| 单个 K 或 V 槽 | 32 KiB | 16 KiB |
| 按预算计算的 `kv_stage` | 3 | 6 |

减半的是单个 K/V 槽的大小；槽数增加后可以预取更多搬运事件。224 KiB 是代码用于选槽数的预算，并非在宣称硬件容量。这一比较来自 [`_setup_attributes`][attributes]，不能从矩阵乘覆盖的行数翻倍直接推断实际吞吐翻倍。

**寄存器配额随角色分配。** 两组 Softmax 每线程上限分别为 176、176，Correction 为 88，最后四个轻量 Warp 为 72。四组各有 128 个线程，对应配额为 $128\times(176+176+88+72)=65536$ 个 32 位寄存器。`setmaxregister_decrease(72)` 将上限设为 72；释放的配额可供 Softmax 增加寄存器使用。MMA 的大累加器位于 TMEM，发射 Warp 因而可以使用较低配额。见[调参表][tuning]和 [`kernel` 中的分配][dispatch]。

以下分支会改变本文的部分描述，读到对应配置时再展开：

- `q_stage=1` 会调整 Softmax 与 Load/Empty 的角色；非 TMA KV 路径也会增加 Load 线程。
- 非 TMA 输出路径可由 Correction Warp 直接承担 epilogue，不再使用本文的独立 TMA store 路径。
- 某些 head dimension 或 SplitKV 配置会让 sO 与 sQ 复用 SMEM，并关闭 persistence；跨 work tile 的搬运安排随之改变。
- CLC（Cluster Launch Control）使用额外调度角色。Causal/local 路径采用 LPT 调度，优先安排工作量较大的 tile；哪些配置选择 1CTA/2CTA，需要查看同版本的 host dispatch。

> 主 kernel 独立接收 `is_causal` 和 `use_2cta_instrs`，调参表还包含 `2CTA + causal + D256`。因此，非 causal 是本文分析配置的一部分，不能泛化为“2CTA 必须非 causal”。

继续阅读时，可先从 `__init__`、`_setup_attributes` 确认配置，再沿 `kernel → load/mma → softmax_step/correction_loop → epilogue_s2g` 对照上述生命周期。[MagiAttention 导读](https://gin-sin.github.io/magiattention-blackwell-tutorials/index.html)可作为 Blackwell Attention 实现的扩展阅读。
