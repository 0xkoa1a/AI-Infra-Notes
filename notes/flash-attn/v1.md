# FlashAttention v1

FlashAttention v1 通过分块计算和 Online Softmax，在片上完成局部 Attention，避免在显存中保存完整的 Score 和概率矩阵。本文沿[原始论文的前向算法](https://arxiv.org/pdf/2205.14135#page=5)，解释它如何得到完整输出，以及主要节省什么。

## 标准 Attention 的存储与访存瓶颈

下面讨论自注意力前向，先省略 Mask、Dropout、Batch 和 Head 维度。设输入为：

$$Q,K,V\in\mathbb{R}^{N\times d}$$

其中：

- $N$ 是序列长度；
- $d$ 是 Head Dimension。

Scaled Dot-Product Attention 为：

$$S=\frac{QK^\top}{\sqrt d},\qquad P=\operatorname{softmax}(S),\qquad O=PV$$

Softmax 沿每一行的 Key 维度归一化；每个 Query 得到一组权重，再用它们对 Value 加权求和。中间结果和输出的形状为：

$$S,P\in\mathbb{R}^{N\times N},\qquad O\in\mathbb{R}^{N\times d}$$

HBM 是 GPU 的大容量显存。片上存储容量小，但访问带宽更高，因此适合保存正在计算的数据块。标准实现通常分成三个阶段，每个阶段通过 HBM 传递中间结果：

```text
QK^T → 将 S 写入 HBM
          │
          ▼
Softmax → 读取 S，将 P 写入 HBM
          │
          ▼
PV      → 读取 P 和 V，写回 O
```

$QK^\top$ 和 $PV$ 是计算密集的矩阵乘；Softmax、Mask 等操作则需要反复读取和写入中间结果。随着 $N$ 增长，完整的 $S$ 和 $P$ 都包含 $N^2$ 个元素，其显存占用和 HBM 流量会迅速成为瓶颈。

FlashAttention 希望每次只计算一个局部块，将它对输出的贡献累加后丢弃，从而省去完整 $S$ 和 $P$ 的 HBM 读写。

> 论文使用 HBM 与片上 SRAM 的简化模型分析访存。下面用“片上存储”描述数据驻留；具体实现由寄存器和 Shared Memory 承担这些数据，累加器不必存放在 Shared Memory 中。

## 分块 Attention 与 Online Softmax

FlashAttention 沿序列维度切分输入。设每个 Query Tile 包含 $B_r$ 个 Query，每个 KV Tile 包含 $B_c$ 个 Key 和对应的 Value，均保留完整的 head dimension：

$$Q_i\in\mathbb{R}^{B_r\times d},\qquad K_j,V_j\in\mathbb{R}^{B_c\times d}$$

其中 $i$、$j$ 分别是 Query Tile 和 KV Tile 的索引。每次只在片上计算一个局部 Score Tile：

$$S_{ij}=\frac{Q_iK_j^\top}{\sqrt d}\in\mathbb{R}^{B_r\times B_c}$$

$S_{ij}$ 的每一行对应一个 Query，$B_c$ 列对应当前 KV Tile 中的 Key。块大小需要让本轮使用的输入、局部 Score、输出累加值和行统计量共同放进片上存储。

分块解决了局部工作集的大小问题，但还有一个依赖：**每个 Query 的 Softmax 分母覆盖整行的全部 Key。** 当前 Tile 只包含其中一部分，块内归一化得到的概率还不是最终概率。因此，各块分别做 Softmax 后，不能直接把输出相加或简单平均。

**先看一个 Query、两个 KV Tile。** 为了方便手算，例子只展示 Value 的一个分量：

| KV Tile | 两个 Key 的 Score | 对应的 Value 分量 | 单独对这一块做 Attention 的输出 |
| --- | --- | --- | --- |
| 第一块 | $0,0$ | $2,4$ | $3$ |
| 第二块 | $\ln 2,\ln 2$ | $6,8$ | $7$ |

整行的指数权重为 $1,1,2,2$，所以第二块的总权重是第一块的两倍。将局部输出 $3$ 和 $7$ 相加得到 $10$，简单平均得到 $5$；正确输出需要按各块的总权重合并：

$$O=\frac{1\cdot2+1\cdot4+2\cdot6+2\cdot8}{1+1+2+2}=\frac{17}{3}.$$

实际计算指数时，通常先减去已见 Score 的最大值，防止指数过大。分子和分母都会乘上相同的因子，因此最终比值不变。这个例子中，第一块以最大值 $0$ 为基准，权重为 $1,1$；第二块到来后，最大值变为 $\ln 2$，旧权重需要乘以 $1/2$，变成 $1/2,1/2$，新块的权重则为 $1,1$。此时加权和为 $17$，分母为 $3$，输出仍然是 $17/3$。

**Online Softmax 保存能够继续合并的状态。** 它一块一块处理 Key，在新最大值出现时调整旧贡献的尺度。保留这个最大值、累计分母和 Value 加权结果后，就能丢弃已经处理过的局部 Score。下面将这个过程推广到一个 Query Tile；每一行独立执行相同的更新。

处理当前 $K_j,V_j$ 之前，每个 Query Tile $Q_i$ 使用三个状态概括已经处理过的所有 KV Tile：

- $m_i\in\mathbb{R}^{B_r}$：每个 Query Row 目前见过的最大 Score，用作稳定计算指数的基准；
- $l_i\in\mathbb{R}^{B_r}$：每个 Query Row 在该基准下累积的指数和，也就是当前归一化分母；
- $O_i\in\mathbb{R}^{B_r\times d}$：每个 Query Row 对已经处理过的 Value 得到的归一化输出。

尚未处理任何 KV Tile 时，令 $m_i=-\infty$、$l_i=0$、$O_i=0$，表示目前没有贡献。第一次加入包含合法 Key 的 Tile 后，便得到有效的分母和归一化输出。

现在处理新的 $S_{ij}$。先计算当前 Tile 自己的逐行最大值：

$$\widetilde m_{ij}=\operatorname{rowmax}(S_{ij})\in\mathbb{R}^{B_r}$$

减去逐行最大值后计算指数：

$$\widetilde P_{ij}
=
\exp\left(S_{ij}-\widetilde m_{ij}[:,\mathrm{None}]\right)
\in\mathbb{R}^{B_r\times B_c}$$

这里的 $[:,\mathrm{None}]$ 表示将每行的最大值广播到该行的所有列。$\widetilde P_{ij}$ 是当前 Tile 的未归一化权重，对应的逐行指数和为：

$$\widetilde l_{ij}
=
\operatorname{rowsum}(\widetilde P_{ij})
\in\mathbb{R}^{B_r}$$

旧状态使用 $m_i$ 作为指数基准，当前 Tile 使用 $\widetilde m_{ij}$ 作为指数基准。为了让两部分能够相加，先逐行取两者的最大值作为新的共同基准：

$$m_i'=\max(m_i,\widetilde m_{ij})\in\mathbb{R}^{B_r}$$

然后分别计算旧状态和当前 Tile 到新基准的缩放系数：

$$\alpha_{ij}=\exp(m_i-m_i'),\qquad
\beta_{ij}=\exp(\widetilde m_{ij}-m_i')$$

$\alpha_{ij},\beta_{ij}\in\mathbb{R}^{B_r}$，其中每个元素对应一个 Query Row 的缩放系数。

对于第 $r$ 行已经处理过的任意 Score $s$，将指数基准从 $m_{i,r}$ 改成 $m_{i,r}'$，等价于将原来的指数值乘以 $\alpha_{ij,r}$：

$$e^{s-m_{i,r}'}
=
e^{m_{i,r}-m_{i,r}'}e^{s-m_{i,r}}
=
\alpha_{ij,r}e^{s-m_{i,r}}$$

当前 Tile 中的指数值同理乘以 $\beta_{ij}$。缩放后，两部分处于同一个指数尺度，因此新的累计分母为：

$$l_i'
=
\alpha_{ij}\odot l_i+
\beta_{ij}\odot\widetilde l_{ij}
\in\mathbb{R}^{B_r}$$

这里的 $\odot$ 表示两个长度为 $B_r$ 的向量逐元素相乘。

由于 $O_i$ 是已经归一化的输出，旧状态在原尺度下的未归一化 Value 加权和是 $l_{i,r}O_{i,r,:}$。当前 Tile 在自身尺度下的未归一化 Value 加权和为：

$$\widetilde P_{ij}V_j\in\mathbb{R}^{B_r\times d}$$

将旧加权和乘以 $\alpha_{ij,r}$，将当前 Tile 的加权和乘以 $\beta_{ij,r}$，便可在新尺度下相加。对每个 Query Row $r$，新的归一化输出为：

$$O_{i,r,:}'
=
\frac{
\alpha_{ij,r}l_{i,r}O_{i,r,:}+
\beta_{ij,r}(\widetilde P_{ij}V_j)_{r,:}
}{l_{i,r}'}$$

每轮用 $m_i',l_i',O_i'$ 替换旧状态。所有 KV Tile 处理完成后，$O_i$ 已经包含整个 Key/Value 序列对 $Q_i$ 的贡献，因此就是完整 Attention 对应的输出。

> “精确 Attention”指上述分块合并与完整 Attention 在数学上等价，没有引入近似。浮点实现改变运算顺序后，舍入结果可能不同，并不保证逐位相同。

## v1 的完整前向流程

前文解释了一个 Query Tile 的状态如何更新。实际遍历还需要决定哪些数据先读入、能够复用多久。[原始 v1 算法](https://arxiv.org/pdf/2205.14135#page=5)采用 KV Tile 作为外层循环、Query Tile 作为内层循环，让同一份 KV 在片上服务多个 Query Tile。

输入 $Q,K,V$ 位于 HBM，输出 $O$ 和行统计量 $m,l$ 也在 HBM 中初始化。随后执行：

```text
在 HBM 中初始化 O = 0, l = 0, m = -∞

for each K_j, V_j Tile
    将 K_j, V_j 从 HBM 加载到片上

    for each Q_i Tile
        从 HBM 加载 Q_i, O_i, m_i, l_i
        计算局部 S_ij = Q_i K_j^T / sqrt(d)
        通过 Online Softmax 更新 m_i, l_i 和 O_i
        将 O_i, m_i, l_i 写回 HBM
        丢弃局部 Score 和未归一化权重
```

这里各类数据的生命周期不同：

- $K_j,V_j$ 在当前外层迭代中驻留片上，直到所有 Query Tile 都使用完它们。
- $Q_i,O_i,m_i,l_i$ 在处理当前 Query Tile 时读入；更新后的输出与统计量写回 HBM，供下一个 KV Tile 继续使用。
- 局部 $S_{ij}$ 和 $\widetilde P_{ij}$ 只在本次更新中使用，参与输出累加后即可释放。

Kernel Fusion 将局部矩阵乘、Softmax 和输出更新放进同一个 GPU kernel，连续消费这些片上中间结果。Tiling 控制工作集大小，Online Softmax 允许跨 Tile 正确合并，两者共同使这个融合流程成为可能。

> 对于 Causal Attention，先在局部 $S_{ij}$ 中屏蔽未来位置，再执行 Online Softmax；这些位置的指数权重视为 $0$。完全位于因果边界之外的 Tile 可以跳过。若某行在当前 Tile 中没有合法 Key，则保持该行旧状态，避免直接计算 $-\infty-(-\infty)$。

## 存储收益与剩余开销

这套计算顺序改变了中间结果的存放方式。需要区分三个量：

| 项目 | FlashAttention v1 的变化 |
| --- | --- |
| HBM 中的存储量 | 保留 $Q,K,V,O$ 这类 $O(Nd)$ 张量和 $O(N)$ 的逐行统计量，省去完整 $S,P$ 的 $O(N^2)$ 存储 |
| HBM 读写量 | 省去完整 $S,P$ 在算子之间的往返；在上述 KV-outer 流程中，$Q$ 随每个 KV Tile 重新读入，输出与行统计量则反复读入和写回 |
| 主要计算量 | 仍需计算全部有效 Query-Key 对及其 Value 贡献，dense Attention 的主要计算复杂度仍为 $O(N^2d)$ |

因此，固定 $d$ 时，存储量随序列长度线性增长。输入和输出状态仍可能多次读写，HBM 总流量并不因此变成线性。性能改善来自在片上完成局部计算，减少大矩阵的搬运；[论文的 IO 分析](https://arxiv.org/pdf/2205.14135#page=6)进一步说明了块大小与片上容量如何影响读写量。

> 训练时，反向计算仍需要 Score 和概率。FlashAttention 保存输出及逐行归一化统计量，在反向按需分块重算 $S,P$，因而也不必为反向保存完整的 $N\times N$ 概率矩阵。重算增加了一些计算，但减少了 HBM 读取；[原论文的重计算说明](https://arxiv.org/pdf/2205.14135#page=5)讨论了这一取舍。

v1 已经消除了完整注意力矩阵的 HBM 存储，但每轮输出归一化、GPU 上可并行的工作数量，以及计算单元之间的数据交换仍会影响速度。[v2](./v2.md)继续优化这些开销。
