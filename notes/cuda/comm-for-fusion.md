# 通算融合中的通信方式

这篇笔记讨论一个问题：当我们想把通信写进计算 Kernel 里面，可以使用哪些通信方式，它们分别处在什么层级，本质区别是什么。

本文只讨论数据全程留在 GPU 侧的路径，不讨论把数据先搬到 Host 内存再发出去的方式。

***

## 0. 为什么需要通算融合

### 通信开销无法被消除，只能被隐藏

单次通信的时间可以用最简模型描述：

$$T_{\text{comm}}=\alpha+\beta N$$

其中 $\alpha$ 是固定启动延迟，$\beta$ 是每字节传输时间，$N$ 是通信量。

在一个 Transformer Layer 中，通信与计算存在数据依赖，例如 TP 中的 GEMM 后接 AllReduce。如果串行执行：

$$T_{\text{total}}=T_{\text{comp}}+T_{\text{comm}}$$

理想的重叠可以把它压到：

$$T_{\text{total}}=\max(T_{\text{comp}},T_{\text{comm}})$$

这是通算融合能拿到的收益上界。要接近这个上界，前提是通信和计算之间存在可以被切碎的依赖：整体上 GEMM 的结果要全部参与 AllReduce，但**单个输出 tile 算完之后，它对应的那部分通信立刻就可以开始**。

### 非融合形态的三重代价

把通信当作一个独立算子，代价体现在三个地方：

```text
代价一：Kernel 边界的全局同步
  GEMM Kernel 必须整体结束，通信 Kernel 才能开始
  最后一个 tile 决定了通信的起始时刻

代价二：额外的 HBM 往返
  计算结果写回 HBM
  通信 Kernel 再从 HBM 读出来送走
  接收端写入 HBM，下游算子再读一次

代价三：资源争抢
  通信 Kernel 与计算 Kernel 争抢 SM、L2、HBM 带宽
  即使在时间上重叠了，两者的效率都会下降
```

前两项是结构性的，只能通过改变通信的发起方式来消除。第三项是融合之后依然存在、甚至更突出的问题，后面会专门讨论。

### 区分 Overlap 与 Fusion

这两个词经常混用，但它们对应的技术手段完全不同：

```text
Overlap（重叠）
  通信和计算仍是独立的 Kernel
  通过多 Stream、分块流水把它们在时间上错开
  调度粒度 = Kernel 粒度（或 chunk 粒度）

Fusion（融合）
  通信语义被写进计算 Kernel 内部
  一个 tile 算完，由计算它的那些线程直接把它发出去
  调度粒度 = tile 粒度
```

Overlap 只需要 Host 侧的调度技巧，Fusion 则要求**通信能够由 Device 侧的线程发起**。这是本文的核心分界线。

## 1. 三个平面：本文的分析框架

不同通信方式的差异，可以拆解到三个正交的平面上。后面每一节都会回到这三个维度。

```text
控制平面（Control Plane）：通信由谁发起
  Host 侧：CPU 向 Stream 里 enqueue 一个完整的通信 Kernel
  Device 侧：Kernel 内的 thread / warp / block 直接发起传输

数据平面（Data Plane）：数据怎么被搬运
  Buffer 中转：源 → 通信 Buffer → 链路 → 通信 Buffer → 目标
  直接远端访存：线程用普通 load/store 指令读写对端显存，零拷贝
  在网计算：交换机内部完成复制或归约

同步平面（Synchronization Plane）：完成性由谁保证
  Stream / Event：粒度是整个通信操作
  Kernel 内 Flag / Barrier / Signal：粒度是一个 tile 或一条消息
```

一个通信方式在这三个平面上的位置，直接决定了它能支持多细的融合粒度。三者之间有强耦合关系：

```text
控制平面在 Host  →  同步平面只能是 Stream 粒度  →  融合粒度不可能小于 Kernel
控制平面在 Device →  同步平面可以是 Flag 粒度   →  融合粒度可以到 tile
```

**通算融合的本质，是把通信的控制平面从 Host 下沉到 Device。** 数据平面的优化（零拷贝、在网归约）是重要的加速手段，但不改变融合的可行性；控制平面的位置才是决定性的。

## 2. 能力底座：硬件与地址空间

在讨论任何通信库之前，先看硬件本身提供了什么。上层库的能力边界完全由这一层决定。

### 2.1 域内：NVLink 与 NVSwitch

在一个 NVLink / NVSwitch 域内，GPU 之间的连接不是「网络」，而是**内存互连**。它提供的语义是访存，而不是消息传递：

```text
消息语义：我要发送一段数据，对端要有一个动作来接收
访存语义：我执行一条 load 指令，目标地址恰好落在对端的显存上
```

这个区别是根本性的。访存语义意味着：

* 单个线程就可以发起，不需要凑齐一个 Kernel 的所有线程；
* 不需要对端参与，对端 SM 可以在做完全无关的事情；
* 传输的最小粒度是一次访存事务，而不是一条消息；
* 延迟可以和本地 HBM 访问放在同一个量级去比较（NVLink 域内的远端访存延迟高于本地 HBM，但仍在同一数量级，远低于网络往返）。

第三代 NVSwitch 在此之上增加了两项在网计算能力：

```text
Multicast：一次写入，Fabric 复制到多个目标显存
In-Switch Reduction：一次读取，Fabric 从多个源显存取值、归约后返回
```

这两项能力把「一对多复制」和「多对一归约」从 GPU SM 的工作变成了 Fabric 的工作。对应的访问方式是特殊的 Multimem 指令（`multimem.st`、`multimem.ld_reduce`），它们操作的不是某个具体 GPU 的地址，而是一个映射到多份物理内存的多播地址。

### 2.2 跨节点：RDMA 与 GPUDirect

跨节点没有内存互连，只有网络。这里的硬件底座是 NIC，它的角色是一个**第三方 DMA 引擎**：

```text
GPU 显存 ──(PCIe/NVLink)──► NIC ──(网络)──► NIC ──► 远端 GPU 显存
```

GPUDirect RDMA 让 NIC 直接读写 GPU 显存，数据不经过 Host 内存。这是「数据平面不经 CPU」的部分，早已是标准做法。

但 RDMA 的语义是消息（或单边 Put/Get），不是访存：

* 传输需要构造一个工作请求，提交给 NIC 的队列；
* 需要敲一次 Doorbell 通知 NIC 有活干了；
* 完成需要通过完成队列或某种标志来检测。

于是就出现了一个关键问题：**这些控制动作由谁来做。** 这是跨节点场景下控制平面下沉的核心难点，第 5 节专门讨论。

### 2.3 分水岭：远端内存能否进入本地虚拟地址空间

把上面两节合起来看，真正划分层级的是一个问题：

```text
远端的那块内存，在我的虚拟地址空间里有没有一个地址？
```

* 如果有：Device 侧线程可以直接对它做 load/store，控制平面天然就在 Device 侧。
* 如果没有：任何传输都必须通过某种「提交请求」的机制，控制平面能否下沉取决于这个提交动作能否由 SM 完成。

让远端内存获得本地地址，涉及几层机制的叠加：

```text
物理可达性     NVLink / PCIe P2P 是否连通
跨进程共享     IPC Handle 把一个进程分配的显存导出给另一个进程
虚拟地址映射   把导出的物理内存映射到本进程的虚拟地址空间
多播对象       把多个 GPU 的物理内存绑定到同一个多播虚拟地址
```

这几层是递进关系：多播对象依赖虚拟地址映射，虚拟地址映射依赖跨进程共享，跨进程共享依赖物理可达性。后面讲的对称内存、NVSHMEM，本质上都是在这套机制上包装出一个好用的编程模型。

## 3. 层级一：Host-Driven Collective

这一层的代表是 NCCL，也包括其他以集体通信为核心抽象的库。

### 3.1 编程模型

它的抽象单位是 Collective：一个进程组内的所有 Rank 共同参与一次具有整体语义的操作，例如 AllReduce、AllGather、ReduceScatter、AllToAll。

```text
Host 侧：
  每个 Rank 在自己的 Stream 上 enqueue 同一个 Collective
  库根据拓扑选择算法（Ring / Tree / 分层 / NVLS 后端）
Device 侧：
  库启动自己的通信 Kernel，占用若干 SM 上的若干 Block（Channel）
  这些 Kernel 完成搬运、归约与 Rank 之间的握手
```

关键性质：**Collective 描述的是「最终每个 Rank 应该得到什么数据」，不描述数据什么时候到。** 它是一个原子的、不可拆解的语义单元。

### 3.2 三个平面上的定位

```text
控制平面：Host。CPU 决定何时发起，Device 侧无法在计算途中插入一次通信
数据平面：多数算法经内部通信 Buffer 中转；NVLS 后端可以走 Multimem
同步平面：Stream / Event。粒度是整个 Collective 的开始与结束
```

### 3.3 它能做到的融合，和做不到的融合

能做到的是 Overlap，手段是**把大 Collective 切成多个小 Collective**：

```text
把 GEMM 切成 K 个 chunk，计算与通信错开一拍：

Stream 0:  GEMM(0)  GEMM(1)  GEMM(2)  GEMM(3)
Stream 1:           Comm(0)  Comm(1)  Comm(2)  Comm(3)
```

这已经能覆盖相当一部分收益，且不需要改动 Kernel 内部，工程成本最低。但它有几个无法绕开的限制：

* **粒度受启动开销约束。** chunk 越小，$\alpha$ 的占比越高，也意味着更多次 Kernel Launch 和更多次 Stream 同步。存在一个最优 chunk 数，切得更细反而变慢。
* **依赖只能表达在 chunk 边界上。** Kernel 内部某个 tile 提前算完，这个信息无法传递给通信侧。真实的数据依赖比 chunk 边界细得多，这部分并行度被浪费了。
* **接收侧无法提前消费。** 下游算子必须等整个 Collective 完成，即使它需要的那一小块数据早就到了。
* **HBM 往返无法消除。** 数据必须落到 Buffer 里，通信 Kernel 才能读到它。

### 3.4 SM 争抢：一个被低估的代价

要打满 NVLink 带宽，通信 Kernel 需要开足够多的 Channel，每个 Channel 是一组 Block。这些 Block 和计算 Kernel 抢的是同一批 SM。

后果是：即使在时间轴上通信与计算完全重叠，两者的效率都低于各自单独运行时的水平。在 GEMM 这种对 SM 占用率敏感的算子上，这个损失可能吃掉一部分重叠带来的收益。

这也解释了为什么后面几层技术会反复强调「通信占用多少 SM」这件事——它是通算融合中的一个一等公民问题，而不是实现细节。

### 3.5 这一层的价值

尽管在融合能力上是天花板，这一层不可替代：

* **拓扑适配**：自动处理 NVLink、PCIe、多层网络交换机的混合拓扑，选择分层算法；
* **正确性与规模**：在任意规模、任意拓扑下都能正常工作，是所有优化方案的正确性基线与 Fallback；
* **工程成本**：不侵入算子实现。

合理的定位是：**它是基线，不是靶子。** 后面的层级是在特定条件（同一 NVLink 域、特定算子形态）下用更强的假设换取更细的粒度。

## 4. 层级二：对称内存与 Device-Side 访存

这一层开始，控制平面下沉到 Device 侧。前提是第 2.3 节说的那个条件成立：远端内存在本地虚拟地址空间里有地址。

### 4.1 对称内存解决的是寻址问题

对称内存（Symmetric Memory）的定义是：所有 Rank 在一段约定的堆上分配**大小与布局完全相同**的 Buffer，于是任意一个逻辑对象在所有 Rank 上都处于同一个相对位置。寻址退化为：

$\text{远端地址}=\text{base}[\text{peer}]+\text{offset}$

其中 `offset` 是所有 Rank 共享的，`base[peer]` 是一个在 Kernel 启动前就准备好的小指针数组。

为什么「对称」这个约束如此重要？因为它让**地址计算可以完全在 Device 侧完成**：

```text
非对称布局：
  想访问对端的某个对象 → 需要查询对端的分配信息 → 需要一次元数据交换
  这个查询无法在 Kernel 内低成本完成

对称布局：
  想访问对端的某个对象 → 本地 offset 直接可用 → 一次指针运算
```

一次指针运算是线程可以随手做的事。这就是对称内存成为所有 Device-Side 通信的地基的原因：它不是一个性能优化，而是**让 Device 侧发起通信在逻辑上成为可能**的前提。

另一个隐含收益是：对称性使得 Buffer 可以既是通信缓冲区、又是算子的输入输出张量。数据不需要为了通信而额外拷贝一次，这就是零拷贝的来源。

### 4.2 三种数据平面能力，按层级递增

在对称内存的基础上，Device 侧线程有三类操作可用，能力逐级增强：

#### （1）P2P 直接访存

把 `base[peer] + offset` 当成一个普通指针，直接 load 或 store。

```text
写远端（Push 模式）：
  我算完一个 tile → 直接 store 到对端的目标位置

读远端（Pull 模式）：
  我需要一个 tile → 直接从对端 load 进寄存器/共享内存
```

这是最朴素也最灵活的形式。特性：

* 零拷贝，无中间 Buffer；
* 粒度任意，可以细到一次向量化访存；
* 归约必须由本地 SM 完成（读回来自己加）。

Push 与 Pull 的选择不是风格问题，而是影响同步结构的设计决策：

```text
Push：生产者主动写出去，之后必须通知消费者「可以读了」
      → 需要生产者置 Flag，消费者等 Flag
Pull：消费者主动去拿，但它必须先知道「对端已经算好了」
      → 同样需要 Flag，只是等待方变成了拉取方
```

无论哪种，**同步信息本身也要通过远端访存来传递**，这是下一节的内容。

#### （2）Multimem：把复制与归约交给 Fabric

利用 NVSwitch 的多播地址，一条指令即可完成扇出或扇入：

```text
一次多播写：
  GPU 0 ──► NVSwitch ──┬──► GPU 1
                       ├──► GPU 2
                       └──► GPU 3

一次归约读：
  GPU 1 ──┐
  GPU 2 ──┼──► NVSwitch 归约 ──► GPU 0 的寄存器
  GPU 3 ──┘
```

相对 P2P 直接访存，它的收益在于：

* 一对多不再需要发起 $p-1$ 次独立传输，端点侧的指令数与访存事务数大幅下降；
* 归约的算术不再消耗 GPU 的计算资源和 HBM 带宽。

但要清楚它**不是**「零 SM 开销」：SM 仍然要发出 Multimem 指令、处理地址、参与同步、写回结果。它降低的是搬运与步数，而非彻底解放 SM。

#### （3）组合出的集体语义

有了上面两种能力，域内的 AllReduce 有两种典型构造方式：

```text
One-Shot：
  每个 GPU 对完整数据做一次归约读，直接拿到完整结果
  依赖链最短，端点通信量约 p·N
  适合小消息、延迟敏感

Two-Shot：
  ReduceScatter（每个 Rank 只归约自己负责的分片）
  → AllGather（把自己的分片多播出去）
  端点通信量约 2·(p-1)/p·N，与 Ring 的理想值相同
  但关键路径只有两个 Fabric 阶段，而不是 2(p-1) 步
```

对融合而言，这里真正重要的不是通信量公式，而是：**这两种构造都可以被拆开，嵌进计算 Kernel 的不同位置。** 例如把 ReduceScatter 阶段放进 GEMM 的 Epilogue，把 AllGather 阶段放进下一个算子的 Prologue。

### 4.3 同步平面：这一层最容易出错的地方

控制平面下沉之后，同步不再由 Stream 提供，必须自己在 Kernel 内构造。核心是一个 Flag（或 Signal）机制：

```text
生产者：写数据 → 保证数据已经对远端可见 → 写 Flag
消费者：轮询 Flag → 确认 Flag 已置位 → 保证能读到 Flag 之前写的数据 → 读数据
```

两个「保证」不是可选步骤。GPU 是弱内存模型，「我已经执行过写入」与「对端保证能读到这次写入」是两件不同的事。必须用带 Release 语义的写和带 Acquire 语义的读来建立跨 Rank 的 happens-before 关系，否则会出现「Flag 已置位但数据还是旧的」这种极难复现的错误。

同时要注意作用域（Scope）的选择：跨 GPU 的可见性要求比跨 Block 更强，不能用 Block 级的同步去保证系统级的可见性。

### 4.4 融合形态

有了上述三个平面的能力，典型的融合结构是这样的（只描述数据流）：

```text
Fused GEMM + ReduceScatter：
  GEMM 主循环算出一个输出 tile
    → 在 Epilogue 里判断这个 tile 属于哪个 Rank 的分片
    → 直接把它归约写到该 Rank 的对称 Buffer
    → 置对应的 Flag
  整个 Kernel 结束时，通信也已经结束

Fused AllGather + GEMM：
  Kernel 的 Prologue 需要某个远端 tile
    → 轮询该 tile 的 Flag
    → 直接从远端 load 进共享内存，进入主循环
  通信被隐藏在 GEMM 的流水线预取阶段里
```

注意这两种结构里，通信**没有专属的 SM**——它由计算线程在自己的空隙里顺手完成。这既是收益（无争抢、无额外 Kernel）也是代价（占用了计算线程的寄存器、共享内存和发射带宽）。

### 4.5 边界

这一层的全部能力都建立在「远端显存有本地地址」之上，因此**严格限制在单一 NVLink / NVSwitch 域内**。Multimem 还要额外要求 NVSwitch 具备在网计算能力。跨出这个域，需要一套新的抽象。

***

## 5. 层级三：NVSHMEM 与统一的 Device-Side 通信抽象

第 4 节的能力很强，但它的形态是「裸地址 + 裸指令」，而且过不了节点边界。NVSHMEM 做的事情是：把对称内存 + 单边通信 + Device 侧发起，抽象成一个在域内和跨节点都成立的统一模型。

### 5.1 PGAS 模型

NVSHMEM 采用 PGAS（Partitioned Global Address Space，分区全局地址空间）思想：

```text
存在一个全局的地址空间
它被划分成若干分区，每个分区归属一个 PE（Processing Element，通常对应一个 GPU）
访问自己分区 = 本地访存
访问别人分区 = 远端操作，语法上和本地几乎一致
```

对称堆是这个模型的载体：所有 PE 在对称堆上做相同的分配，于是「一个 offset + 一个 PE 编号」就唯一确定了全局地址空间中的一个位置。

### 5.2 单边通信（One-Sided）

这是理解 NVSHMEM 的关键。传统 MPI 风格是双边的：

```text
双边：Rank i 调用 Send，Rank j 必须调用匹配的 Recv
      两侧都要参与，需要配对，需要匹配 tag/size
单边：Rank i 发起 Put，把数据放进 Rank j 的内存
      Rank j 不需要执行任何通信动作
```

单边语义为什么对融合是必需的？因为在融合场景里，对端的 SM 正在忙着做自己的计算，**你不能要求它在某个时刻停下来配合你收数据**。双边语义会把两个 Kernel 的执行进度强行耦合在一起，而单边语义只要求对端的内存可写。

在此之上还有一类 Signal 操作：把「传输数据」和「置完成标志」组合起来，让接收侧可以只轮询标志，而不必猜测数据是否到齐。这正是第 4.3 节手写 Flag 机制的规范化版本。

### 5.3 发起粒度

NVSHMEM 的操作有不同的参与范围，这直接对应可用的融合粒度：

```text
单线程发起      一个线程搬一小块，适合不规则、细碎的访问模式
Warp / Block 协同发起  一组线程协作搬一大块，能拿到更好的合并访存与带宽
整个 PE 集合参与       集体操作，语义上接近传统 Collective
```

在融合 Kernel 里，通常用 Warp 或 Block 级的操作：它既能被自然地嵌入 tile 处理循环，又能保证足够的传输效率。

### 5.4 同一语义，不同代价：传输后端的差异

这是 NVSHMEM 最需要警惕的一点。同一个 Put 操作，在不同拓扑下的实现和代价完全不同：

```text
目标 PE 在同一 NVLink 域内：
  编译/运行时把它变成对远端地址的直接 load/store
  代价模型 ≈ 一次远端访存，延迟低，无协议开销

目标 PE 在其他节点：
  必须变成一次 RDMA 操作
  代价模型 = 构造请求 + 通知 NIC + 网络往返 + 完成检测
  延迟高出一到两个数量级，且对消息大小极其敏感
```

抽象的统一性带来了编程便利，但也带来了一个陷阱：**一段在单机上高效的细粒度访问模式，跨节点时可能因为消息过小、数量过多而完全崩掉。** 因此融合设计通常必须显式区分域内路径与跨节点路径，让跨节点传输的消息尽量聚合、数量尽量少——这正是第 7 节要讲的领域专用库的核心工作之一。

### 5.5 定位

回到三个平面：

```text
控制平面：Device。thread / warp / block 均可发起
数据平面：域内退化为直接访存，跨节点转为 RDMA 单边传输
同步平面：Signal 与原子操作，粒度可细到单条消息
```

NVSHMEM 的独特价值在于：它是目前把**跨节点**通信写进 Kernel 内部的主流路径。域内的融合可以用第 4 节的裸对称内存做，但一旦需要跨节点，就必须依赖这一层（或直接自己实现等价机制）。

## 6. 跨节点的关键跃迁：谁来敲 NIC 的门

第 5 节说跨节点的 Put 会变成一次 RDMA 操作。这里必须把「一次 RDMA 操作」拆开看，因为它涉及本文最核心的一次层级跃迁。

一次 RDMA 传输需要三件事：

```text
1. 构造工作请求（描述：从哪读、发给谁、写到哪、多大）
2. 敲 Doorbell（写一个寄存器，通知 NIC 有新请求）
3. 检测完成（读完成队列或某个标志）
```

数据本身走 GPUDirect RDMA，不经过 Host——这一点在所有方案里都一样。真正的分歧在于**上面这三件事由谁来做**。

### 6.1 三种控制路径

```text
路径 A：CPU Proxy
  GPU Kernel 写一个请求描述到某块内存 → 置 Flag
  CPU 上的 Proxy 线程持续轮询这个 Flag
  CPU 构造 WQE、敲 Doorbell
  CPU 轮询完成队列 → 回写状态给 GPU

路径 B：GPUDirect Async（部分卸载）
  CPU 提前把工作请求准备好排在队列里
  GPU Kernel 在合适的时刻触发它们
  减少了 CPU 的在线介入，但请求的构造仍在 CPU 侧

路径 C：IBGDA（GPU-Initiated）
  GPU 的 SM 直接构造工作请求、直接写 Doorbell
  GPU 的 SM 直接轮询完成信息
  控制平面完全在 Device 侧，CPU 不在关键路径上
```

### 6.2 必须区分的两种「经过 CPU」

这里有一个极容易混淆的点，需要显式说清：

```text
数据平面经过 Host 内存：
  GPU 显存 → Host 内存 → NIC → ...
  这是真正的低效路径，多一次 PCIe 往返和内存拷贝
  现代方案已经通过 GPUDirect RDMA 全面消除

控制平面经过 CPU：
  数据仍然是 GPU 显存 → NIC 直接读，不落 Host
  但「什么时候发」这个决定由 CPU 线程做出
  代价不是带宽，而是延迟与可扩展性
```

路径 A 属于后者。它的数据平面是干净的，问题在控制平面：

* **延迟链条长**：GPU 写 Flag 到 CPU 观察到，要经过 PCIe 与轮询间隔，这个延迟对小消息是致命的；
* **引入了 CPU 侧的串行瓶颈**：Proxy 线程数量有限，大量并发小消息会在这里排队；
* **破坏了 Kernel 内的自治性**：Kernel 想在内部完成一次通信并等待其完成，就必须依赖一个外部线程的进度，这在 Persistent Kernel 结构中尤其别扭。

所以路径 A 虽然数据平面高效，但它在控制平面上把通算融合的粒度重新钉回了粗粒度。理解它的局限，才能理解路径 C 的价值。

### 6.3 IBGDA 的本质与代价

IBGDA 的本质就一句话：**把 NIC 的队列与 Doorbell 暴露给 SM，让 SM 成为 RDMA 的发起者。**

它带来的能力：

* 一个 Warp 在 Kernel 内部就能完成「发出去 + 确认送达」的完整闭环，不依赖任何 CPU 线程；
* 消息发起速率不再受 Proxy 线程数量限制，可以随并发 Warp 数扩展；
* 跨节点通信终于可以像域内访存那样，被嵌入 tile 级的处理循环。

它的代价同样明确：

* **资源开销**：为了让多个发起单元并发工作而互不干扰，需要更多的队列资源。发起并发度越高，队列资源消耗越大，这对可扩展性构成上限；
* **SM 承担协议开销**：构造请求、管理队列指针、轮询完成，这些以前由 CPU 或 NIC 固件承担的工作现在落在 SM 上，会占用寄存器、指令发射带宽和线程时间；
* **小消息效应被放大**：既然发起变得廉价，就容易写出大量小消息的模式，而网络侧对每条消息都有固定开销。消息聚合的责任回到了上层设计者身上。

### 6.4 回到那个具体问题：RDMA 的完成检测要不要 SM 去做

在 Device-Initiated 模型下，答案是：**要，而且这是这套方案的固有成本，不是实现缺陷。**

可以这样理解这个取舍：

```text
让 CPU 做完成检测   → SM 不被占用，但控制路径长、延迟高、并发受限
让 SM 做完成检测   → 控制路径最短、粒度最细，但用掉了本可以算 GEMM 的线程
```

这不是「哪个更好」的问题，而是**用 SM 资源换控制路径长度**的定价问题。判断依据是具体场景：

* 消息小、数量多、延迟敏感（例如 MoE 的 Dispatch/Combine）：控制路径长度是瓶颈，值得付出 SM；
* 消息大、数量少、带宽受限（例如大张量的 AllReduce）：控制开销可以被摊薄，不值得为它牺牲 SM，用 Host-Driven 的方式反而更合适。

这也是为什么成熟的融合通信库会把「通信占用多少 SM」做成一个可调参数，而不是写死。

## 7. 层级四：领域专用融合通信库

前面三层是通用机制。这一层不引入任何新的硬件能力，它做的是**把特定算子的通信模式打包成专用原语**，代表是面向 MoE 的 DeepEP。

### 7.1 它替换掉了什么

以 MoE 的 Expert Parallelism 为例，朴素实现把一次 Dispatch 拆成多个独立算子：

```text
Router 输出 Top-k
  → Token 重排 / 打包
  → AllToAllV
  → 按本地 Expert 再次重排
  → Grouped GEMM
  → 反向重排 + AllToAllV + Unpermute
```

每个箭头都意味着一次 Kernel 边界、一次 HBM 往返、一块临时 Buffer，以及可能的 Host 侧同步（因为发送量取决于 Router 的运行时结果）。

专用库把这些合并成两个原语：

```text
Dispatch：按 Top-k 结果重排 token 并送到目标 Expert 所在的 Rank
Combine：把 Expert 输出送回原 Rank 并恢复原始 token 布局
```

### 7.2 收益来自领域知识，而非新机制

它的优化全部建立在「我知道这是 MoE 的 AllToAllV」这个假设上：

* **重排与传输融合**：token 的重排不需要单独一个 Kernel，直接体现在传输的源地址与目标地址计算里，省掉中间 Buffer 与 HBM 往返；
* **拓扑分层**：同节点内的 token 走 NVLink 直接访存，跨节点的 token 走 RDMA，两条路径的消息组织方式完全不同。通用库无法做这种区分，因为它不知道数据的语义；
* **消息聚合**：明确知道哪些 token 去同一个目标 Rank，可以把它们合并成少量大消息，规避第 6.3 节说的小消息问题；
* **动态形状的 Device 侧处理**：发送量由 Router 决定，是运行时才知道的。Device 侧发起的通信可以直接读取 Device 上的路由结果，不需要把它同步回 Host 再决定发多少——这是 Host-Driven 模型在动态场景下最难处理的部分；
* **SM 占用可控**：把用于通信的 SM 数量作为显式参数，让上层根据计算与通信的相对负载去调。

### 7.3 定位

这是层级三之上的**语义特化层**：

```text
层级一  通用集体语义，Host 驱动
层级二  通用访存能力，Device 驱动，域内
层级三  通用单边语义，Device 驱动，跨节点
层级四  特定算子语义，Device 驱动，全拓扑，人工调优
```

层级越高，适用范围越窄，但在其适用范围内的效率越高。它不是取代下层，而是构建在下层之上：这类库本身通常正是用对称内存 + NVSHMEM/IBGDA 实现的。

## 8. 横向对比与选型

### 8.1 主对比表

| 维度 | NCCL 等集体库 | 对称内存 P2P | Multimem / NVLS | NVSHMEM（域内） | NVSHMEM + IBGDA（跨节点） | 领域专用库 |
| --- | --- | --- | --- | --- | --- | --- |
| 控制平面 | Host | Device | Device | Device | Device | Device |
| 数据平面 | Buffer 中转 | 零拷贝直接访存 | 在网多播 / 归约 | 单边 Put/Get | 单边 Put/Get over RDMA | 融合原语 |
| 传输语义 | 集体 | 访存 | 访存 | 单边消息 | 单边消息 | 算子级 |
| 最小融合粒度 | Kernel / chunk | tile | tile | tile | 消息 | 算子 |
| 同步机制 | Stream / Event | Flag + Release/Acquire | 同左 | Signal | Signal + 完成检测 | 库内封装 |
| 归约计算位置 | GPU SM | GPU SM | NVSwitch | GPU SM | GPU SM | 视实现 |
| SM 开销 | 高（多 Channel） | 中 | 低到中 | 中 | 中到高（协议开销） | 可配置 |
| 作用范围 | 任意拓扑 | 单 NVLink 域 | 单 NVSwitch 域 | 域内 / 跨节点 | 跨节点 | 全拓扑 |
| 工程成本 | 低 | 高 | 高 | 中到高 | 高 | 低（若场景匹配） |

一个值得注意的规律：**从左到右，作用范围收窄或工程成本上升，换来的是融合粒度变细。** 没有一个方案在所有维度上占优。

### 8.2 选型判断

```text
是否需要细于 Kernel 的融合粒度？
├─ 不需要 → 集体通信库 + 多 Stream 分块重叠
│           工程成本最低，先把这条路走到极限
└─ 需要
   │
   ├─ 是否跨节点？
   │  ├─ 否（单 NVLink 域）
   │  │   ├─ 需要归约且数据量大 → Multimem 两阶段构造，把归约交给 Fabric
   │  │   ├─ 需要归约但消息小、延迟敏感 → Multimem 一阶段构造
   │  │   └─ 不需要归约（AllGather / AllToAll 类） → 对称内存 P2P 直接访存
   │  │
   │  └─ 是（跨节点）
   │      ├─ 消息大、数量少 → 仍然优先考虑集体通信库，控制开销可摊薄
   │      └─ 消息小、数量多、动态形状 → NVSHMEM + GPU-Initiated RDMA
   │
   └─ 是否有匹配的领域专用库？
      └─ 有且场景吻合 → 直接用，别自己重写
```

另一个横向判断依据是**通信与计算的相对负载**：

```text
通信远快于计算  → 融合收益小，不值得付出复杂度，别做
两者量级相当    → 融合收益最大，是主要目标场景
通信远慢于计算  → 融合能隐藏的部分有限，应该先考虑改并行策略降低通信量
```

最后一条尤其重要：通算融合是在**降低通信量之后**才该做的优化。如果并行切分本身就选错了，融合只是在给一个错误的方案打补丁。

## 9. 通算融合的共性陷阱

这些问题与具体用哪个库无关，是控制平面下沉之后必然要面对的。

### 9.1 内存可见性

最高频的错误来源。三种典型形态：

```text
漏掉 Release / Acquire 语义
  → 消费者看到 Flag 已置位，读到的却是旧数据
  → 表现为偶发的数值错误，规模越大越容易出现

作用域选错
  → 用 Block 级或 Device 级的同步去保证跨 GPU 的可见性
  → 在小规模测试中「碰巧」正确，扩大规模后暴露

Flag 与数据的顺序颠倒
  → 编译器或硬件重排导致 Flag 先于数据可见
```

这类 bug 的共同特点是不可靠地复现，且在小配置下往往测不出来，因此必须靠推理而非测试来保证正确性。

### 9.2 死锁与调度假设

Kernel 内轮询远端 Flag，隐含了一个假设：**对端那个负责置 Flag 的 Kernel 已经在运行了。**

```text
如果对端 Kernel 还没被调度：
  本端 Kernel 占着 SM 无限轮询
  对端可能正在等一个需要本端资源的前置 Kernel
  → 死锁
```

这在下列情况下容易发生：Persistent Kernel 结构、多 Stream 混合、Kernel 占用的资源超过单次可驻留的上限、不同 Rank 的执行进度存在系统性偏差。缓解手段是保证参与融合的 Kernel 在所有 Rank 上被同时启动且能够同时驻留，但这本身就是一个额外的全局约束。

### 9.3 资源争抢换了形式，没有消失

融合把通信搬进计算 Kernel，Kernel 边界的争抢消失了，但出现了新的争抢：

```text
寄存器压力  通信逻辑需要额外寄存器 → 占用率下降 → GEMM 效率下降
共享内存    通信的暂存区与 GEMM 的 tile 缓冲争抢容量
指令发射    地址计算、Flag 轮询占用发射带宽
L2 与 HBM   远端访存与本地访存共享同一套访存通路
```

结果可能是：重叠做到了，但 GEMM 从 90% 的峰值掉到 75%，净收益被吃掉大半。**必须实测端到端时间，而不是只看重叠率。**

### 9.4 尾部效应被放大

融合把通信绑在计算的时间片上，任何不均衡都会直接传导：

```text
某个 Rank 计算慢一点 → 它的通信也晚 → 依赖它的所有 Rank 一起等
MoE 中某个 Expert 负载偏高 → 该 Rank 成为全局瓶颈
```

非融合形态下，通信是一个整体操作，某些不均衡可以在 Buffer 里被吸收；融合形态下依赖链更紧，抖动的传播更快。

### 9.5 正确性验证困难

```text
归约顺序不确定 → 浮点结果与基线不逐位一致，需要用容差比较，掩盖真实 bug 的空间变大
时序相关 bug   → 单元测试规模下不出现
调试手段受限   → Kernel 内的通信状态难以观测
```

实践上的建议是：保留一条基于集体通信库的、拓扑无关的实现路径作为正确性基线，融合实现始终与它对比。这条路径的存在价值不只是 Fallback，更是唯一可信的参考答案。

## 10. 小结

把全文压缩成几句话：

* 通算融合的收益上界由 $\max(T_{\text{comp}},T_{\text{comm}})$ 给出，接近这个上界需要 tile 级的依赖表达；
* 决定融合粒度的是**控制平面在 Host 还是 Device**，而不是数据平面用了什么加速手段；
* 控制平面下沉的前提是寻址可以在 Device 侧完成，这就是对称内存存在的理由；
* 域内的底座是访存语义（P2P、Multimem），跨节点的底座是消息语义（RDMA），两者的代价模型差一到两个数量级，统一的抽象不能掩盖这个差别；
* 跨节点控制平面下沉的关键是让 SM 直接驱动 NIC，代价是用 SM 资源换控制路径长度；
* 层级越高、假设越强，效率越高但适用范围越窄；集体通信库是不可替代的正确性基线；
* 同步正确性、调度假设、资源争抢是融合的固有成本，必须以端到端实测判断收益。
