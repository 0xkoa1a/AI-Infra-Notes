# ROLLER：按硬件特点构造分块，减少 Kernel 调优的尝试

同一个矩阵乘法，可以采用许多分块大小、线程分工和存储安排。全部生成代码、编译、运行一遍，通常要花很长时间。**ROLLER 希望先根据计算和硬件特点，构造少量有希望的实现，再把昂贵的实测留给这些候选。**

它是一套张量编译器。输入是算子的计算表达式、形状和硬件信息，输出是 GPU kernel。它自己构造候选，不需要 LLM Agent 提出方案。对我们的 Agent + Compiler 调研，它提供了一个具体参照：**在开始写代码之前，怎样用数据复用、存储容量和访存成本收窄选择。**

> 本文依据 OSDI 2022 论文 [ROLLER: Fast and Efficient Tensor Compilation for Deep Learning](https://www.usenix.org/system/files/osdi22-zhu.pdf) 编写。下文的矩阵分块数字是教学示例；实验数字来自论文。原文主要在 V100、K80 等设备上评价，硬件参数需要针对新设备重新确定。

## 动机：好实现很多，为什么还要试这么久

矩阵乘法的分块存在两种相反的需求。块大一些，同一份输入可以用于更多输出，减少重复搬运；块小一些，每块占用的资源更少，也能分出更多块同时工作。到底选多大，要结合矩阵形状和 GPU 的能力判断。

搜索式编译器可以尝试许多配置，用运行时间判断优劣。但每个候选都需要生成程序、编译并测量。ROLLER 观察到，硬件已经排除了很多选择：矩阵指令只接受特定形状，访存有事务粒度，共享内存和寄存器有容量上限。先利用这些信息，就能少试一些明显不合适的配置。

**核心取舍是：接受一个有适用范围的近似模型，换取更少的设备评估。** 模型负责把好候选排到前面，最终速度仍由 GPU 实测确认。[论文第 2、3 节](https://www.usenix.org/system/files/osdi22-zhu.pdf#page=3)

## 方法：先构造分块，再比较少量候选

ROLLER 将这类分块称为 **rTile**。一个 rTile 记录逻辑上计算哪块数据，以及这些数据在某层存储中怎样排列。根据输出块和计算表达式，可以推导它需要哪些输入，再估计空间和搬运量。

下面的箭头表示候选怎样逐步收窄。最后进入设备编译和实测的，已经是筛选后的少量方案。

```mermaid
flowchart LR
    I["计算与硬件信息"] --> A["对齐的初始分块"]
    A --> G["按复用收益扩大"]
    G --> R["容量与吞吐检查"]
    R -->|继续扩大| G
    R --> K["少量候选"]
    K --> M["编译、实测"]
    M --> O["选最快实现"]
```

### 分块大了，为什么可能更快

用一个矩阵乘法教学示例看这件事。假设输入是 FP16，一个线程块负责一块输出，每次沿相乘求和的维度取 32 个元素。这里比较的只是**一轮输入加载**，暂不计多缓冲、布局填充和输出写回。

| 输出块 | 本轮需要的两块输入 | 输入空间 | 相对于小块的乘加工作量 |
|---|---|---|---|
| 64 × 64 | 64 × 32 与 32 × 64 | 8 KiB | 1 倍 |
| 128 × 128 | 128 × 32 与 32 × 128 | 16 KiB | 4 倍 |

输出的行、列都翻倍后，乘加工作量变成四倍，输入却只变成两倍。原因是每个输入元素被用于更多输出。**如果原来在等待输入，增加复用就可能让相同的访存支撑更多计算。**

代价也同时增加。更大的输出块需要保留更多累加值，输入缓冲也变大。一个 SM 是执行线程块的硬件单元；每块占用更多寄存器或共享内存后，一个 SM 能同时容纳的块可能减少。原来有其他块可以在访存等待时继续执行，调整后可能缺少这样的工作。

因此，选块大小要一起回答两件事：少搬了多少数据，又多占了多少资源。这个教学例子中的空间只是输入数据大小；估算一个具体实现时，还要考虑同时保留的缓冲和累加结果。

### 从硬件合适的大小开始，沿有收益的方向扩大

ROLLER 先让分块对齐目标硬件的执行和访存粒度。例如，矩阵指令要求特定的计算形状；连续访存通常要与内存事务匹配；共享内存的排列也会影响访问是否冲突。必要时，它加入少量填充，把逻辑数据安排成适合硬件访问的形状。

然后，它逐步扩大分块。每次比较：**沿哪个维度扩大，能用较少的新增空间，换来较多的访存减少？** 这使构造过程沿着数据复用的方向推进，而不必枚举所有尺寸组合。

这个过程会在各级存储和执行范围上重复：先安排较小范围的计算与数据，再组合成更大范围的分块。容量达到限制，或该层的数据供应已足以支撑计算时，就不再一味扩大，而继续考虑其他层的安排。[论文第 3.1、3.2 节](https://www.usenix.org/system/files/osdi22-zhu.pdf#page=4)

在 GPU 上，各层有不同的职责：线程用寄存器保留局部数据，线程块通过共享内存协作，多个线程块分担整张输出。模型要分别考虑各层的数据访问与容量，不能只看显存带宽。

> **扩大哪个维度，取决于计算关系。** 在 GEMM 中扩大输出行或列，会改变输入的复用次数；单纯扩大沿求和维度的一轮加载量，并不自动得到相同收益。这也是从算子表达式推导输入块的作用。

**还要留出足够的并行工作。** 对大矩阵，一个好的线程块方案可以复制到很多输出区域。对小矩阵，块太大可能只剩下几个线程块，无法用上足够多的执行单元。ROLLER 因此也会缩小分块，以增加并行度。复用率高与整个 GPU 忙起来，是两个需要共同满足的目标。

### 模型具体估什么

ROLLER 的估计围绕三个对象展开：

- **空间需求。** 根据分块和数据排列，估计各层存储中占用的空间，包括填充，并检查容量。
- **数据搬运。** 估计各层需要传输多少数据，以及目标访问方式能达到怎样的访存性能。
- **数据能否足够快地送到计算单元。** 如果数据供应不足，优先提高复用；如果已有足够的数据供应，再扩大块可能只增加空间需求。

搬运时间的基本估法很直观：要搬的数据越多，时间越长；可用带宽越高，时间越短。如果数据量为 $D$，有效带宽为 $B$，粗略时间就是：

$$
T_{\rm transfer} \approx \frac{D}{B}.
$$

这里的有效带宽要对应存储层级和访问方式。小块访问未必能用满设备标称带宽。ROLLER 会预先测量并缓存部分小访问的性能，也用微基准取得计算性能参照。对于共享某层带宽的执行单元，它采用简化的带宽分配假设。[论文第 3.3 节](https://www.usenix.org/system/files/osdi22-zhu.pdf#page=7)

**寄存器数量在这里主要是容量约束。** 编译器可能额外产生地址和临时变量，也可能改变值的保留方式，因此逻辑上的数据量无法直接给出最终寄存器分配。ROLLER 在 V100、K80 实现中采用每线程 96 个寄存器的保守限制，为设备编译器留出余量。这个数是论文的实现选择，迁移时需要重新判断。[论文第 4 节](https://www.usenix.org/system/files/osdi22-zhu.pdf#page=8)

> 模型没有精确模拟实际 warp 调度、所有指令开销和编译器行为，也未展开多缓冲等空间需求的完整聚合规则。论文中，线程与并行块数量不足时，模型误差变大；小或不规则算子还可能难以构造充分对齐、复用良好的分块。

### 为什么最后仍要编译和实测

相同的高层分块，经设备编译器处理后，指令安排和寄存器分配可能不同。这会改变并行度和执行效率。ROLLER 因此保留少量候选，编译成机器码，在目标设备上运行，再选择候选中实测最快的实现。

论文通常构造约 5–20 个候选，并比较只取首选方案与测量前 10 个候选的做法。测更多候选更有机会纠正模型排序，但也付出更多编译和评估成本。**模型的价值在于减少要测的数量；实测的价值在于修正模型没有覆盖的细节。**[论文第 3.2、4 节](https://www.usenix.org/system/files/osdi22-zhu.pdf#page=7)

## 实验：省下多少尝试，保留了怎样的性能

论文在 V100 上评价了 119 个算子。最能说明开发成本差异的是下面两个口径：

| 做法 | 平均时间 | 应怎样理解 |
|---|---|---|
| ROLLER Top-1 | 0.43 秒 | 论文报告的首选结果生成时间，主要花在递归构造；计时阶段未逐项说明 |
| ROLLER Top-10 | 13.3 秒 | 编译、评价多个候选，主要时间花在设备编译和设备评估 |
| TVM、Ansor 对照 | 约 0.65、0.66 小时 | 作者在同组算子、所用搜索配置下报告的平均编译时间 |

在同一组算子上，论文报告 ROLLER 有 81.5% 的算子达到 CUDA 库性能的 10% 范围内，59.7% 比库实现更快。它的主要弱项包括较大卷积：cuDNN 可采用 Winograd 等算法，而改变分块无法替代这种算法选择。[论文第 5.1 节](https://www.usenix.org/system/files/osdi22-zhu.pdf#page=10)

这些结果支持“少量候选可以保留较好的算子性能”，同时也说明**分块与存储调度受输入计算表达式约束**。只在给定表达式下挑分块，无法自动替代 Winograd 这类算法变化。

> 论文还把 ROLLER 接入 Rammer，评价完整模型。那些结果同时受计算图调度、融合和 kernel 性能影响，不能全部归因于分块模型。算子级编译速度也不等于 Agent 从理解任务到交付的总时间。

## 对我们当前调研的帮助

ROLLER 给出的开发指导是：**先把一个方案要搬的数据、要保留的值和可并行的工作算清楚，再决定哪些配置值得实现。** 这样，Agent 可以先排除容量明显超限的方案，再围绕复用收益与并行度选择少量候选，减少编译和测量次数。

与 [CAKE](./CAKE.md) 相比，ROLLER 更明确地规定了怎样构造分块、怎样用近似模型引导构造；CAKE 让 Agent 写出执行安排，再由编译器检查、估计并返回反馈。与 [KernelPro](./KernelPro.md) 相比，ROLLER 的主线在候选生成之前，KernelPro 的主线在运行之后：解释指标，再决定下一次改动。

我们的 Grouped GEMM + Reduce 还需要补充一层估计：归约何时拿到输入，两项工作能否同时驻留，以及共同执行后各自慢多少。ROLLER 的分块和资源估计可以帮助提出候选，但这类依赖与竞争需要结合实际路由、执行安排和测量继续建模。相关问题见 [Agent + Compiler 总览](./agent-compiler-overview.md)。
