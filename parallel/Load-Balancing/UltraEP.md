# UltraEP

UltraEP 是一个面向 Rack-Scale Node（RSN，机架规模的 scale-up 域）的 EP 负载均衡器。它与 EPLB 的分界可以用一句话说清：

```text
EPLB：   用「历史统计」的负载，周期性地重算放置方案
         求解在关键路径之外，可以慢慢算
UltraEP：用「当前 microbatch 的精确负载」，每层都重算
         求解与权重搬运都在关键路径上，必须极快
```

这一个改动会连锁改变几乎所有设计决策。本文的主线就是追踪这条连锁反应。

背景（MoE 结构、Dispatch/Combine、不平衡度 $\rho$、纯重排的下界与冗余的必要性）见同目录 `background.md`，本文不再重复；DeepSeek EPLB 的具体做法见同目录 `EPLB.md`。UltraEP 面向训练与推理 Prefill，不面向 Decode，原因在末尾的适用边界一节说明。

---

## 一、动机：历史统计为什么不够

`background.md` 已经说明负载是数据相关的。UltraEP 的出发点是把这句话再往下拆一层：负载不只是「不均匀」，它还是**非稳态**的。

```text
skewed（倾斜）：      少数 Expert 拿走远超平均的 token
heterogeneous（异质）：不同层的热点分布互不相同
non-stationary（非稳态）：热点会随时间漂移，而且漂移得很快
```

前两条 EPLB 已经处理了（复制削峰、逐层独立求解）。真正扎手的是第三条。

**Serving Prefill 侧。** 热点分布会随请求的语义域整体平移：代码类、数学类、科学类流量激活的 Expert 集合不同。更麻烦的是即使限定在同一个域内，热点也会逐 batch 漂移；而混合域流量会把多种路由模式叠加起来，让分布更难预测。

**Training 侧。** 训练早期 Router 尚未形成稳定的专业化分工，负载剧烈波动。训练后期平均分布变平滑了，但短期动态依然存在，而且**部分是被均衡机制自己制造出来的**：辅助损失或路由 bias 是一种负反馈——它压低当前过载的 Expert、抬高欠载的 Expert，于是负载在两个方向之间来回摆动。加上采样随机性带来的 microbatch 间抖动，瞬时分布始终在动。

### 滞后的方案可能是负收益

这是最关键的一条论断，也是 UltraEP 全部设计的立足点。

基于历史的均衡器隐含一个假设：**接下来的负载分布与刚刚统计到的差不多。** 一旦这个假设不成立，为旧热点准备的副本容量落在了现在的冷门 Expert 上，而新冒出来的热点没有任何副本可用。

```text
理想情况：方案与实际热点吻合 → 削掉峰值
假设失效：方案对准了旧热点   → 副本空转
                              → 新热点无副本，成为新的 straggler
最坏情况：比不做均衡更差
```

也就是说，历史统计的误差不是「收益打折」，而可能是**负收益**。

大 EP 会放大这个问题。EP 度越大，每个 Rank 持有的主专家越少（常见只有两到四个），于是单个 Expert 的路由波动几乎直接就是该 Rank 的负载波动，没有任何「多个 Expert 互相平均」的缓冲效果。换句话说：**EP 度越大，Rank 级负载越像单个 Expert 的负载，抖动越剧烈。**

结论是：要在这种负载下拿到稳定收益，必须对**瞬时负载**做出反应，而不是从过时的测量里外推。

## 二、把精确负载拉进关键路径

「实时用精确负载」听起来需要额外的信息采集，其实不需要。

EP 的 Dispatch 本身就要求先交换路由元数据（每对 Rank 之间发多少、偏移在哪），否则不等长的 AllToAllV 无法执行。这一步做完之后，**全局的精确负载已经在每个 Rank 手上了**。UltraEP 复用这次已有的元数据交换，不引入新的通信。

更重要的一个性质是：既然每个 Rank 都拿到了完全相同的全局负载，那么只要求解算法是确定性的，各 Rank 各自独立算出来的方案必然一致，**不需要任何额外同步**，也不需要一个中心节点做决策。

```text
拿到精确负载 = 免费（复用已有的路由元数据交换）
方案一致性   = 免费（相同输入 + 确定性算法）
真正的代价   = 求解与权重搬运进入了关键路径
```

代价具体是什么？前向的顺序变成了：拿到路由信息 → 求解方案 → 把主专家权重分发给远端副本 → 才能开始 token 的 Dispatch。权重分发不能与 Dispatch 并行，因为两者争抢同一份带宽。于是求解与权重分发都**暴露在关键路径上**。

这就把问题的性质彻底改变了：

```text
EPLB 的难点：   在充足预算下把方案求得尽量好
UltraEP 的难点：在极短窗口内求出一个足够好的方案，并把权重搬完
```

后文的每一个设计——只复制不重排、quota 作为耦合变量、GPU 上求解、持久化 tile 流式传输、relay 化 fan-out——都是在回答同一个问题：**怎么把这条关键路径压到足够短。**

## 三、只复制，不重排

UltraEP 的第一个减法：**主专家的位置永不改变，均衡只靠添加副本完成。**

每个 Rank 上预留两类槽位：

```text
主槽位（main slot）：      放该 Rank 名下逻辑专家的原始实例，位置固定
冗余槽位（redundant slot）：放某个逻辑专家的一份副本，或者空着
```

每个 Rank 的两类槽位数量都相同，同一个逻辑专家不允许在同一个 Rank 上出现两次。于是逻辑到物理是一个一对多映射：每个逻辑专家有一个固定的主实例，加上零个或多个副本。

### 为什么放弃重排是划算的

`background.md` 指出「只做放置受制于 $\max_e w_e$」，所以复制是必需的。但反过来，「复制之后还必须重排」并不是必然的。大 EP 下这个取舍很清楚：

```text
重排能改变的：  每个 Rank 手上那两三个主专家的归属
                可调整的局面本来就很小 → 边际收益递减
重排要付出的：  主专家的完整状态（权重、梯度、优化器状态）迁移
                运行时布局不再确定，控制逻辑复杂
                原有的数据局部性被打乱
                这些代价并不随 EP 度增大而变小
```

一边是随 EP 度递减的收益，一边是不随 EP 度递减的代价，交点很早就过去了。相比之下，复制直接给真正的瓶颈——那几个最热的 Expert——扩容，钱花在了刀口上。

固定布局还有一个容易被低估的好处：**运行时是确定性的。** 主专家在哪永远不变，只有副本这一层在动，寻址逻辑、buffer 布局、算子形状都可以按固定布局写死。这在一个每层都要重算方案的系统里非常关键——如果连主专家的位置都逐层变化，运行时的复杂度会失控。

## 四、显存：把空间问题换成时序问题

冗余槽位要占显存，而它是逐层都要用的。如果每层每个冗余槽位都常驻一份权重和梯度，显存开销会非常可怕（一个近百层的 MoE 模型上，单个冗余槽位的权重加梯度可以达到接近十 GB 的量级）。

UltraEP 的做法是两条：

```text
不存优化器状态：优化器更新只在主专家上做
                副本只是「临时的计算容量」，不是一份独立的参数
                → 反向结束后副本的梯度必须归约回主专家，才能保持与
                  无副本时数学上的等价性
跨层复用 buffer：所有层共用同一份冗余槽位的权重/梯度缓冲区
                → 显存从「层数 × 槽位」降到「槽位」，降低两个数量级
```

但跨层复用不是白拿的。既然所有层共用一份 buffer，那么某一层的副本权重必须**在这一层要用它之前刚好写进去**，而且用完就要腾出来给下一层。于是：

**跨层复用把一个显存容量问题，换成了一个逐层的时序问题。** 每一层都出现一个硬性的权重物化 deadline，而这个 deadline 正落在前向关键路径上。反向同理：副本梯度归约必须在下一个 MoE 层开始之前完成，否则 buffer 还没腾空。

这也解释了为什么第九节要花那么大力气优化权重分发的有效带宽——它不是锦上添花，而是这个设计能否成立的前提。

## 五、目标函数：每一项由谁决定

UltraEP 把均衡写成一个逐层、逐 EP 组独立求解的在线优化问题。看目标函数最有价值的地方不是它的形式，而是**每一项的代价由谁决定**。

前向要最小化的是四件事的总时间：求解方案、重路由、把权重分发给副本、token 的 AllToAll，以及最后的 MoE 计算。这几项里有的可以互相重叠，有的必须串行，所以真实形式是「求解 + max(重路由, 权重分发) + token AllToAll + MoE 计算」这样的混合结构。反向则简单得多：副本相关的通信（权重重新物化、梯度归约）都能藏在计算下面，暴露出来的只剩 token AllToAll 与 MoE 计算本身。

三个主要代价项的直觉如下。

**MoE 计算耗时由重路由之后最忙的那个 Rank 决定。** 它拿到的 token 最多，别人都得等它：

$$T_{\text{moe}}\ \propto\ \max_{r}\sum_{e}q_{er}$$

其中 $q_{er}$ 是 Expert $e$ 在 Rank $r$ 上那个物理实例分到的 token 数（下文称**配额**，quota）。这里的 $\sum_e q_{er}$ 就是 `background.md` 里的 $L_r$，只是现在它由配额直接给出而不是由放置隐式决定。

**token AllToAll 的耗时由最忙的收发方决定**，一个 Rank 既要发出自己的 token、又要收进别人发来的 token，两者取最大：

$$T_{\text{a2a}}\ \propto\ \max_{r}\max\!\left(\ \text{该 Rank 发出的总量},\ \ \text{该 Rank 收进的总量}\ \right)$$

值得注意的是发出量基本是固定的（训练时由 microbatch 形状决定，Prefill 时被 chunk 大小限制住），所以**能优化的其实只有收进量**，而收进量正是配额之和。这意味着均衡计算与均衡通信仍然是同一件事，与 `background.md` 「一次均衡治两个症状」的结论一致。

**权重分发的耗时由持有最热主专家的那个 Rank 决定。** 一个 Rank 要往外推的权重份数，等于它名下所有主专家的副本数之和：

$$T_{\text{distr}}\ \propto\ \max_{r}\sum_{e\ \in\ \text{Rank } r\text{ 的主专家}}\left(|H_e|-1\right)$$

其中 $|H_e|$ 是 Expert $e$ 的物理实例总数，减 1 是因为主实例自己不用传。这一项是 UltraEP 相比 EPLB 全新出现的代价：**副本开得越多越均衡，但要搬的权重也越多，而搬运就在关键路径上。** 均衡质量与均衡开销第一次被放在了同一个目标函数里，这也是后面 relay 设计要解决的问题的源头。

约束方面有四条值得记住：主专家位置不可变；每 Rank 的冗余槽位数有预算，且同一逻辑专家不能在同一 Rank 上重复；反向引入的副本通信必须完全被计算掩盖（否则反向也会出现暴露开销）；每个新建的副本必须至少分到一个**最小配额**，否则不值得为它付出搬运成本。最后这条约束在下一节会看到它的作用。

## 六、Quota：用配额作为耦合变量

这是 UltraEP 最核心的算法洞察，也是它与 EPLB 类方法在思路上分道扬镳的地方。

### 先定副本再补路由，问题在哪

传统的分工是两段式的：

```text
离线：先决定副本集合与放置（有充足预算，可以精细求解）
在线：再决定 token 怎么分给这些副本（预算极少，常用轮询或小修补）
```

这个分工在离线场景下是合理的。但当负载是精确且实时的时候，它会产生一类**无效副本**：某个副本在放置阶段看起来是合理的（它让某个启发式指标变好了），但在线路由阶段实际分给它的 token 很少。

```text
副本被创建 → 权重被搬运（付出了关键路径上的时间）
          → 实际只分到很少 token（没有削掉任何峰值）
          → 净亏损
```

根因是**放置阶段优化的目标与运行时实际发生的事情之间有一层间隔**。`EPLB.md` 里讨论过的「均摊假设」是这个问题的另一面：EPLB 假设 token 能在副本间均匀分摊，但保证这件事的机制在它职责之外。当均衡开销进入关键路径后，这层间隔就从「假设可能不成立」升级成了「实打实的浪费」。

### UltraEP 的做法：直接解最终配额

UltraEP 不先定副本，而是直接求解**每个物理实例最终要承担多少 token**，也就是配额表 $\{q_{er}\}$。然后：

```text
配额是决策变量
  ├─ 复制：只是「把非零配额的实例物化出来」
  └─ 重路由：只是「把配额分解成逐源 Rank 的份额」
```

两件事都变成了配额的推论，而不是两个需要各自求解、再想办法对齐的子问题。**放置与路由之间那层间隔被消掉了**：一个副本只有在被赋予了实际配额时才会存在，所以不存在拿不到流量的副本。

### 阈值的二分搜索

具体怎么解？先换一个提问方式。不直接问「怎么分配最均衡」，而是问一个判定问题：

**给定一个负载上限 $\theta$，能不能只靠加副本，把所有 Rank 的负载都压到 $\theta$ 以下？**

对一个候选的 $\theta$，每个 Rank 落在两种角色之一。超出上限的部分是它必须甩掉的**超载量**（excess）：

$$\mathrm{exc}_r(\theta)=\max\left(L_r-\theta,\ 0\right)$$

还没到上限的余量是它可以再吸收的**空闲量**（slack）：

$$\mathrm{slk}_r(\theta)=\max\left(\theta-L_r,\ 0\right)$$

前者是「必须送出去多少」，后者是「还能接多少」。$\theta$ 可行的条件就是：所有超载量都能被搬到别人的空闲量里，且不违反槽位预算与同 Rank 不重复的限制。

于是求解退化为在「理想的平均负载」与「当前最大 Rank 负载」之间**二分搜索最小可行的 $\theta$**，每个探针跑一次贪心的可行性判定。

### 可行性判定里的两个降序

判定过程用贪心：按超载量从大到小遍历过载的 Rank；对每个过载 Rank，按 Expert 总负载从大到小遍历它名下的主专家；把这个最热的 Expert 尽可能多的负载搬到**当前空闲量最大**的合法目标 Rank 上。

两个降序的作用与 `EPLB.md` 里装箱用降序的理由同源——**先处理大块，把误差留给小块**：

```text
过载 Rank 按超载量降序：先救最急的，避免最后剩一个大缺口无处安放
主专家按负载降序：      从最热的 Expert 上卸载，单次转移的削峰效果最大
目标按空闲量降序：      往最空的地方放，最不容易把目标 Rank 顶成新的过载
```

每次接受一次转移，同时做两件事：创建一个副本，并给这个副本记上它分到的配额。**所以放置方案在生成的那一刻就已经带着可用的路由容量了**，不需要事后再补一次路由决策。

最小配额约束在这里起作用：如果一次转移能搬的量低于这个下限，就不做这次转移。它过滤掉那些「为了凑一点均衡而新建一个副本」的交易——搬一份完整权重的代价是固定的，配额太小的副本不值得。**这是一个在关键路径上必须有的判断：均衡收益要能覆盖搬运开销。**

如果所有超载量都被排空了，说明这个 $\theta$ 可行，记下方案并继续往下探；否则往上探。

### 为什么这样是高效的

关键在于配额同时扮演了两个角色：

```text
它是均衡目标：      max_r Σ_e q_er 就是要压低的那个量
它是路由容量的承诺：一个副本存在，就意味着它已经被分配了具体的流量
```

因为有这个双重身份，每次探针在挑选副本的同时就把路由容量预留好了。这既避免了枚举副本集合（组合空间在大 EP 下极大），也避免了在 token 粒度上做规划（规模更大），同时从根上排除了无效副本。

## 七、重路由：分解，而不是再优化

配额定下来之后，重路由要做的事情性质就变了：**它不再触碰均衡目标，只是把已经解出来的聚合配额分解成「每个源 Rank 给每个物理实例发多少」。** 均衡质量在上一步已经锁定，这一步只要保持一致就不会变差。

正因为如此，这里可以免费地捞一个局部性收益。

```text
第一步：本地优先
  某个 Rank 自己产生的、发往 Expert e 的 token
  如果这个 Rank 上恰好就有 e 的一个实例，优先用本地的这份配额
  → 这些 token 根本不用出这张卡

第二步：剩余需求按比例分摊
  扣掉本地消费之后，剩下的需求分给其他实例的剩余配额
  按剩余容量比例分摊，并用确定性的取整规则收尾
  → 保证「每个源发出的总量」和「每个实例收到的总量」都精确对上
```

为什么局部性是免费的？因为**本地优先只改变了「谁来消费这份配额」，没有改变配额本身**。配额表不动，就意味着解出来的那个负载上限 $\theta$ 不受影响。于是跨卡流量减少了，而均衡质量一点没损失。这是整个设计里少见的没有代价的一步，其根源正是把配额提为决策变量之后带来的解耦。

最后还要落到 token 粒度：AllToAll 需要知道每一个 token 的目的地，而配额只是聚合的计数。做法是把每个逻辑专家的各个物理实例按顺序排好、算出配额的累加值，某个 token 就发给「累加配额第一次覆盖到它的序号」的那个实例。这样每个 token 的目的地就是一次本地的上界查找，与前面的优化过程完全解耦。

## 八、在 GPU 上求解

求解在关键路径上，就不能放到 CPU 上做。理由不只是 CPU 慢：一旦上了 CPU，就需要把负载矩阵传到 host、算完再传回 device，还要引入一次同步，这会打断整个设备端的执行流（对于用 graph capture 固化执行序列的框架，这种打断代价更大）。

但把它搬上 GPU 并不轻松，因为这个算法**不是一个数据并行的扫描**：

```text
二分搜索的每个探针都会改写状态：超载量、空闲量、槽位占用、每专家的副本集合
可行性判定内部有顺序依赖：后一次转移能搬多少，取决于前面已经接受的转移
```

这类「有状态、有顺序依赖」的组合搜索天生不适合 GPU 的执行模型。UltraEP 的应对是换一个并行维度：

```text
并行维度不取「数据」，而取「探针」
  → 不同 warp 同时评估不同的候选阈值 θ
  → 每个 warp 内部串行地跑自己那次可行性判定

规模压到单个 SM 上
  → 用一个协作线程块，把负载矩阵与放置状态暂存进共享内存
  → 状态读写都在片上，避免全局内存往返
  → warp 级归约用来快速找到「空闲量最大且合法」的目标 Rank
```

这样一来，原本是 CPU 侧组合搜索的问题，被压缩成了一个驻留在单个 SM 上的紧凑可行性判定，并且同一个 kernel 直接把槽位映射、配额、以及重路由所需的累加元数据一起产出。

值得注意的是这里的取舍：**只用一个 SM。** 求解只占一个 SM，剩下的算力还能跑别的东西，这在一个关键路径极紧的系统里是有意义的选择——求解快是必要的，但求解不应该把整块卡占住。

## 九、数据平面：瓶颈从带宽转向控制路径

到这里算法侧讲完了。但 UltraEP 有近一半的复杂度在数据平面，原因是：**求出方案只是一半，把权重按方案搬完才算真的做到。** 而这次搬运的形态与常规通信非常不同。

### 为什么现成的通信栈不好用

RSN 提供了很高的 scale-up 带宽（通常是 scale-out RDMA 网络的若干倍），看起来搬权重不该是问题。但均衡流量的形态是：

```text
常规 collective：       通信组固定、每对之间的量可预知、模式规则
                        通信栈可以为它做静态优化
均衡流量：              一张运行时才确定的稀疏传输图
                        谁发给谁、发多少，逐层、逐 microbatch 都在变
                        而且高度不对称（热点 Rank 发很多，其他几乎不发）
```

现成的通信库是为前者优化的，面对后者适配得很差。

### 非载荷开销被放大

更本质的观察是：在这种不规则传输上，**瓶颈已经不在链路带宽，而在控制路径上。**

```text
一次副本传输要做的事：
  查任务表：这份权重要发给哪些 Rank？        ← 控制
  切分任务：拆成多少个传输单元？             ← 控制
  数据暂存：从哪读、暂存到哪                  ← 控制
  动态寻址：目标 Rank 上的目标地址是多少？    ← 控制
  真正的数据搬运                              ← 载荷
```

当传输是规则且量大的时候，控制部分被摊薄到可以忽略。但这里的传输是碎片化的、地址是动态的、任务表每层都变，于是控制开销的占比急剧上升，链路带宽根本跑不满。

一个直觉上的应对是「多开并行度」，但这条路走不通：反向阶段的权重与梯度通信本来是要藏在计算下面的，盲目提高并行度会与被重叠的计算 kernel 争抢同一份 SM 资源，把重叠本身破坏掉。

**所以真正的目标不是峰值链路速率，而是在这种多变计划下的有效带宽。**

### 持久化 tile 流式传输

UltraEP 的核心手法是把「每个副本发起一次传输」改成「一个持久 kernel 不断从任务流里取活干」。

```text
准备阶段：
  把每个专家的权重（或梯度）切成固定大小的 tile
  把求解出来的方案编译成一串驻留在设备上的 tile 级传输任务

执行阶段：
  启动一个持久 kernel，它的线程块反复从任务流里取下一个 tile
  权重分发方向：源 tile 暂存进共享内存一次，然后写到所有远端副本
  梯度归约方向：把远端副本的梯度 tile 取回来累加进主专家的缓冲区
                累加完就地清零，供后面的层复用（对应第四节的跨层复用）
```

这个改写解决了两件事。

**第一，源数据只读一次。** 一份权重要发给多个副本，如果按副本逐个发起传输，同一份数据要被读多次。暂存进共享内存一次、再散发到所有目的地，把重复读消掉了。

**第二，控制开销被折进流水线。** 线程块内部对共享内存做双缓冲：在把第 $i$ 个 tile 写出去（或归约）的同时，就已经在查第 $i+1$ 个 tile 的任务、翻译它的地址、并启动它的加载。

```text
改写前：查任务 → 搬数据 → 查任务 → 搬数据 → …（控制串在关键路径上）
改写后：搬数据 ‖ 查下一个任务（控制被数据搬运掩盖）
```

于是「计划相关的任务查找、地址翻译、同步」不再是每次副本传输前的独立步骤，而是被藏进了 tile 的流水线里。这正是对前面那个诊断的正面回答：**既然瓶颈在控制路径，那就把控制路径隐藏在数据搬运之下。**

### 常驻线程块数作为「重叠感知」的旋钮

持久 kernel 有一个天然的资源旋钮：常驻线程块的数量。它决定了同时有多少个 tile 在飞。UltraEP 明确按**重叠窗口**来配置这个数字：

```text
前向的权重分发：在暴露的关键路径上
  → 没有可以重叠的计算，唯一目标就是尽快搬完
  → 多给线程块，压满在飞的 tile，把 scale-up 带宽吃满

反向的权重重新物化与梯度归约：藏在计算下面
  → 有明确的重叠窗口，目标是「在窗口内搬完且不干扰计算」
  → 显式限制 SM 占用与共享内存用量，给同时在跑的计算 kernel 留余量
```

这一点很值得单独记住：同一个传输机制，在关键路径上和在重叠窗口里，**最优资源配置是相反的**。前者要抢占，后者要克制。把它做成一个可配的旋钮，而不是写死一个值，是这类系统里的常见正确做法。

## 十、热点 fan-out 与 relay

即使每一次传输都足够高效，还有一个结构性的瓶颈：**热点专家的扇出。**

副本机制天然产生了一个动态的子组多播：一个热门主专家可能要把权重推给很多个目标 Rank。注意这个压力是**不对称的**，暴露在发送侧：

```text
接收侧：每个 Rank 最多接收「冗余槽位数」份权重 → 有天然上界
发送侧：一个 Rank 可能名下有多个热门主专家
        每个都要推给很多目标 → 无上界，可以非常大
```

而且这里有一个讽刺的耦合：越热门的 Expert 越需要多开副本，副本越多扇出越大，扇出越大搬运越慢，搬运越慢关键路径越长——**均衡的收益被均衡的开销抵消掉了。**

### 两级 relay

应对方式是不让源 Rank 独自承担全部扇出，而是建一个两级转发：源 Rank 先把权重发给少量**中继** Rank，每个中继再转发给分配给它的叶子 Rank。

问题是中继选多少个。这里有一个清晰的权衡：中继太少，第二级每个中继要转发的份数太多；中继太多，第一级源 Rank 的扇出又没降下来。两级的负担分别正比于「中继数」与「总数除以中继数」，要让两者相当，中继数应取总数的平方根：

$$\text{中继数}\ \approx\ \sqrt{|H_e|-1}$$

一句话说，**把一次很宽的扇出拆成两次都不太宽的扇出，最优的拆法是让两级同样宽，也就是取平方根。** 这样源 Rank 的关键扇出从线性降到了平方根量级。

### 两个实现上的判断

**为什么按 chunk 调度，而不是按整个专家。** 如果一个中继必须先完整收下一个专家的权重才开始转发，那第二级只能等第一级全部结束，两级实际上是串行的。改成以连续若干 tile 组成的 chunk 为单位调度后，中继收到第一个 chunk 就可以开始往下转，两级形成流水，且每条边仍然复用上一节的 tile 流式传输。

**为什么不用交换机的多播卸载。** 有些 RSN 支持把多播下沉到交换机做，这本来是最直接的方案。但它通常要求通信组和投递模式是预先确定的，而这里的组是稀疏的、易变的——逐层、逐 microbatch 都在变。**硬件多播的前提（组静态）与实时均衡的性质（组动态）直接冲突**，所以只能在软件侧构造转发树。

值得注意的是，relay 的本质是**用其他 Rank 的空闲发送能力，去补热点 Rank 发送能力的不足**。这与均衡本身是同一个思路，只不过均衡的对象从计算换成了发送带宽。

## 十一、代价与适用边界

UltraEP 的收益不是无条件的。它的前提相当具体。

**必须有 scale-up 域内的高带宽。** EP 组必须落在一个 RSN 的 scale-up 域内，跨机架的扩展交给 PP 与 DP。原因是每层都要搬权重，如果这些搬运要走带宽低一个量级的 scale-out 网络，关键路径上的开销会立刻吃掉全部收益。**换句话说，UltraEP 是被 RSN 这种硬件形态「解锁」出来的方案**——在只有普通节点间网络的年代，把权重搬运放上关键路径是不可想象的。

**求解与权重分发在关键路径上。** 这是与 EPLB 最根本的性质差异。EPLB 可以接受一个跑在 CPU 上、含串行循环的实现，因为它不在关键路径上；UltraEP 的每一个设计决策都被这条路径的长度约束着。

**不适用于 Decode。** Decode 是 memory-bound 的：每一步都要把大量权重和 KV cache 从显存读上来，而单 token 的计算量太小，盖不住这些访存。于是**计算侧的不均衡在很大程度上被访存延迟稀释掉了**，均衡的收益本来就不大。想提高计算强度就得增大 batch，但那与 Decode 的延迟目标冲突。所以实际值得均衡的是 Prefill 与训练。这一点与 `EPLB.md` 里「Decode 用全局策略」的讨论是不同层面的问题：那里讨论的是用哪种放置策略，这里讨论的是**要不要做实时均衡**。

**显存换来了时序 deadline。** 跨层复用 buffer 省下了大量显存，代价是每层都有一个硬性的物化 deadline。这个交换只在数据平面足够快的时候才成立。

**反向必须完全隐藏。** 副本引入的通信如果在反向暴露出来，就等于用一份新开销换另一份开销。这是一条硬约束而不是优化目标。

## 十二、与 EPLB 的对照

| | EPLB | UltraEP |
| --- | --- | --- |
| 负载来源 | 历史统计（预测值） | 当前 microbatch（精确值） |
| 时间粒度 | 周期性，若干 batch 一次 | 每 microbatch、每层 |
| 求解位置 | 关键路径之外（可在 CPU） | 关键路径之内（在 GPU，占单个 SM） |
| 主专家位置 | 可重排 | 不可变，只加副本 |
| 决策变量 | 副本数与放置，路由是下游 | 直接是每实例的配额，复制与路由都是推论 |
| 拓扑手段 | group 与节点对齐，换取跨节点局部性 | 重路由时本地优先消费本地配额 |
| 留在系统外 | 负载预测、权重迁移、副本选择 | 基本都拉进来了 |
| 硬件前提 | 无特殊要求 | scale-up 域内高带宽（RSN） |
| 适用阶段 | Prefill / Decode / 训练 | Prefill / 训练 |

两者不是替代关系，而是**同一个问题在不同硬件前提下的两个解**。EPLB 的设计前提是「均衡开销必须为零，所以只能离线」，于是它必须承受预测误差；UltraEP 的前提是「scale-up 带宽足够高，可以把开销放上关键路径」，于是它换来了零预测误差。哪个更好，取决于跨 Rank 搬权重到底有多贵。

还有一点值得记住：`background.md` 中提到的「路由侧 vs 放置侧」这个划分，UltraEP 仍然完全落在放置侧——它不改变 Router 的任何输出，因此**不影响模型语义**，副本梯度归约回主专家保证了训练时与无副本形态的数学等价性。实时化改变的是均衡的时机与粒度，不是它的性质。

## 小结

* UltraEP 的单一起点是「用精确负载实时均衡」，其余设计几乎都是这个起点的连锁推论；
* 历史统计的问题不只是精度打折：当方案对准了旧热点时，副本空转而新热点无副本，**可能比不做均衡更差**；大 EP 会放大这一点，因为每 Rank 只剩两三个主专家，Rank 负载几乎就是单专家负载；
* 精确负载本身是免费的（复用 Dispatch 已有的路由元数据交换），方案一致性也是免费的（相同输入加确定性算法，无需同步）；真正的代价是求解与权重分发进入了关键路径；
* 因此难点从「求得多好」变成「多快求出并搬完」，这是理解全文所有设计的钥匙；
* **只复制不重排**：大 EP 下重排的收益随 EP 度递减、代价不递减；固定主专家位置换来确定性的运行时，这在逐层重算的系统里是必需的；
* 冗余槽位不带优化器状态、buffer 跨层复用，把显存问题换成了**逐层的物化 deadline**——空间问题变时序问题；
* 目标函数里出现了 EPLB 没有的一项：权重分发代价随副本数增长，**均衡质量与均衡开销第一次进入同一个目标函数**；
* **核心洞察是用配额作为耦合变量**：不先定副本再补路由，而是直接解每实例的最终配额，复制与重路由都成为它的推论。这消掉了放置与路由之间的间隔，从根上排除了「拿不到流量的无效副本」；
* 求解方式是二分负载上限加贪心可行性判定，超载量与空闲量分别是「必须送出多少」与「还能接多少」；最小配额约束确保均衡收益能覆盖搬运开销；
* 配额定下后重路由只是分解，因此本地优先消费本地配额是**免费的局部性收益**——只改变谁消费配额，不改变配额本身；
* GPU 上求解的并行维度不是数据而是**探针**：不同 warp 评估不同阈值，单 SM 单块加共享内存暂存，只占一个 SM；
* 数据平面上，瓶颈从链路带宽转向**控制路径**（任务查找、切分、暂存、动态寻址）。对策是持久化 tile 流式传输：源数据只读一次，控制开销被双缓冲折进流水线而非暴露在每次传输之前；
* 常驻线程块数是一个重叠感知的旋钮：**同一机制在关键路径上要抢占、在重叠窗口里要克制**；
* 热点扇出的压力不对称地压在发送侧，两级 relay 把它从线性降到平方根量级；按 chunk 而非整专家调度才能让两级流水；硬件多播用不上，因为它要求通信组静态而这里的组逐层在变；
* 适用边界很具体：需要 scale-up 域内的高带宽（这是被 RSN 硬件解锁的方案）、面向 Prefill 与训练而非 memory-bound 的 Decode、反向副本通信必须完全隐藏；
* 它与 EPLB 是同一问题在不同硬件前提下的两个解，且同样落在放置侧，**不改变模型语义**。
