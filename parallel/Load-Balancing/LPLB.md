# LPLB：把均衡写成一个能实时解开的最优化问题

EPLB 用降序贪心装箱这类启发式来决定负载怎么分布，LPLB 想知道如果换成一个真正的最优化问题会怎样。

难点显然是时间。最优化问题一般解不快，而均衡决策必须在每个 batch 的关键路径上做完。LPLB 的解法是从两头往中间挤：一头是**通过约束副本的组织形式，把问题的规模压到与 batch 无关**；另一头是**放弃求最优解，只要一个够用的解，并为解不出来准备退路**。

在 `background.md` 的两条分水岭上，LPLB 的位置很特殊：它在当前实例侧取精确信号，但在决策变量上只做分流不做放置。副本数与副本位置那一层它完全外包给 EPLB，自己只解副本已经就位之后的最后一公里：这个 batch 的 token 该怎么在主副本之间分。

## 分工：静态定拓扑，实时定分流

**离线一级：EPLB 只用来重排。** 用历史负载统计跑一遍 EPLB，但关掉它的复制能力，只取排列结果；再在每个 Rank 内部按历史负载降序排一次，取最重的几个专家作为复制的候选。这一级处理的是持续性的不均衡——某些专家因为数据分布长期偏热。

**在线一级：LP 决定分流。** 每个 batch 用当前的精确路由统计负载，在已经存在的副本关系上解一个 LP，得出每个可分流专家的 token 该按什么比例分给主副本。这一级处理的是小 batch 随机性带来的逐 batch 波动。

分成两级的原因是两种不均衡的处理代价差了几个量级：持续性不均衡要改变权重的物理位置，只能低频做；逐 batch 波动只需要改变 token 的去向，权重一动不动，所以可以每步做。`EPLB.md` 的周期性重规划与 `UltraEP.md` 的逐层重解是这根轴上的两端，LPLB 的做法是在两端各放一件合适的事。

## 拓扑：把副本关系约束成图

副本关系原则上可以任意组织：一个专家复制到哪几个 Rank，各 Rank 复制几个专家，都没有天然限制。但那样得到的是一个一般的分配问题，规模和结构都不好控制。LPLB 主动加了两条约束：

- 每个 Rank 的冗余专家数量相同
- 某个 Rank 上的第 $i$ 个冗余专家，必须是另一个 Rank 上第 $i$ 个专家的副本

这两条合起来保证了一件事：**每份副本恰好被两个 Rank 共享**，一个是主专家的家，一个是副本的落点。于是副本关系不再是一个一般的多对多关系，而是一张图——Rank 是顶点，每一对「主专家 + 它的副本」是一条边。

**边是一条允许 token 流动的通道，边的容量就是这个专家在当前 batch 收到的 token 数。** 能在这条边上转移的 token 最多就这么多，因为可分配的只有这个专家自己的 token。这句话直接给出了后面 LP 的容量约束。

约束成图的收益是问题结构一下子清楚了：均衡变成「在一张固定的图上安排流量，让最高的顶点负载尽可能低」。而**图上有哪些边完全由拓扑决定，也就完全决定了 LP 的可行域**——没有边相连的两个 Rank 之间不可能转移任何负载。选拓扑就是在选「允许谁救谁」。

三种预置拓扑对应三种可行域：

- Cube：在 8 卡子组内构成一个带对角边的立方图，要求每卡至少两个专家。可行域覆盖节点内的任意两卡（对角边让距离更远的卡也能互救），且完全不牵动跨节点通信
- Hypercube：与 Cube 类似但去掉对角边，需要 16 卡，适合跨 16 卡的 EP
- Torus：每个专家的一个副本放在同节点的邻居卡上，另一个放到邻节点，构成环面图。可行域覆盖全局，代价是引入了跨节点流量，节点内的均衡效率不如 Cube

这是利用拓扑差异的一种特定方式：**不在求解时把带宽差异写进目标函数，而是在构造可行域时就把不想要的边排除掉。** 边越多可行域越大、解越优，但边跨越的距离越远、真正转移时的通信代价越高，这个取舍在求解之前就已经定死了。

## LP：最小化组内最大负载

**先看直觉。** 把每个 Rank 想成一个水位不同的水池，边是连接水池的管子，管子有粗细上限。要做的事是通过在管子里放水，让最高的水位尽可能低。

障碍在于「最高水位」不是一个线性函数，没法直接写进 LP 的目标。绕过去的办法是换一种说法：**先假设最高水位是某个未知数 $t$，要求每个池子的水位都不超过 $t$，然后最小化 $t$。** 这样目标函数变成了单个变量，而「不超过 $t$」是一组线性不等式。这是 minimax 问题转成 LP 的标准手法，也是理解整个建模的钥匙。

**再看形式。** 设组内有 $G$ 个 Rank，每个 Rank 上有 $D$ 个可分流的专家（即 $D$ 条边的一端）。变量分三类：

- 分流比例：每条边有两个变量 $\alpha_j^{\text{ori}}$ 与 $\alpha_j^{\text{dup}}$，表示这条边对应的专家的 token 有多少比例留在主专家、多少比例去副本
- 松弛量 $s_r \ge 0$：Rank $r$ 的负载与 $t$ 之间的差距
- 最大值 $t$

第一类约束定义每个 Rank 的负载并把它压在 $t$ 之下。Rank $r$ 的负载由两部分组成：与它相关的边按比例贡献的部分，以及它上面那些不参与分流的固定专家贡献的常数。加上松弛量后等于 $t$：

$$\sum_{j\,:\,\text{边 }j\text{ 与 } r \text{ 相关}} \alpha_j\, w_j \;+\; \mathrm{const}_r \;+\; s_r \;=\; t$$

$w_j$ 是这条边对应专家的 token 数，也就是前面说的边容量。松弛量非负，所以这条等式的效果就是「负载不超过 $t$」，同时它还把不等式变成了等式，方便求解器处理。

第二类约束要求每条边上的两个比例加起来是 1，因为这个专家的 token 必须全部有归属，不能丢也不能凭空多出来：

$$\alpha_j^{\text{ori}} + \alpha_j^{\text{dup}} = 1$$

目标就是那一个变量：

$$\min\ t$$

**这个 LP 的规模与 batch 无关。** 变量数和约束数只取决于组内 Rank 数与每卡的冗余专家数，跟 token 数、hidden size、序列长度全都没有关系。所以它是一个几十个变量的小问题，不会随着 batch 变大而变难。这一点是整套方案能放到关键路径上的前提，也是前面那两条拓扑约束真正换来的东西。

**代价是只均衡了 token 总数。** 每个 Rank 的负载在这里就是它收到的 token 数，而 grouped GEMM 的耗时对 token 数并不是线性的。耗时随 token 数单调增长没问题，但 LP 需要的是线性，所以这里用线性去近似了单调，均衡了 token 数不等于均衡了时间。

## 求解器：够用的解胜过最优的解

**为什么是内点法。** 单纯形法沿着可行域的顶点跳转，每一步要选主元、换基，控制流分叉多，迭代次数还取决于数据，最坏情况很难预估。内点法从可行域内部走，每一步的工作是固定的：构造一个加权的正规方程，解一次小的对称正定线性系统，然后沿着算出来的方向走一小步。形状固定、没有数据相关的分支，这正是 GPU 擅长的形状。LPLB 走的是仿射缩放型的内点法，整个求解装在单个 SM 上，用的是把线性代数塞进单个 block 的设备端库。

**为什么固定步数就停。** 关键路径上时间预算比解的质量更重要。内点法的性质是前几步就能把解拉进可行域内部的一个不错的位置，后面的迭代主要是在提高精度。而这里要的只是一组分流比例，比例差一点带来的均衡损失，远小于多跑几步迭代占掉的时间。所以求解器根本不检查收敛，跑固定步数就交卷。

**解不出来怎么办。** 跑完之后检查三件事：目标方向上还能下降多少（下降量仍然很大说明离解还远）、大 M 法引入的人工变量是否已经被压到接近零（不为零意味着约束没真正满足）、约束残差是否在容忍范围内。三者都通过才认为这个解可用；否则整个组退回均分——每个可分流专家的 token 在主副本之间对半分。均分不是最优，但它一定不会比完全不均衡更差，是一条安全的退路。全局还维护一个成功计数器，让上层能看到求解的成功率。

一般化的结论是：**在关键路径上放优化器，必须为「解不出来」准备一条确定性的退路。** 否则最坏情况的代价会吃掉平均收益，而且这种失败是数据相关的，测不出来也防不住。

## 落地：从比例到每个 token 的去向

LP 给出的是比例，而 AllToAll 需要的是每个 token 的确切目的地。

**基本做法。** 每个逻辑专家在当前 batch 的 token 总数是已知的，乘上 LP 给的比例就得到「应该留在主专家的期望数量」。每个 token 在自己目标专家内部拿一个序号，序号小于这个期望数量就去主专家，否则去副本。

**序号必须先打散。** 序号是各 SM 分段统计再累加出来的，所以它与 token 在序列里的位置强相关：序号靠前的 token 也就是靠前的那些 token。如果直接拿这个序号去比较，一个 SM 负责的连续 token 会整段落到同一侧——比例总数是对的，但每个 SM 内部的目的地极度集中，通信模式退化成一段一段的突发。做法是先把序号过一遍乘法取模的伪随机置换，再与期望数量比较。置换是双射，所以两侧的总数一分不差，只是落点被均匀铺开了。

**为什么不用真随机。** 这个映射必须是确定性的：凡是需要知道某个 token 去了哪里的地方，都要能独立算出同一个答案，不能依赖共享的随机状态。乘法取模置换同时满足确定性、双射和足够的打散效果，恰好是这里需要的东西。

## 代价与边界

- 依赖 EPLB 提供重排，依赖 DeepEP 提供低开销的负载同步——用 NVLink 与 NVSHMEM 直接做规约，而不是走 `torch.distributed` 的 all_reduce
- 求解在关键路径上，节点内是百微秒量级，跨节点更长；小 batch 下这个开销占比不可忽略
- 拓扑是静态的，副本数与位置在一个周期内不变，改拓扑要重新走离线一级
- 只均衡 token 总数，没有考虑 grouped GEMM 时间的非线性
- 极端全局不均衡下可能不如 EPLB。原因在拓扑约束本身：为了让每份副本恰好被两个 Rank 共享，LPLB 不会把同一个专家的多个副本聚在一起，而极端倾斜恰恰需要给那一个超热专家开多份副本。这是「静态拓扑加最优求解」输给「动态拓扑加启发式」的一个具体场景
