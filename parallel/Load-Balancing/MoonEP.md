# MoonEP：把不平衡度变成常量

MoonEP 是 Moonshot AI 的 EP 通信库，不是一个可以单独摘出来的均衡算法。它与 `EPLB.md`、`UltraEP.md` 处理同一个问题，但目标不同：后两者都在设法把 `background.md` 定义的不平衡度 $\rho$ 压向 1，MoonEP 让它恒等于 1。

支撑这一点的是三件互相咬合的事：

- 在线规划：用当前 microbatch 的精确路由，算出一份「哪个专家的哪些 token 落到哪个 Rank」的完整分配表
- 动态冗余专家：需要被分担的远端专家，权重在专家计算前预取到本地的固定槽位，而不是迁移主专家
- 静态形状与零拷贝：因为每个 Rank 收到的 token 数恒定，通信 buffer 固定，形状在编译期已知

之所以说互相咬合，是因为收益并不是三份独立的收益相加。恒定的 token 数才让形状静态化成为可能，静态形状才让「直接写到最终位置」成为可能：

```text
每 Rank 收到的 token 数恒定 ─┬─→ 激活形状恒定 ──→ 显存不再碎片化，不会 OOM
                             ├─→ 形状编译期已知 ──→ 不需要每层与 host 同步
                             └─→ 目的地偏移可预先算出 ──→ 零拷贝
```

EPLB 与 UltraEP 优化的都只是执行时间里的 $\max_r$ 那一项。MoonEP 在压掉这一项的同时，把动态形状引出的一整串麻烦一并消掉了。

## 从压低峰值到消灭峰值

设每个 Rank 输入 $S$ 个 token，路由 top-$k$ 为 $K$，EP 规模为 $R$。MoonEP 要求的是：

$$L_r = S \times K \quad (\forall r)$$

这不是一个乐观的目标，而是一个恰好可满足的守恒条件。每个源 Rank 都精确地产生 $S \times K$ 个 routed token，全局总量恒为 $R \times S \times K$，均分到 $R$ 个 Rank 正好是 $S \times K$。也就是说容量上限与平均负载重合，只要分配得当就一定能填满且不溢出，不存在「达不到」的情况。

与 `UltraEP.md` 的求解目标对比可以看出这个设定的性质：UltraEP 二分搜索最小可行的负载上限 $\theta$，$\theta$ 是解出来的、随路由分布浮动；MoonEP 直接把上限钉在 $S \times K$，不再是待求量。代价转移到了别处——既然容量不能松，专家的 token 就必须无条件地被切开送走，于是「被切走的那部分需要的权重从哪来」变成了必须解决的问题。

## 分配表怎么算出来

分配表 $\mathrm{alloc}[e][d]$ 表示专家 $e$ 的 token 里有多少落在 Rank $d$。它由两级贪心求出，两级解决的是不同的问题：第一级只管 Rank 之间收发多少，第二级才管这些额度由哪些专家出。

**第一级：定 Rank 之间的收发额度。** 把一个 Rank 名下的 $E/R$ 个专家看作一个 home group，先算出每个 group 收到的 token 总数，减去容量得到盈亏：

$$\mathrm{balance}_h = \mathrm{group\_tokens}_h - S \times K$$

由前面的守恒关系，$\sum_h \mathrm{balance}_h = 0$，盈余与亏空必然配对存在。于是反复取最盈余的 home group 与最亏空的目标 Rank，一次就把这个目标 Rank 填满：搬运量取目标 Rank 的亏空量，搬完它的盈亏归零、退出候选。这个「一次填满一个接收方」的选择让每轮至少消掉一个 Rank，循环次数因此有界，不需要迭代到收敛。

**第二级：把额度拆到具体专家。** 额度只说了 home group $h$ 要向 Rank $d$ 送出多少 token，没说这些 token 属于哪些专家。做法是每轮取当前最大的剩余额度与本地剩余 token 最多的专家，搬走两者的较小值，更新双方后继续。优先搬最热的专家不是为了均衡质量（额度已经锁定了均衡质量），而是为了让被搬动的专家种类数尽量少：每一种被搬动的专家都要在接收方占一个预取槽位，种类数直接决定后面要预取几份权重。

**从分配表到每个 token 的目的地。** 与 `UltraEP.md` 的区间查找同构，区别是这里的编号是全局的。每个 routed token 在它的目标专家内部有一个全局序号，等于本 Rank 内的局部序号加上前面所有源 Rank 在该专家上的 token 数前缀和；对 $\mathrm{alloc}[e][\cdot]$ 沿 Rank 维求前缀和得到一串边界，序号落在哪个区间就送往对应的 Rank。因为各 Rank 分到的份额之和恰好等于该专家的 token 总数，每个 token 必然落在唯一一个区间里。最终目的地被编码成一个整数：高位是 Rank 号，低位是该 Rank 内的偏移。

**求解本身在 GPU 上、不落回 host。** MoonEP 由 rank 0 集中求解，结果通过对称内存分发给所有 Rank，整个过程在一次 cooperative kernel 内完成。这与 UltraEP 的「各 Rank 拿相同输入独立算出相同结果」是两种消除同步的办法：集中求解需要一次结果分发，但只算一遍。

## 权重：预取到固定槽位，而不是迁移

被切走的 token 需要在接收方拿到对应专家的权重。MoonEP 的做法不是把主专家搬过去，而是在每个 Rank 上预留固定槽位，把需要的远端专家复制进来。

**布局的连续性是硬约束。** 每层每个投影（gate/up/down）持有一段连续的 $[E+B]$ 行权重，在所有 Rank 上布局完全一致。前 $E$ 行是全部 Rank 的本地专家，每个 Rank 占 $E/R$ 行——这些行物理上就是各 home Rank 自己的参数显存，通过对称内存映射到每张卡上。后 $B$ 行是本地的预取槽位。连续是硬要求，因为 group GEMM 完全靠行号寻址。

**分配表通过 `cu_seqlens` 直接变成 GEMM 的输入。** 规划器产出的 `cu_seqlens` 给出每一行在 token buffer 里的结束偏移，被预取的远端专家，其 token 段就指向 $[E, E+B)$ 里的某个槽位。于是一次 group GEMM 同时算完本地专家和借来的远端专家，计算侧不需要任何分支，甚至不知道哪些专家是借来的。

**$B$ 的取值在训练与推理下不同。** 训练必须取 $B = E/R$：规划器保证每个 Rank 最多从一个远端 home group 借专家，借来的专家数因此不超过 $E/R$，取这个值就能保证 GEMM 摸到的每个专家都在本地。推理只需要前向，$B$ 可以更小（3 到 4）。此时若某个 Rank 需要的远端专家数超过 $B$，溢出的那部分权重让 GEMM 通过对称内存直接读远端：慢一些，但结果正确。

这个溢出处理改变了 $B$ 这个参数的性质。如果溢出会导致错误，$B$ 就是一个必须按最坏情况配置的容量约束；而让溢出退化为远程读之后，$B$ 变成了一个纯性能旋钮，可以按常见情况调小。

**显存代价是 $B$ 份权重的总量，不是每层 $B$ 份。** 预取槽位的物理显存来自一个进程级的全局 pool，所有层共用一份。这与 `UltraEP.md` 里的跨层复用是同一个思路，付出的代价也一样：每一层都必须在自己的计算开始前把权重物化到位，物化因此落在关键路径上，成为一个逐层的 deadline。

## 反向：借来的梯度必须还回去

副本上算出的梯度是临时的，必须归约回 home Rank，否则训练结果与无副本的形态不等价。

**梯度需要一套独立的 buffer。** 梯度缓冲镜像权重的布局，同样是连续的 $[E+B]$ 行，但后 $B$ 行不能落在参数梯度上。原因是框架自己的梯度归约会扫描参数梯度，如果预取槽位的梯度混在里面就会被重复累加。所以这 $B$ 行背后是一块独立的 reduce buffer，对框架不可见，物理显存同样来自跨层共享的 pool。

**归约靠远程读完成。** 每个 Rank 把所有 $R$ 个 Rank 的 reduce buffer 映射成一个统一视图，各自去读那些持有自己专家梯度的槽位，累加进本地参数梯度，然后清零自己已被消费的槽位，为下一个 microbatch 让位。

**清零由各 Rank 在本地做，而不是顺便远程写。** 直觉上，读阶段占的是读方向的带宽，写方向空闲，可以在远程读的同时顺手把远端槽位写零，省掉一个阶段。但同一块 GPU 上同时进行的远程读与远程写共享同一份 NVLink 预算，每个方向大约各得一半，借用写方向会把读阶段拉长，拉长的时间超过本地清零本身的开销。一般化的结论是：**NVLink 的两个方向不是两条独立的管道，反方向不能当成免费资源来用。**

## 零拷贝：完美均衡是它的前提

**先看恒定的 token 数带来了什么。** 每个 Rank 每层收到的 token 数恒为 $S \times K$，于是通信 buffer 只需要一份固定大小；后续算子的形状不再依赖运行时的实际计数，不需要每层把计数同步回 host 再决定形状；每一层每一步的激活形状都相同，显存分配模式稳定，不会因为形状反复变化而碎片化。常规实现里高不均衡下的 OOM 正是碎片化的结果，与显存总量够不够无关。

**再看零拷贝本身。** 常规实现里，dispatch 收到 token 后要 permute 成按专家分组的顺序，专家算完再 unpermute 回 token 顺序，最后从通信 buffer 拷一份到用户 buffer。MoonEP 让源 Rank 直接把 token 写到它在远端专家分组布局里的最终位置——这个偏移在规划阶段就算出来了，正是分配表的产物。于是两次 permute 与那次收尾拷贝一起消失，交给计算的直接是通信 buffer 的视图。

代价是这些视图的生命周期受通信节奏约束：下一次通信会覆盖同一块 buffer，所以视图不能跨通信调用持有。需要 autograd 保存激活的场景必须退回到拷贝模式。

**同一 token 的多个 topk 落到同一个 Rank 时只传一份。** 一个 token 的 $K$ 个目标专家可能有几个在同一个 Rank 上，payload 完全相同。做法是在每个目的 Rank 内只保留第一次出现的位置作为代表，其余位置的偏移编码为 $-x-1$：取负保证重复条目一定为负、可以直接判别，而减一是为了让 $0$ 这个合法偏移也落到负数区间。原值必须可恢复，因为每个 token-topk 条目有自己的路由权重，权重要逐条送对。真正的行复制在目的地本地展开，不占跨卡带宽。

## 代价与边界

- 整个设计建立在 NVLink 域内的对称内存之上：远端权重可以直接按地址读是前提，跨域场景不适用
- 关键路径上多了规划与预取两个 kernel
- 训练下 $B = E/R$ 是硬要求，显存下限由此确定
- 权重必须按 $[E+B]$ 连续布局，对框架的参数管理有侵入性
- 零拷贝下 buffer 视图的生命周期约束会传染到上层，限制了 autograd 的用法
- 定性效果上，迭代时间不随 Router 不均衡程度变差，也不会因激活形状变化而 OOM
