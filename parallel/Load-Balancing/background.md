# EP 负载均衡：问题与目标

## MoE 与 Expert Parallelism

### MoE 的基本结构

MoE（Mixture of Experts）把 Transformer 中的 FFN 替换为 $E$ 个并列的 Expert，每个 Expert 是一个独立的 MLP。一个 Router 为每个 token 打分，只选出 Top-$k$ 个 Expert 参与计算：

```text
token → Router → 打分 → 选出 Top-k 个 Expert
                          │
                          ▼
                    只有这 k 个 Expert 参与计算
                    其余 E - k 个不激活
```

它的立足点是**参数量与激活量解耦**：总参数量随 $E$ 增长，但每个 token 的计算量只随 $k$ 增长。典型配置下 $E=256$、$k=8$，参数规模可以放大几十倍而单 token 计算量几乎不变。

$E$ 个 Expert 的权重无法放进单卡，于是把它们分到不同 Rank 上，这就是 Expert Parallelism。

token 在自己所在的 Rank 上，但它需要的 Expert 可能在别的 Rank 上。**必须把 token 移动到 Expert 所在的位置。**

### Dispatch 与 Combine

于是一层 MoE 需要两次 AllToAll 类通信：

```text
Token-Owned 布局（每 Rank 持有自己的 token）
        │
        ▼
Router / Top-k，得到每个 token 的目标 Expert
        │
        ▼
Dispatch：把 token 送到目标 Expert 所在的 Rank
        │
        ▼
Expert-Owned 布局，本地执行 Grouped GEMM
        │
        ▼
Combine：把 Expert 输出送回 token 原来的 Rank
        │
        ▼
Token-Owned 布局，按 Router 权重加权合并
```

这两次通信是 **AllToAllV**（不等长）。

### 符号约定

| 符号 | 含义 |
| --- | --- |
| $E$ | 逻辑 Expert 数量 |
| $k$ | 每个 token 选择的 Expert 数（Top-$k$） |
| $p$ | Rank / GPU 数量 |
| $T$ | 一次前向中参与该 MoE 层的全局 token 数 |
| $w_e$ | Expert $e$ 的负载，即它收到的 Routed Token 数 |
| $L_r$ | Rank $r$ 的负载 |
| $\bar L$ | 平均 Rank 负载 |
| $\rho$ | 不平衡度 |
| $c_e$ | Expert $e$ 的副本数 |
| $C_r$ | Rank $r$ 的计算工作量 |
| $M_r$ | Rank $r$ 的通信工作量 |
| $F$ | 单卡算力 |
| $BW$ | 有效带宽 |

每个 token 会为它选中的每个 Expert 生成一个 Routed Token Instance，因此全局的 Routed Token 总数为 $kT$，即：

$$\sum_{e=0}^{E-1}w_e=kT$$

### 负载是数据相关的

TP / DP：负载由「切分方式」决定

- 切法在部署时就定好了，每个 Rank 的工作量天然相等
- 不存在负载均衡问题

EP：负载由「Router 的输出」决定

- Router 是一个学出来的、依赖输入内容的函数
- 哪个 Expert 热门，取决于当前这批 token 是什么：**数据相关**

于是 $w_e$ 的分布天然是不均衡的。

## 目标

### 从工作量到时间

记 Expert $e$ 的负载为 $w_e$，Rank $r$ 上放置的 Expert 集合为 $P_r$，则该 Rank 的负载为：

$$L_r=\sum_{e\in P_r}w_e$$

这个 $L_r$ 同时决定了两件事：

- 计算工作量 C_r：本地 Grouped GEMM 要处理的 token 数
- 通信工作量 M_r：Dispatch 要接收、Combine 要发出的数据量

两者都随 $L_r$ 单调增长。设算力为 $F$、有效带宽为 $BW$，那么 Rank $r$ 的计算耗时约为 $C_r/F$，通信耗时约为 $M_r/BW$。

### 执行时间分析

MoE layer 的总执行时间的上下界是：

$$\max_r\max\!\left(\frac{C_r}{F},\frac{M_r}{BW}\right)\ \le\ T_{\text{MoE}}\ \le\ \max_r\left(\frac{C_r}{F}+\frac{M_r}{BW}\right)$$

两端的含义是：

- 右端（上界）：完全串行，每个 Rank 先算完再通信
- 左端（下界）：完美重叠，每个 Rank 的计算与通信完全叠在一起，耗时由其中较慢的那一侧决定
- 实际的 $T$ 落在两者之间，取决于重叠做得多好

注意 $\max_r$ 在**上界和下界中都存在**。这一点是全文的起点：

- 重叠（通算融合）优化的是「单个 Rank 内部的资源闲置」
  - 改变的是括号里那两项如何组合（相加 → 取最大）
  - 把 $T$ 从上界推向下界
- 负载均衡优化的是「Rank 之间的工作量差异」
  - 改变的是外层的 $\max_r$
  - 把下界本身往下压

两者作用在不同位置，互不替代。由此得到一个推论：

**重叠做得越好，负载不均衡就越是唯一剩下的瓶颈。** 因为当 $T$ 已经接近下界时，唯一还能改进的就只有 $\max_r$ 这一项了。这也解释了为什么在通信优化做得越充分的系统里，负载均衡反而越重要。

### 不平衡度

理想情况下每个 Rank 的负载都等于平均值：

$$\bar L=\frac{1}{p}\sum_{e=0}^{E-1}w_e=\frac{kT}{p}$$

定义不平衡度：**负载极值与平均值的比值**。

$$\rho=\frac{\max_rL_r}{\bar L}\ \ge 1$$

$\rho=2$ 意味着最忙的 Rank 承担了两倍平均工作量，而由于所有 Rank 都要等它，全局有一半的 Expert 计算能力被浪费在等待上。负载均衡的目标就是把 $\rho$ 压到接近 1。

### 一次均衡治两个症状

值得注意的是，$w_e$ 同时是两件事：

- $w_e$ 是 Grouped GEMM 的 token 数 → 决定 $C_r$（计算）
- $w_e$ 是 Dispatch 的 receive count → 决定 $M_r$（通信）

因为它们由同一个量驱动，所以一次负载均衡同时缓解计算长尾与通信热点，不需要两套机制。这也意味着无论系统当前是 compute-bound 还是 bandwidth-bound，均衡都有收益。

## 不均衡会反过来削弱通算融合的收益

上一节说明了重叠无法消除 $\max_r$。这一节再往前一步：**不均衡还会反过来削弱重叠本身。**

### 一、重叠的前提是配比稳定

重叠之所以有效，前提是同一个 Rank 上计算与通信的比例大致固定，这样两条流水线才能互相填满对方的空隙。负载倾斜直接破坏这个前提：

- 重负载 Rank：token 多 → 计算溢出，通信侧相对空闲
- 轻负载 Rank：token 少 → 计算很快结束，反而在等通信
- 同一份重叠策略（chunk 大小、流水深度、通信占用的 SM 数）在不同 Rank 上的最优取值不同，但通常只能配一套
  - 倾斜越大，这套配置离各 Rank 的最优点越远

也就是说，负载倾斜不只贡献了一个 $\max_r$，它还让每个 Rank 内部的重叠效率一起下降。

### 二、Collective 是重叠跨不过的硬同步点

Dispatch 与 Combine 要求进程组内所有 Rank 共同参与，完成时间由最慢者决定：

- 重叠能隐藏：单个 Rank 内部「算完等通信」的空隙
- 重叠不能隐藏：所有 Rank 在 Collective 上互相等待

即使某个 Rank 把自己内部的重叠做到了完美，它到达 Dispatch 的时刻仍取决于自己的计算量；而其他 Rank 必须等它。**这个等待发生在 Rank 之间，不在任何单个 Rank 的时间轴内部，因此任何单 Rank 视角的优化都碰不到它。**

### 三、融合让不均衡传导得更快

通算融合把通信写进计算 Kernel，让通信与计算共享 SM、共享寄存器与共享内存（参见 `../../cuda/comm-for-fusion.md`）。这带来一个副作用：

- 非融合形态
  - 通信是独立算子，数据先落 Buffer
  - 某个 Rank 计算慢一点，其影响可以部分被 Buffer 吸收
- 融合形态
  - 某个 tile 算完才发出去，计算与通信在时间上被绑定
  - 某 Rank 计算变慢 → 它发出数据的时刻直接推迟 → 依赖它的所有 Rank 一起被推迟
  - 依赖链更紧，抖动传播更快

融合提高了平均效率，但降低了对不均衡的容忍度。

**结论：越是精心做过重叠与融合的系统，越依赖负载均衡。** 这两类优化必须配套推进，单独做其中一个会遇到收益递减。

## 纯重排的下界：为什么必须有冗余

明确了目标之后，先看一个与算法无关的结论：它决定了任何解法的形态。

最朴素的想法是重新安排 Expert 的放置：把热门 Expert 打散到不同 Rank。这个思路有一个硬性上限。

如果只允许**重排**（permutation），即每个 Expert 恰好放在一个 Rank 上，那么无论怎么排：

$$\max_rL_r\ \ge\ \max_e w_e$$

理由很直接：最热的那个 Expert 总要落在某个 Rank 上，它一个人就贡献了 $\max_e w_e$，而该 Rank 的负载不可能更小。

代入 $\rho$ 的定义得到一个与算法无关的下界：

$$\rho\ \ge\ \frac{\max_e w_e}{\bar L}=\frac{p\max_e w_e}{\sum_e w_e}$$

这个式子说明：**只要存在一个 Expert 的负载超过了平均 Rank 负载 $\bar L$，任何 placement 算法都无法达到均衡。** 而 EP 度越大，$\bar L=kT/p$ 越小，这个条件越容易被满足。在 $E=256$、EP 度较大的部署下，热门 Expert 的负载超过 $\bar L$ 是常态而非例外。

所以必须引入**冗余专家（Redundant Experts）**：允许同一个 Expert 在多个 Rank 上各存一份权重。若 Expert $e$ 有 $c_e$ 个副本，且它的 token 能在副本之间分摊，则每个副本承担：

$$\frac{w_e}{c_e}$$

新的下界变成 $\max_e w_e/c_e$，可以通过分配副本数任意压低。

**这是理解整个问题的第一个要点：冗余不是锦上添花的优化，而是突破上述下界的唯一手段。** 由此问题分裂成两个子问题：

- Replication（复制）：决定每个 Expert 开几个副本 → 削峰
- Placement（放置）：决定每个副本放在哪个 GPU → 填谷

两者缺一不可吗？「必须有冗余」是硬结论：只做放置一定受制于 $\max_e w_e$。但「复制之后必须重新安排所有 Expert 的位置」并不是必然的——当 EP 度很大、每个 Rank 只持有两三个主专家时，重排能改变的局面很小，而它带来的状态迁移与布局不确定性并不因此减少。此时一种可行的取舍是固定主专家的位置、只用副本给瓶颈扩容（见 `UltraEP.md`）。

**所以准确的说法是：冗余是必需的，重排是可选的。** 但无论是否重排，都要回答「副本放在哪」——哪怕答案是「放在预先规划好的固定槽位里」。

## 手段谱系

上一节的结论限定了「放置侧」手段的形态。但放置侧并不是唯一的选择——降低 $\rho$ 有两条完全不同的路径，区别在于**动不动路由结果**。

- 路由侧干预：改变 $w_e$ 的分布本身
  - 训练时：auxiliary-loss-free 均衡
    - 在 gating 中引入可学习的 bias，调整 Expert 被选中的倾向
    - 让负载分布天然平坦
  - 训练时：辅助损失（auxiliary loss）
    - 在损失函数中加入均衡项
  - 推理时：容量限制与 drop / 改路由
    - 超过容量的 token 被丢弃或改投其他 Expert
  - 共同点
    - 改变了模型的选择行为，存在质量风险
    - 推理场景通常不能随意丢 token，手段受限
- 放置侧调整：改变负载到硬件的映射
  - 复制：热门 Expert 多存几份
  - 放置：决定每份放在哪里
  - 共同点
    - 完全不动 Router 的输出
    - 模型的计算结果与不做均衡时一致
    - 代价是额外显存与方案切换开销

两条路径正交且互补：

- 路由侧降低 $w_e$ 分布本身的方差
- 放置侧处理残余的不均衡

放置侧的独特价值在于它**不触碰模型语义**。可以随时开关、随时调参，不需要重新评估模型质量。这也是为什么即使训练时已经做了均衡，部署时仍然需要放置侧手段——训练时的均衡是针对训练数据分布的，无法保证线上任意流量下都成立。

## 一个放置方案必须回答的问题

综合前面的分析，任何放置侧的负载均衡方案都必须回答五个问题。它们构成了评价与理解具体算法的框架。

- 一、副本数怎么分配？
  - 总槽位有限，给谁多分一个副本？
  - 目标是最小化「每副本负载」的最大值
- 二、副本放在哪里？
  - 在「每 GPU 容纳的专家数」这类硬约束下，如何把带权的物理专家分配到各 GPU
- 三、拓扑差异如何利用？
  - 跨节点带宽显著低于节点内带宽
  - group-limited routing 提供了对齐机会，但会带来额外约束
  - 要不要吃这个收益？代价是什么？
- 四、负载用什么？
  - 路线一：用历史统计做预测
    - 方案可以离线慢慢求解，不占关键路径
    - 但预测总会滞后于真实分布的漂移
  - 路线二：用当前 microbatch 的精确负载
    - Router 出分之后负载就已经确定，不存在预测误差
    - 但求解与生效必须挤进关键路径上极短的窗口
- 五、方案怎么生效？
  - 新方案要求权重在 GPU 间实际搬动
  - 何时切换？切换期间如何保证一致性？
  - 搬运开销算在关键路径上还是路径之外？

前三个是**算法问题**，有明确的数学目标。后两个是**系统问题**，而它们的答案会反过来决定前三个问题在什么约束下求解：

- 选历史预测
  - 算法有充足预算，可以精细求解
  - 但要承受预测误差，方案可能对准了过时的热点
- 选实时精确
  - 没有预测误差
  - 但算法必须极快，且搬运开销直接计入端到端时间

两条路线分别对应 `EPLB.md` 与 `UltraEP.md`。
