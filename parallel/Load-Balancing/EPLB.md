# EPLB

EPLB（Expert Parallelism Load Balancer）是 DeepSeek 开源的 EP 负载均衡算法。它根据每个 Expert 的负载估计，计算出一份 Expert 复制与放置方案，使各 GPU 的负载尽量均衡。

本文承接 `EP.md` 中「Capacity、Replication 与 Placement」一节，符号沿用该文：$E$ 个 Experts，$p$ 个 Rank，Top-$k$ 路由，全局 $T$ 个 token。参考实现见同目录 `eplb.py`。

---

## 它要解决的那个数

`EP.md` 给出了一组 MoE Layer 的时间：

$$
\begin{aligned}
T_{\text{MoE}}\approx{}&\max_rT_{\text{route},r}+\max_rT_{\text{permute},r}
+T_{\text{dispatch}}^{\text{collective}}\\
&+\max_rT_{\text{expert},r}
+T_{\text{combine}}^{\text{collective}}
+\max_rT_{\text{unpermute},r}.
\end{aligned}
$$

每一项都带 $\max_r$。Router 是数据相关的，热门 Expert 收到的 token 数可以是冷门 Expert 的几十倍，于是这些 $\max_r$ 与平均值相差很远。

记 Expert $e$ 的负载（收到的 Routed Token 数）为 $w_e$，Rank $r$ 上放置的 Expert 集合为 $P_r$，则该 Rank 的负载为：

$$L_r=\sum_{e\in P_r}w_e$$

理想情况下每个 Rank 都应该等于平均负载：

$$\bar L=\frac{1}{p}\sum_{e=0}^{E-1}w_e=\frac{kT}{p}$$

定义不平衡度：

$$\rho=\frac{\max_rL_r}{\bar L}\ \ge 1$$

$\rho=2$ 意味着一半的 Expert 计算能力和一半的等待时间被浪费。EPLB 的目标就是把 $\rho$ 压到接近 1。

值得注意的是，$w_e$ 同时是两件事：

```text
w_e 是 Grouped GEMM 的 token 数     → 决定 max_r T_expert（计算）
w_e 是 Dispatch 的 receive count   → 决定最大接收量与热点链路（通信）
```

因为它们是同一个量，所以一次负载均衡同时缓解计算长尾与通信热点，不需要两套机制。

---

## 关键洞察：单纯换位置是不够的

最朴素的想法是重新安排 Expert 的放置：把热门 Expert 打散到不同 Rank。这个思路有一个硬性上限。

如果只允许**重排**（permutation），即每个 Expert 恰好放在一个 Rank 上，那么无论怎么排：

$$\max_rL_r\ \ge\ \max_e w_e$$

理由很直接：最热的那个 Expert 总要落在某个 Rank 上，它一个人就贡献了 $\max_e w_e$，而该 Rank 的负载不可能更小。

代入 $\rho$ 的定义得到一个与算法无关的下界：

$$\rho\ \ge\ \frac{\max_e w_e}{\bar L}=\frac{p\max_e w_e}{\sum_e w_e}$$

这个式子说明：**只要存在一个 Expert 的负载超过了平均 Rank 负载 $\bar L$，任何 placement 算法都无法达到均衡。** 而 EP 度越大，$\bar L=kT/p$ 越小，这个条件越容易被满足。在 $E=256$、EP 度较大的部署下，热门 Expert 的负载超过 $\bar L$ 是常态而非例外。

所以必须引入**冗余专家（Redundant Experts）**：允许同一个 Expert 在多个 Rank 上各存一份权重。若 Expert $e$ 有 $c_e$ 个副本，且它的 token 能在副本之间分摊，则每个副本承担：

$$\frac{w_e}{c_e}$$

新的下界变成 $\max_e w_e/c_e$，可以通过分配副本数任意压低。

**这是理解 EPLB 的第一个要点：冗余不是锦上添花的优化，而是突破上述下界的唯一手段。** 由此问题分裂成两个子问题：

```text
Replication（复制）：决定每个 Expert 开几个副本  →  削峰
Placement（放置）：  决定每个副本放在哪个 GPU    →  填谷
```

两者缺一不可。只做放置受制于 $\max_e w_e$；只做复制而随意放置，仍可能把多个重副本堆在同一个 GPU 上。

## 逻辑专家与物理专家

引入副本后必须区分两套编号，这是整套机制的骨架。

```text
Logical Expert（逻辑专家）
  模型定义中的 Expert，数量固定为 E
  Router 输出的是逻辑编号，与部署方式无关

Physical Expert（物理专家）
  实际驻留在某个 GPU 上的一份 Expert 权重
  数量为 P ≥ E，多出的 P - E 份就是冗余副本
```

放置方案由三组关系描述：

```text
物理 → 逻辑：每个物理槽位放的是哪个逻辑专家
逻辑 → 物理：每个逻辑专家有哪些物理副本可选
副本计数：   每个逻辑专家的副本数 c_e
```

### 硬约束与优化目标处在不同层次

$P$ 必须能被 GPU 数整除，即**每个 GPU 持有的物理专家数量完全相同**。于是问题的两个方面性质不同：

```text
硬约束：每 GPU 的物理专家「个数」必须相等
        → 权重显存整齐、Grouped GEMM 形状规整、无需处理不规则布局

优化目标：每 GPU 的「负载」尽量相等
        → 软目标，允许有残余误差
```

个数是硬的，负载是软的。EPLB 是在个数完全均等的前提下去优化负载均等，这是一个带基数约束的划分问题。这个约束显著限制了解空间，后面会看到它带来的连带影响。

### 逐层独立

负载统计的组织方式是「每层一组 $w_e$」，**每个 MoE 层独立求解、独立放置**。

理由是不同层的热点分布不同：某个逻辑编号的 Expert 在第 3 层是热门的，在第 20 层可能是冷门的。若所有层共用一套放置方案，就只能按各层的平均情况妥协，浪费大量优化空间。代价是路由表变成按层组织的，元数据量乘以层数。

### 职责边界：容量分布，不是路由决策

「逻辑 → 物理」给出的是一个**候选副本列表**，而不是指定某个副本。运行时把某个 token 具体发给哪一个副本，不属于 EPLB 的职责。

换句话说：**EPLB 定义的是容量在硬件上的分布，不是瞬时的路由决策。** 这个分工在后面讨论「均摊假设」时会变得重要。

## 分层算法的三步

DeepSeek-V3 使用 group-limited routing：Expert 被划分为若干 group，每个 token 只能路由到有限数量的节点。这个性质提供了一个额外的优化机会——**如果同一个 group 的 Expert 都放在同一个节点上，跨节点流量就被路由规则本身限制住了。**

分层策略据此按「节点 → 副本 → GPU」三步求解：

```text
Step 1  把 Expert Group 装箱到节点
        单位：group（保持 group 完整，这是分层策略的全部意义所在）
        目标：各节点总负载均衡
        决定：跨节点流量

Step 2  在每个节点内部构造冗余副本
        约束：一个逻辑专家的所有副本都留在同一节点内
        目标：最小化该节点内所有副本的最大负载
        决定：负载峰值能被削到多低

Step 3  把节点内的物理专家装箱到该节点的各个 GPU
        单位：物理专家，权重为 w_e / c_e
        目标：各 GPU 负载均衡
        决定：节点内 GPU 之间的均衡
```

三步分别对应拓扑、容量、放置三个层次，职责不重叠。

### 唯一真正的取舍

Step 2 为什么要把副本限制在节点内？因为 Step 1 已经把 group 绑定到了节点上。如果副本可以跨节点，那么某个 group 的 Expert 就会同时出现在多个节点上，token 的目标节点数增加，Step 1 建立的局部性被抵消。

于是分层策略的代价很清楚：

```text
放弃：副本放置的自由度（副本只能在本节点内摆放）
换取：跨节点流量受 group 局部性约束
```

这是整个分层策略里唯一实质性的取舍。它成立的前提是跨节点带宽显著低于节点内带宽——如果两者接近，这个取舍就不划算。

## 两个子算法的性质

三步里其实只用了两种子算法，且它们的算法性质**根本不同**，这一点值得单独说清。

### 装箱：降序贪心，启发式

Step 1 与 Step 3 是同一个子问题：把 $n$ 个带权物体装进 $m$ 个箱子，**每箱恰好 $n/m$ 个**，使各箱总重尽量均衡。

做法是按权重降序遍历，每次把物体放进「当前最轻且尚未装满」的箱子。

两个细节决定了它的性质：

* **降序是必要的。** 先放大物体、用小物体做微调，误差被限制在小物体的量级；若升序或随机，最后剩下的大物体无处安放，误差会被放大到大物体的量级。这也是经典 LPT（Longest Processing Time first）规则有理论保证的原因。
* **「尚未装满」这个限制让它不再是标准 LPT。** 标准的 makespan 最小化问题没有基数约束，LPT 有 $4/3$ 的近似比；加上「每箱恰好 $n/m$ 个」之后，贪心的候选集被裁剪，它退化为一个没有紧近似比的启发式。

它不追求最优解，理由有两层：

```text
理论上：带基数约束的均衡划分是 NP-hard 的
实践上：输入 w_e 本身只是负载「估计值」
        为一个带噪声的目标函数求精确最优没有意义
```

第二条更关键。这是一个贯穿 EPLB 设计的判断：算法精度不应超过输入精度。

### 副本分配：贪心，且是最优的

Step 2 的问题是：给定 $E$ 个逻辑专家、$P$ 个物理槽位，分配副本数 $c_e$（满足 $\sum_e c_e=P$ 且 $c_e\ge1$），使得

$$\max_e\frac{w_e}{c_e}$$

最小。

做法是从每个逻辑专家一个副本开始，把剩余的 $P-E$ 个槽位逐个分配，每次给**当前 $w_e/c_e$ 最大**的那个逻辑专家。

与装箱不同，**这个贪心得到的是最优解**。可以这样看：

```text
判断「max_e w_e/c_e ≤ θ 是否可行」
  等价于问 Σ_e ⌈w_e/θ⌉ ≤ P 是否成立
  即：达到 θ 这个上界，最少需要多少个槽位

贪心每一步都在削减当前的最大值
  等价于让 θ 从大到小连续下降，恰好停在槽位耗尽的那一刻
```

这与选举席位分配中的除数法（divisor method）是同一个算法，其最优性有成熟结论。

### 一个隐含假设

注意 Step 2 优化的是 $w_e/c_e$ 而不是 $w_e$：它衡量的是**每个副本的平均负载**，而不是逻辑专家的总负载。这里隐含了一个假设：

> 同一个逻辑专家的 token 能够在它的副本之间均匀分摊。

这个假设由**运行时的副本选择策略**保证，而它不在 EPLB 的职责范围内（见前文「容量分布，不是路由决策」）。如果运行时把某个热门 Expert 的 token 都发给了同一个副本，那么 EPLB 规划出的容量就是虚的，$\rho$ 不会真的下降。

**规划与执行必须配套，这是 EPLB 落地时最容易踩空的地方。**

## 两种策略：Prefill 与 Decode

除分层策略外还有一个全局策略：忽略 group 结构，在全局范围内复制 Expert，再把所有物理专家直接装箱到所有 GPU。

实现上，全局策略是分层策略在「group 数与节点数都退化为 1」时的特例，两者共用同一套逻辑：Step 1 变成 trivial（只有一个箱子），Step 2 在全局范围复制，Step 3 面向全部 GPU 装箱。

选择依据是部署阶段：

```text
分层策略
  适用条件：节点数能整除 group 数
  特点：保持 group 的节点局部性，副本受限于节点
  场景：Prefill，EP 度较小

全局策略
  适用条件：其他情况
  特点：放弃 group 局部性，放置自由度最大
  场景：Decode，EP 度较大
```

### 为什么两个阶段的选择不同

有三条理由，且第三条最容易被忽略。

```text
理由一：瓶颈位置不同
  Prefill：T = B×S，token 量巨大 → 通信量大，bandwidth-bound
           跨节点流量是主要矛盾 → 优先保 group 局部性
  Decode： T = B，消息小、数量多 → latency-bound
           单个 Rank 的长尾是主要矛盾 → 优先保负载均衡

理由二：容错空间不同
  Prefill 的 Grouped GEMM 较大，少量不均衡可以被计算时间摊薄
  Decode 每步时间极短，任何长尾都直接放大到端到端延迟

理由三：EP 度大时约束会冲突
  EP 度大 ⇒ 每 GPU 的物理专家数极少（可能只有一两个）
          ⇒ 放置的自由度本来就很低
          ⇒ 「每 GPU 个数相等」这个硬约束叠加 group 局部性
             可能根本没有可行的均衡解
```

第三条把前面的伏笔收了回来：**EP 度越大、放置粒度越粗，硬约束就越容易与 group 约束冲突。** 此时坚持 group 局部性不是保守，而是无解，所以必须放弃它。

## EPLB 不做什么

EPLB 是一个纯函数：输入负载估计，输出放置方案。它刻意把几件事留在了外面，而这些被排除项恰恰是实际部署中更难的部分。

### 负载预测

上游明确说明预测方法不在其范围内，常见做法是对历史统计做滑动平均。这是整个系统最脆弱的环节：

```text
统计窗口太短 → 噪声大，方案频繁变动，迁移开销吃掉收益
统计窗口太长 → 跟不上负载漂移，方案总是过时
```

更棘手的是负载分布本身会随**输入分布**漂移：不同语言、不同任务、不同领域的 token 激活的 Expert 不同。一个在通用流量上标定的方案，遇到某类请求突增时可能完全失效。

因此 EPLB 的效果上限由预测质量决定，而不是由算法质量决定。

### 权重迁移

新方案要生效，必须把 Expert 权重在 GPU 之间实际搬动。这部分代价不在 EPLB 内：

```text
迁移时机：不能每步做，需要按周期或触发条件
迁移开销：Expert 权重体积大，搬运期间可能需要暂停服务或双缓冲
一致性：  迁移过程中，路由表与实际放置必须始终保持一致
```

由此可以推出一个重要结论：**EPLB 是周期性、粗粒度运行的，不是每个 step 都重新求解。** 这也解释了为什么它可以接受一个跑在 CPU 上、含串行循环的实现——它不在关键路径上。

### 运行时副本选择

前文已述：它决定了「均摊假设」是否成立。

### 与训练侧负载均衡的关系

DeepSeek-V3 有两套均衡机制，容易混为一谈，但它们作用在完全不同的层面：

```text
训练侧：auxiliary-loss-free 均衡
  手段：在 gating 中引入可学习的 bias，调整 Expert 被选中的倾向
  改变：路由本身，使负载分布天然平坦
  代价：干预了模型的选择行为，存在质量风险

部署侧：EPLB
  手段：调整 Expert 的副本数与放置位置
  改变：负载如何映射到硬件，完全不动路由结果
  代价：额外显存与迁移开销，但对模型输出零影响
```

两者正交且互补：训练侧降低 $w_e$ 分布本身的方差，部署侧处理残余的不均衡。

EPLB 的优雅之处正在于它**不触碰模型语义**——启用与不启用 EPLB，模型的输出完全一致（浮点归约顺序变化除外）。这使它成为一个纯粹的部署层优化，可以随时开关、随时调参，不需要重新评估模型质量。

## 代价

```text
显存：P - E 份额外的 Expert 权重
      EP 度大时这个比例可以相当高
      这部分显存本可以用来放 KV cache 或支撑更大的 batch

迁移：周期性的权重搬运开销

复杂度：统计收集、按层组织的路由表、运行时副本选择
        且与 Dispatch / Combine 的实现耦合

残余不均衡：输入是估计值，装箱是启发式
            实际的 ρ 不会真正等于 1
```

其中显存代价是最需要权衡的。判断标准可以写得很直接：

```text
EPLB 划算 ⟺ 减少的 max_r 等待时间 > 少放的 KV cache 导致的吞吐损失
```

这也说明 EPLB 不是无条件收益的。在负载本来就比较均匀、或显存已经极度紧张的场景下，增加冗余副本可能是净亏损。

## 小结

* EP 的时间由 $\max_r L_r$ 决定，而 Router 的数据相关性让负载天然长尾；$w_e$ 同时是计算量与通信接收量，因此一次均衡治两个症状；
* **纯 placement 存在下界 $\max_r L_r\ge\max_e w_e$**，只要有 Expert 的负载超过 $\bar L$ 就无解——这是必须引入冗余副本的根本原因，也是理解 EPLB 的起点；
* 冗余把逻辑专家与物理专家分离，副本数把有效负载降为 $w_e/c_e$；问题随之分裂为削峰（复制）与填谷（放置）；
* 硬约束是「每 GPU 物理专家个数相等」，优化目标是「每 GPU 负载相等」，前者硬后者软；每层独立求解；
* 分层策略三步走：group 装箱到节点、节点内复制、物理专家装箱到 GPU；其唯一实质取舍是**用副本放置的自由度换 group 的节点局部性**；
* 两个子算法性质不同：装箱是带基数约束的降序贪心，属启发式；副本分配的贪心是最优的。不追求最优的理由是输入本身是估计值——算法精度不应超过输入精度；
* 副本分配隐含「token 在副本间均匀分摊」的假设，该假设由运行时副本选择保证，规划与执行必须配套；
* Prefill 用分层（通信为主要矛盾），Decode 用全局（长尾为主要矛盾，且 EP 度大时 group 约束可能让问题无解）；
* 它刻意不管负载预测、权重迁移、副本选择，这三者才是实际部署的难点，也决定了 EPLB 的效果上限；
* 它与训练侧的 bias 均衡正交：**不改变任何模型输出**，是纯部署层优化，代价是显存与复杂度。
