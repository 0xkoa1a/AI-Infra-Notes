
# 分布式通信基础

## Rank、Process Group 与 Collective

在分布式程序中，每个 GPU 通常由一个独立进程控制，这个进程在通信组中的编号称为 Rank。

参与同一次通信的一组 Rank 称为 Process Group，即进程组。

Collective Communication，中文通常称为集体通信，是指通信组中的多个 Rank 共同参与一个具有整体语义的通信操作，例如：

* AllReduce；
* AllGather；
* ReduceScatter；
* AllToAll；
* Broadcast。

集体通信描述的是“最终每个 Rank 应该得到什么数据”，并不严格限定底层必须使用哪种算法实现。

例如，AllReduce 可以使用：

* Ring Algorithm；
* Tree Algorithm；
* Recursive Doubling；
* Hierarchical Algorithm；
* NVLink、NVSwitch 和跨节点网络组成的分层算法。

---

## 通信成本模型

最简单的通信成本模型是：

$$
T_{\text{comm}}=\alpha+\beta N
$$

其中：

* $\alpha$：Latency Term，即一次通信的固定启动延迟；
* $\beta$：每字节传输时间，可以近似理解为带宽的倒数；
* $V$ ：每个 Rank 在整个 Collective 中发送的数据总量（**通信量**）。

如果有效带宽为 $BW$，则可以近似认为：

$$
\beta\approx\frac{1}{BW}
$$


### 小消息与大消息

当通信量很小时：

$$
s\alpha\gg\beta V
$$

通信主要受启动延迟限制，即 latency-bound。

当通信量很大时：

$$
\beta V\gg s\alpha
$$

通信主要受链路带宽限制，即 bandwidth-bound。

## 通信原语

### AllGather

初始状态：每 Rank 持有完整数据的一个分片 $\frac{N}{p}$

结束状态：每 Rank 持有完整数据 $N$

AllGather 只拼接不同 Rank 的分片，不执行归约。若 Rank $r$ 的分片为 $X_r$，则每个 Rank 最终得到：

$$Y=[X_0;X_1;\ldots;X_{p-1}]$$


### ReduceScatter

初始状态：每 Rank 持有一个大小为 $N$ 的待归约张量

结束状态：每 Rank 只保留归约结果的一个分片 $\frac{N}{p}$

ReduceScatter 先在不同 Rank 的对应元素之间执行 Sum、Max 等归约，再把归约结果沿指定维度切成 $p$ 份：

$$Y=\operatorname{Reduce}(X_0,X_1,\ldots,X_{p-1})$$

第 $r$ 个 Rank 最终只得到 $Y$ 的第 $r$ 个分片 $Y_r$，而不是完整 $Y$。


### AllReduce

初始状态：每 Rank 持有一个大小为 $N$ 的待归约张量

结束状态：每 Rank 都持有大小为 $N$ 的完整归约结果

AllReduce 在所有 Rank 的对应元素之间执行归约，并把完整结果发送给每个 Rank：

$$Y=\operatorname{Reduce}(X_0,X_1,\ldots,X_{p-1})$$

在语义上，它可以理解为：

```text
ReduceScatter
      │
      ▼
每 Rank 得到归约结果的一个分片
      │
      ▼
AllGather
      │
      ▼
每 Rank 得到完整归约结果
```


### AllToAll

初始状态：每 Rank 持有一份大小为 $N$ 的本地数据，并按目标 Rank 切成 $p$ 个大小为 $\frac{N}{p}$ 的分片

结束状态：每 Rank 从所有源 Rank 各接收一个分片，最终数据大小仍为 $N$

设 Rank $r$ 的输入为：

$$X_r=[X_{r\rightarrow0},X_{r\rightarrow1},\ldots,X_{r\rightarrow p-1}]$$

AllToAll 后，Rank $j$ 得到：

$$Y_j=[X_{0\rightarrow j};X_{1\rightarrow j};\ldots;X_{p-1\rightarrow j}]$$

AllToAll 不执行归约，也不复制完整数据，只是按照目标 Rank 重新分发数据。这里的 $N$ 表示每 Rank 的输入和输出大小。

> 就像一个转置操作

### Point-to-Point

初始状态：源 Rank 持有一份大小为 $N$ 的数据，目标 Rank 尚未持有该数据

结束状态：目标 Rank 收到这份大小为 $N$ 的数据

Point-to-Point 只涉及指定的发送方和接收方，通常表示为：

```text
Rank i -- Send --> Rank j
Rank j -- Recv <-- Rank i
```

它不是 Collective，不要求 Process Group 中的所有 Rank 同时参与。Pipeline Parallelism 中相邻 Stage 之间的激活和梯度传输通常使用 Point-to-Point。

## Ring 算法

### Ring AllReduce (ReduceScatter + AllGather)

### Ring Pairwise AllToAll

将 $p$ 个 Rank 编号为 $0,1,\ldots,p-1$。设 Rank $r$ 的输入为：

$$X_r=[X_{r\rightarrow0},X_{r\rightarrow1},\ldots,X_{r\rightarrow p-1}]$$

其中 $X_{r\rightarrow j}$ 是 Rank $r$ 要发送给 Rank $j$ 的分片。发给自己的分片留在本地，其余分片通过 $p-1$ 轮循环发送。

第 $k$ 轮中，Rank $r$：

* 向 Rank $(r+k)\bmod p$ 发送对应分片；
* 从 Rank $(r-k+p)\bmod p$ 接收发给自己的分片。

因此每一轮中，每个 Rank 都发送一个分片并接收一个分片。

例如，三个 Rank 的初始数据为：

```text
Rank 0：[1, 2, 3]
Rank 1：[4, 5, 6]
Rank 2：[7, 8, 9]
```

每一列分别表示发给 Rank 0、Rank 1 和 Rank 2 的数据。两轮通信为：

```text
Round 1：
Rank 0 → Rank 1：2
Rank 1 → Rank 2：6
Rank 2 → Rank 0：7
```

得到：

```text
Rank 0：[1, 待接收, 7]
Rank 1：[2, 5, 待接收]
Rank 2：[待接收, 6, 9]
```

其中 `1、5、9` 是保留在本地的分片，`2、6、7` 是 Round 1 收到的分片；其余位置将在 Round 2 填入。

然后第二回合：

```text
Round 2：
Rank 0 → Rank 2：3
Rank 1 → Rank 0：4
Rank 2 → Rank 1：8
```

最终得到：

```text
Rank 0：[1, 4, 7]
Rank 1：[2, 5, 8]
Rank 2：[3, 6, 9]
```

若每 Rank 的输入大小为 $N$，每个分片大小为 $N/p$，则每 Rank 的发送量为：

$$V_{\text{Pairwise AllToAll}}=(p-1)\frac{N}{p}$$

等长分片下，每个 Rank 在每一轮的逻辑发送量和接收量都相同。

## NVLS

NVLS（NVLink SHARP）利用第三代 NVSwitch 提供的 Multicast 和 In-Switch Reduction 能力实现 Collective。它不再让数据沿 Ring 经过 $p-1$ 个邻居，而是让 NVSwitch Fabric 直接完成一对多复制和多对一归约。

NVLS 主要用于 Hopper 及之后架构组成的 NVSwitch Domain。它依赖对称内存和 CUDA Multicast Object：多个 GPU 上的物理内存被映射到同一个 Multimem 虚拟地址，GPU 通过专用 PTX 指令访问这些地址。

---

### Multicast

普通 Broadcast 中，源 GPU 需要把同一份数据分别发送给其他 GPU：

```text
GPU 0 ──► GPU 1
      ├─► GPU 2
      └─► GPU 3
```

NVLS 使用：

```text
multimem.st
```

向 Multimem Address 写入一次，NVSwitch Fabric 会把该数据复制到这个地址映射的所有物理内存位置：

```text
GPU 0
  │ 一次 Multimem Store
  ▼
NVSwitch Multicast
  ├──► GPU 1
  ├──► GPU 2
  └──► GPU 3
```

GPU 发起的是一个 Multicast Memory Operation，而不是为每个目标 GPU 分别执行一次 Store。

---

### In-Switch Reduction

普通 Reduce 需要把来自不同 GPU 的值搬到某个 GPU，再由 GPU SM 执行累加。

NVLS 使用：

```text
multimem.ld_reduce
```

该指令从同一个 Multimem Address 对应的所有物理内存位置读取数据，并按照 Sum、Min 或 Max 等操作进行归约，最后把归约结果返回发起指令的 GPU Register：

$$Y=\operatorname{Reduce}(X_0,X_1,\ldots,X_{p-1})$$

```text
GPU 0 ──┐
GPU 1 ──┼──► NVSwitch Reduction ──► Result
GPU 2 ──┼
GPU 3 ──┘
```

GPU SM 仍需要发出 Multimem 指令、处理同步并写回结果，所以 NVLS 是减少 SM 搬运与通信步骤，而不是完全不占用 SM。

---

### One-Shot AllReduce

设 $p$ 个 GPU 分别持有大小为 $N$ 的输入：

$$X_0,X_1,\ldots,X_{p-1}$$

AllReduce 的目标是让每个 GPU 都得到：

$$Y=X_0+X_1+\cdots+X_{p-1}$$

One-Shot 的做法是让每个 GPU 都对完整数组执行一次 Multimem Reduce Load：

```text
GPU 0：对完整 N 执行 multimem.ld_reduce → 完整 Y
GPU 1：对完整 N 执行 multimem.ld_reduce → 完整 Y
...
GPU p-1：对完整 N 执行 multimem.ld_reduce → 完整 Y
```

每个 GPU 直接得到完整归约结果，因此不需要再执行 AllGather。

优点是依赖链短，适合单个 NVSwitch Domain 内的小消息和延迟敏感场景。

缺点是每个 GPU 都独立请求完整数据，然后本地执行归约，通信量为：

$$V_{\text{One-Shot}}\approx pN$$


---

### Two-Shot AllReduce

Two-Shot 与 Ring AllReduce 一样，在语义上分为：

```text
ReduceScatter
      │
      ▼
AllGather
```

但 NVLS 将每个阶段交给 NVSwitch Multimem Operation，而不是执行 $p-1$ 轮 Ring 传递。

首先将每个输入切成 $p$ 个分片：

$$X_r=[X_r^{(0)},X_r^{(1)},\ldots,X_r^{(p-1)}]$$

其中每个分片大小为 $N/p$。

#### ReduceScatter

Rank $j$ 使用 `multimem.ld_reduce`，只归约所有 GPU 的第 $j$ 个分片：

$$Y^{(j)}=\sum_{r=0}^{p-1}X_r^{(j)}$$

完成后：

```text
Rank 0：Y^(0)
Rank 1：Y^(1)
...
Rank p-1：Y^(p-1)
```

每个 Rank 只负责最终结果的一个分片。

#### AllGather

每个 Rank 再使用 `multimem.st`，将自己的归约结果分片 Multicast 给所有 Rank：

```text
Rank 0：Multicast Y^(0)
Rank 1：Multicast Y^(1)
...
Rank p-1：Multicast Y^(p-1)
```

最终每个 Rank 都得到：

$$Y=[Y^{(0)};Y^{(1)};\ldots;Y^{(p-1)}]$$

按每 Rank 端点发送量计算，ReduceScatter 和 AllGather 各需要：

$$V_{\text{RS}}=V_{\text{AG}}=\frac{p-1}{p}N$$

因此 Two-Shot AllReduce 为：

$$V_{\text{Two-Shot}}=2\frac{p-1}{p}N$$

它与 Ring AllReduce 的理想通信字节数相同，但关键路径只有 ReduceScatter 和 AllGather 两个 Fabric 阶段，而不是 $2(p-1)$ 个 Ring 步骤。

### 不同通信算法比较

|  | Ring–AR | One–Shot AR | Two–Shot AR |
| --- | --- | --- | --- |
| 编程模型 | 通信Buffer中转 | 对称内存访问（零拷贝） | 对称内存访问（零拷贝） |
| 步数 | $2(p-1)$ | $1+1$，广播+本地reduce | $1+1$，RS+AG |
| 每GPU通信量 | $2\cdot\dfrac{p-1}{p}\cdot N$ | $p\cdot N$ | $2\cdot\dfrac{p-1}{p}\cdot N$ |
| Reduce计算位置 | GPU SM | GPU SM | NVSwitch/GPU SM均可 |
| SM占用 | 高（需要大量channels打满带宽） | 中（需要本地reduce） | 低（在网reduce）/ 中（本地reduce） |
| 最佳场景 | 多机/单机Fallback | 单机，小消息量，延迟敏感 | 单机，数据量较大，吞吐/SM资源敏感 |
