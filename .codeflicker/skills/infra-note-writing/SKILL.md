# inference-learning 笔记写作

面向 `0xkoa1a/Inference-Infra-Notes` 仓库的中文技术笔记。目标读者是作者本人，用于日后快速回忆一个系统「为什么这样设计」。

核心判据：**读者读完应该能自己复述出因果链，而不是记住一堆结论。**

## 工作流

1. **先读源材料再动笔。** 论文/源码要读完相关章节，不要只看 abstract 就开始写。PDF 没有 `pdftotext` 时用 Python 提取（见「工具」）。
2. **先出写作计划，等确认后再写。** 计划里要写清章节结构、每节写什么、与已有笔记的关系（引用还是重复）。
3. **不确定的写作决策要问，不要自行决定。** 典型需要问的：文件命名、是否写评测数据、与已有笔记冲突时怎么处理、章节是否拆分。
4. **写完自查**（见「自查清单」）。

## 格式约定

### 列表优先于代码块

能枚举的内容一律用 `-` 列表，**不要用 ```text 代码块**。列表标记统一 `-`，不用 `*`。

只有内容依赖空间布局或箭头时才保留代码块：流程图、数据布局变换、连续的因果链示意。

反例（本仓库曾出现，已被改掉）：

````markdown
```text
四、负载用什么？
    路线一：用历史统计做预测
            方案可以离线慢慢求解，不占关键路径
```
````

改成：

```markdown
- 负载用什么？
  - 路线一：用历史统计做预测
    - 方案可以离线慢慢求解，不占关键路径
```

保留代码块是对的场景：

````markdown
```text
Token-Owned 布局（每 Rank 持有自己的 token）
        │
        ▼
Dispatch：把 token 送到目标 Expert 所在的 Rank
```
````

### 标题与编号

标题**不带任何编号**，包括中文数字。bullet 开头也不带编号。

- 错：`## 七、重路由：分解，而不是再优化` / `### 一、重叠的前提是配比稳定` / `- 四、负载用什么？`
- 对：`## 重路由：分解，而不是再优化` / `### 重叠的前提是配比稳定` / `- 负载用什么？`

正文引用其他章节用「前文」，不要用「第四节」「上一节」「下一节」（章节会被增删重排，编号引用一定会失效）。

### 章节层级要克制

倾向精简章节数。只有一小段正文加一组 bullet 的 `###` 子节，应该降级为加粗段落并入父节。

```markdown
**硬约束与优化目标处在不同层次。** $P$ 必须能被 GPU 数整除……
```

判断标准：这个子节的内容值得读者在目录里单独看到吗？不值得就并进去。

### 不写小结章节

**不要有「小结」「总结」「要点回顾」这类章节。** 内容讲完就结束。小结只是把正文的结论再抄一遍，读者要么已经读懂了不需要它，要么没读懂而小结也救不了。

如果觉得非得靠小结才能串起来，说明正文的因果链本身没写清楚，应该去修正文。

## 公式表达

**每个公式前必须有一句自然语言说明它的本质含义。** 公式是那句话的精确化，不是替代。

对：

```markdown
如果只允许**重排**（permutation），即每个 Expert 恰好放在一个 Rank 上，那么无论怎么排，都会有 Rank 的负载最大值大于专家的负载最大值：

$$\max_rL_r\ \ge\ \max_e w_e$$
```

多项构成的时间/代价分解，先用自然语言把执行顺序和依赖讲清，再给公式；然后逐项展开，每项都是「一句话本质 + 公式」：

```markdown
前向中，方案求解必须先完成；随后重路由与副本权重分发可以互相重叠，两者都完成后才能执行 token AllToAll 和 MoE 计算。因此前向总时间近似为：

$$T_{\text{fwd}}\ \approx\ T_{\text{solve}}+\max(T_{\text{reroute}},T_{\text{distr}})+T_{\text{a2a}}+T_{\text{moe}}$$

其中与负载和副本方案直接相关的三个主要代价项是：

- **MoE 计算耗时由重路由之后最忙的 Rank 决定。** 它拿到的 token 最多，其他 Rank 都要等它：

  $$T_{\text{moe}}\ \propto\ \max_{r}\sum_{e}q_{er}$$
```

独立成行的公式用 `$$...$$`，行内符号用 `$...$`。不要把块级公式写成行内。

## 叙述结构

### 原因 → 做法，一次说完

**先把原因说透，再给做法。同一个原因不允许说两遍。**

真实反例（`UltraEP.md` 重路由节，已重写）：

```markdown
配额定下来之后，重路由不再触碰均衡目标，只是把配额分解成……

正因为如此，这里可以免费地捞一个局部性收益。        ← 原因第一次，模糊

- 第一步：本地优先
  - ……
- 第二步：剩余需求按比例分摊
  - ……

为什么局部性是免费的？因为本地优先只改变了「谁来消费    ← 同一个原因第二次，
这份配额」，没有改变配额本身。配额表不动，就意味着解出    才真正说清
来的负载上限 $\theta$ 不受影响。

最后还要落到 token 粒度：AllToAll 需要知道每一个 token   ← 关键机制反而只有
的目的地，而配额只是聚合的计数。做法是把各个物理实例按    一句，说不明白
顺序排好、算出配额的累加值，某个 token 就发给「累加配额
第一次覆盖到它的序号」的那个实例。
```

三个病灶：

- 原因被拆成「模糊的一句」和「后面补充的详细解释」，中间隔着做法
- 「正因为如此」「为什么 X 是免费的？」这类衔接是冗余的信号
- 真正需要展开的机制（token 粒度）被压成一句

重写后：

```markdown
配额已经锁定了均衡质量，重路由只需保证分解出来的份额总量与配额一致，均衡就不会变差。这带来一个不花任何代价的局部性收益：**本地优先只改变「谁来消费这份配额」，不改变配额本身**，配额表不动就意味着解出来的负载上限 $\theta$ 不受影响，于是跨卡流量减少而均衡质量毫发无损。

分解分两步：

- 本地优先消费：……
- 剩余需求按比例分摊：……

最后要落到 token 粒度，因为 AllToAll 需要的是每一个 token 的目的地，而配额只是聚合计数。做法是把配额表变成一组区间边界：

- 把 Expert $e$ 的各个物理实例排成一个固定顺序
- 对它们分到的配额做前缀和，得到一串累加边界，相邻边界之间就是一个实例负责的区间
- 该 Rank 发往 $e$ 的 token 按本地序号编号，序号落在哪个区间就发给哪个实例

因为这些配额之和恰好等于该 Rank 发往 $e$ 的 token 总数，每个 token 必然落在唯一一个区间里，不会漏也不会撞。于是每个 token 的目的地只是一次在有序边界上的本地上界查找，不需要任何跨 Rank 协调。
```

### 详细程度要对齐重要性

越核心的机制写得越细。判断一段够不够细的办法：**读者能照着这段话在脑子里跑一遍这个机制吗？** 不能就是不够细。

常见失衡：动机和背景写了三段，真正的算法只有两句。

### 禁止元叙述评价句

不传递信息、只预告下文或自我评价的句子一律删掉，直接说内容。

黑名单（都是本仓库真实出现过并被删掉的）：

- 「这一点值得单独说清」
- 「这里有一个很关键的洞察」
- 「值得注意的是，X 同时是两件事」→ 直接写「X 同时是两件事」
- 「这一点很值得单独记住」
- 「这是 XXX 最核心的算法洞察」
- 「第三条把前面的伏笔收了回来」
- 「后面会看到它带来的连带影响」
- 「有三条理由，且第三条最容易被忽略」→ 「有三条理由」
- 「这一节再往前一步」「综合前面的分析」
- 「固定布局还有一个容易被低估的好处」→ 直接写这个好处
- 「而且这里有一个讽刺的耦合」→ 直接写这个耦合
- 「本文的主线就是追踪这条连锁反应」
- 「两个细节决定了它的性质」→ 「它的性质由两个细节决定」（去掉预告感）

保留的不是元叙述、而是实质判断的句子：

- 「第二条更关键。」（指出哪条理由权重更高，是信息）
- 「这也是后续 relay 设计要解决的问题」（真实的前后依赖关系）

## 内容边界

- **不写代码实现细节**：函数名、伪代码行号、张量形状、API 签名、参数名都不写。写清算法的逻辑与取舍即可。
- **默认不写评测数据**：笔记讲方法与洞察。要写数据需先确认。
- **文档要 self-contained**：跨笔记的内容重复是允许的，不要为了去重让单篇读不通。但背景篇已详述的内容，在方法篇里几句话带过并给出文件引用（如 `` `background.md` ``）。
- **推断要与论文原文区分**。自己的推断（例如「X 是被某种硬件形态解锁出来的方案」）可以写，但要意识到它不是论文的论断，必要时向用户确认是否保留。
- **新笔记与已有笔记冲突时**：不要默默改，也不要放着。把冲突点找出来告诉用户，通常的处理是把原来过强的普适性论断改成中性表述并留出口，例如「冗余是必需的，重排是可选的」。

## 自查清单

写完或改完后跑一遍：

```bash
# 元叙述残留
grep -n "值得注意\|值得单独\|值得记住\|这一点值得\|洞察\|伏笔\|后面会看到\|容易被低估\|正因为如此\|综合前面\|本文的主线" *.md

# 标题与 bullet 编号
grep -nE "^#+ (一|二|三|四|五|六|七|八|九)、|^- (一|二|三|四|五)、" *.md

# 章节编号式引用
grep -n "上一节\|下一节\|第[一二三四五六七八九]节" *.md

# 星号列表
grep -nE "^\s*\* " *.md

# 小结类章节（应为空）
grep -nE "^#+ *(小结|总结|要点回顾|本节回顾)" *.md

# 块级公式定界符（应为偶数）
grep -c '^\$\

# 代码围栏配对（应为偶数）
grep -c '^```' *.md
```

再人工确认：

- 每个公式前是否都有一句自然语言的本质说明
- 有没有「原因说两遍」的段落
- 最核心的机制是不是写得最细
- 跨文件引用的路径与章节名是否还存在
