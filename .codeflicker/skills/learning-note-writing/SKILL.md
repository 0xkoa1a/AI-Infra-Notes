# 综合学习笔记写作

把笔记写成日后能够重新建立理解的材料，而不是对源材料的缩写或结论清单。

核心判据：**读者读完后，应该能沿着因果链在脑中运行一遍关键机制，并知道结论依赖哪些假设。**

## 开始前确定边界

先确认当前任务属于哪一种：

- **新建完整笔记**：允许重新组织源材料，建立适合学习的叙述顺序。
- **结构性重构**：可能改变章节、内容边界、术语体系或与其他笔记的分工。
- **保守重组**：只统一术语、删除明确重复、移动段落和补少量承接句；不主动压缩或重写原文。
- **局部增补或修正**：在现有风格中做最小、语义安全的修改。

以下情况先给出写作计划并等待确认：

- 新建完整笔记。
- 跨章节或跨文件重构。
- 改变详略、来源范围、章节骨架或内容边界。
- 用户明确要求先制订计划。

以下情况通常直接执行：

- 局部解释、术语修正和格式调整。
- 用户已经提供并确认了可执行计划。
- 不改变内容取舍的机械整理。

遇到会实质改变成品的选择时优先询问，不自行决策。常见问题包括：

- 文件名、标题和目标读者。
- 允许使用哪些来源，是否可以补充在线资料或源码。
- 应采用哪种笔记结构，是否需要单独背景篇。
- 是否保留实验、实现细节、推断、问题和配图。
- 新材料与已有笔记或既有共识冲突时怎样处理。
- 某段内容应删除、压缩、移动还是保留。

## 建立来源基线

先完整阅读与目标内容相关的源材料，再动笔。不要只根据摘要、README、搜索片段或论文结论写方法。

- 用户限定唯一来源时，严格守住边界，不从相邻资料补充“常识”。
- 使用论文时，同时核对正文、公式、算法、图注和原页版面；图示有时包含正文省略的依赖关系。
- 使用源码时，交叉核对入口、核心实现、测试、常量和说明文档；记录所依据的版本或 commit。
- 使用多个来源时，先确定证据优先级，避免把实现行为、论文主张和个人推断混成一个事实。
- 修改现有笔记时，先读目标文件、共同背景和同系列代表性笔记，确认术语与详略基准。

写作中区分四类内容：

- **来源明确说明的事实**：按原意表述，不扩大适用范围。
- **从实现行为得到的推断**：明确写成推断，并给出推断依据。
- **不同来源之间的冲突**：列出冲突及各自上下文，交给用户决定如何统一。
- **来源没有交代的问题**：放入“问题”或相邻段落，不自行发明缺失机制。

## 选择适合内容的结构

不要把一种章节模板强加给所有笔记。先判断读者要建立哪一种理解；拿不准时询问用户。

### 具体工作或系统方案

默认采用：

- `背景`：按需使用，只放工作特有的前置知识。
- `动机`：说明现有限制、方案要改变什么，以及核心取舍。
- `方法`：先给输入、输出和职责边界，再按依赖顺序讲机制。
- `代价与适用条件`：说明关键路径、资源成本、证据边界和成立条件。
- `问题`：按需记录来源没有解释清楚的事实问题。

这套结构不是硬模板。如果原文已有更适合的组织方式，或用户要求保守重组，优先保留内容和理解顺序。

### 基础概念或原理

围绕“问题是什么—直觉是什么—对象如何定义—机制或推导如何进行—结论在哪些条件下成立”组织，不必设置“动机”和“方法”。

### 源码或实现导读

先讲组件职责、逻辑维度、输入输出、状态所有权和数据移动，再讲关键实现。不要一开始就按文件或函数逐个翻译。

### 比较、综述或共同背景

先建立统一抽象和术语，再呈现假设分歧、设计变量、目标与代价。不同工作对负载、数据、用户或环境的判断可能不同；不要把某一工作的动机写成所有工作接受的共同事实。

### 数学或算法推导

先说明问题、变量和目标，再逐步推导。每个中间结果都解释它解决了什么，最后写清结论的适用条件，不只给公式链。

## 按理解依赖排序

如果理解 A 需要先知道 B，就先介绍 B。常见的可靠顺序是：

- 共同对象与职责边界。
- 输入、输出和约束。
- 提供自由度的静态结构或长期状态。
- 基于这些自由度作出的决策。
- 决策怎样落到具体对象或执行步骤。
- 通信、同步、状态更新和异常路径。
- 代价、证据和适用条件。

避免以下倒序：

- 先抛出一个表、拓扑或变量，后面才解释它是什么。
- 先讲求解器，后讲它求解的问题。
- 先讲优化收益，后讲数据实际怎样移动。
- 先使用简称、符号或正式标识，后面才定义。

叙述较复杂的在线流程时，明确区分：

- 哪个信号属于当前步骤，哪个来自历史或预测。
- 哪个决策服务当前对象，哪个通过流水线服务后续对象。
- 哪些操作必须串行，哪些可以重叠，重叠是否竞争同一资源。

## 控制详略而不丢信息

详略应跟理解重要性对齐。判断一段是否足够具体：**读者能否只根据这段话，在脑中执行一次机制？**

- 核心算法、数据流、状态变化和正确性条件写细。
- 通用背景、论文组织、实现样板和重复结论写短。
- 不逐节翻译论文，也不逐文件翻译源码。
- 不以缩短篇幅为目标；简洁意味着删除无信息文字，不是删掉必要上下文。

动机不应比方法更详细。常见失败是用多段文字证明问题重要，真正的方法却只剩两句。

进行保守重组前，先盘点并在完成后复核：

- 公式与符号定义。
- 图片、图注和图号。
- 数值例子与反例。
- 算法步骤和约束。
- 实验数字与边界。
- 实现细节、比较和答疑结论。

除非用户明确要求删节，否则不要在移动章节时顺手压缩这些内容。

## 讲清原因、机制与结果

先把原因说透，再给做法；同一个原因不要拆成前后两次解释。

推荐使用下面的局部结构：

- 当前约束或问题是什么。
- 因此需要引入什么自由度或中间量。
- 具体怎样计算、移动或更新。
- 为什么这一步保持正确性或改善目标。
- 它引入了什么新代价或限制。

不要用“这里有一个关键洞察”“这一点值得注意”“后面会看到”等元叙述代替信息。若一句话只评价下文重要、不增加事实，就直接删掉。

## 使用公式

公式用于消除歧义、表达守恒关系、目标函数、下界或时间依赖，不用于显示形式化程度。

- 先用自然语言说明公式表达的本质，再给公式。
- 在公式前定义符号；不要让读者从公式倒推变量含义。
- 时间或代价分解先讲串行、依赖和重叠关系，再用加法与 `max` 精确化。
- 公式之后只解释真正影响理解的项，不逐字符朗读。
- 用户要求避免 math-heavy 时，只保留能防止误解的公式，其余用直觉和例子讲解。

行内符号使用 `$...$`，独立公式使用 `$$...$$`，并遵循目标文档现有格式。

## 保留必要的实现细节

不要把学习笔记写成 API 文档或逐行源码翻译，但也不要排斥实现细节。

应保留能够解释以下问题的细节：

- 数据、参数或状态具体存在哪里、往哪里移动。
- 哪个组件生成某个结构，哪个组件消费它。
- buffer 的所有权、生命周期和复用约束。
- 同步、并发、fallback 和正确性条件。
- 某个数据结构、常量或执行策略为什么决定算法行为。

函数签名、完整参数表、伪代码行号和无关张量形状通常省略。若正式标识有助于对照源码，首次出现时保留标识并给出自然语言解释。

源码没有解释的常量、取整或特殊处理，不要替作者补理由。描述观察到的行为，并将解释标为推断或未决问题。

## 使用实验与证据

实验数据的作用是支撑方法判断，不是复刻论文实验章节。

- 只保留能回答“收益是否存在、开销是否隐藏、在哪种规模成立”的关键数字。
- 同时写明硬件、规模、部署方式、基线或其他影响外推的条件。
- 区分端到端结果、微基准、合成测试和正确性测试。
- 不把 README 宣称、测试阈值或单个例子写成普遍性能结论。
- 用户明确不写实验时，不加入实验内容。

## 处理系列笔记与术语

同一系列先确定共同背景和术语来源，再写具体笔记。

- 独立笔记应在合理范围内 self-contained。
- 专题系列把共同概念、统一符号和设计空间放在背景篇。
- 具体工作只保留其特有背景；必要时用一两句提醒共同概念，不重新展开教程。
- 去重不能破坏理解顺序。若某个定义是紧邻机制所必需，可以简短重述。

统一术语时：

- 一个概念只使用一个主要名称。
- 首次出现可附原文术语或正式标识，后文使用统一名称。
- 保留论文、源码或标准中的正式类名、函数名、算法名和缩写。
- 不做脱离上下文的机械替换；同一个词在不同语境中可能表达不同动作。

如果不同工作采用不同假设，显式呈现 assumption divergence。不要为了术语统一，把实质分歧抹平成一条“共识”。

## 使用列表、标题与图示

### 列表

枚举、步骤、输入输出、约束和对比优先使用 `-` 列表，列表标记统一用 `-`。

仅当内容依赖空间布局、箭头、时间关系或连续因果链时使用 `text` 代码块。不要把普通层级列表包进代码块。

### 编号

标题不使用“第一章”“七、方法”等装饰性编号。普通 bullet 也不加中文数字前缀。

算法确有顺序依赖时，可以使用有序列表或 Step 1/2/3；这里的编号表达执行语义，不是装饰。

正文优先使用稳定的内容引用，如“前文的配额定义”，避免依赖可能变化的章节编号。

### 标题层级

章节层级保持克制。只有一小段正文或一组短 bullet 的子节，通常改成加粗段落并入父节。

默认不设置重复正文的“小结”“要点回顾”等章节。如果需要小结才能理解，先检查正文的因果链是否断裂；用户明确要求总结时除外。

### 图示

只使用能显著降低理解成本的图：结构、数据流、时间线、拓扑、布局或状态变化。

- 引用源材料图片时，保留必要图形区域并注明原图号。
- 正文解释读图方式和图片承担的论证作用，不只写“如下图”。
- 不用装饰性图片填充页面。
- 修改现有笔记时保留仍然承担信息功能的图和图注。

## 修改现有笔记

先判断用户要求的是重写还是保守编辑。

### 重写

允许重新组织、合并、删节和改写，但仍需保持来源忠实，并确认内容边界。

### 保守重组

只做以下修改：

- 统一术语。
- 删除共同背景中已经充分解释的重复内容。
- 移动原有段落以建立依赖顺序。
- 添加必要的承接句。

不要把原文改写成摘要。尤其不要删除原有例子、公式、图表、实现细节、实验数字、对比或答疑，除非用户明确授权。

### 局部编辑

保持目标文件原有风格、符号、标题和详略，只修正用户指出的问题。不要顺手重构相邻内容。

## 写作质量检查

完成后只做与写作本身有关的核对，并服从用户对检查范围的要求。

- 每个关键结论能否追溯到允许的来源或明确标注的推断。
- 术语、符号、输入输出和职责边界是否前后一致。
- 是否先介绍依赖概念，再使用它。
- 核心机制是否比通用背景写得更详细。
- 公式前是否已有自然语言解释。
- 串行、重叠、资源竞争和状态生命周期是否说清。
- 实验数字是否带有必要条件，是否被过度外推。
- 来源未说明的内容是否被误写成事实。
- 保守编辑是否意外丢失原有技术信息。
- 列举是否使用列表，图示是否确实依赖空间关系。
- 是否残留重复原因、空洞评价、装饰性编号或重复正文的小结。

最后通读并尝试用自然语言回答本文最重要的几个问题。如果答案需要依靠源材料而不是笔记本身，说明关键解释仍不完整。
