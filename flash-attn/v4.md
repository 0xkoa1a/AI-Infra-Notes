## 1. 整体心智模型


### 1.2 数据经过哪些存储空间

先只看数据路径：

```text
GMEM Q/K/V
    │
    │ TMA 或 cp.async
    ▼
SMEM Q/K/V
    │
    │ SS-UMMA: Q × K^T
    ▼
TMEM S
    │
    │ TMEM → registers
    ▼
registers: mask、row max、exp、row sum
    │
    │ registers → TMEM
    ▼
TMEM P
    │
    │ TS-UMMA: P × V
    ▼
TMEM O
    │
    │ final correction、类型转换
    ▼
SMEM O
    │
    │ TMA store 或普通 cooperative store
    ▼
GMEM O
```

这里的 SS-UMMA 表示两个输入都来自 SMEM；TS-UMMA 表示第一个输入 P 来自
TMEM，第二个输入 V 来自 SMEM。S、P、O 都不会写回 HBM 作为中间结果。

### 1.3 一个 CTA 中的 warp 角色

默认配置有 16 个 warp，也就是 512 个线程。角色在
[flash_fwd_sm100.py:263](/Users/yangyixin03/Workspace/inference-learning/flash-attention/flash_attn/cute/flash_fwd_sm100.py:263)
中分配：

| Warp ID | 角色 | 主要工作 |
|---|---|---|
| 0–3 | Softmax 0 | 处理 query stage 0 的 128 行 S |
| 4–7 | Softmax 1 | 处理 query stage 1 的 128 行 S |
| 8–11 | Correction | 根据新的 row max 修正 TMEM 中的旧 O |
| 12 | MMA | 分配 TMEM，发出 QK/PV UMMA |
| 13 | Epilogue | 将 correction 写入 sO 的结果搬到 GMEM |
| 14 | Load | 发起 Q/K/V 的 TMA load |
| 15 | Empty 或 CLC | 默认不参与数据计算；启用 CLC 时负责调度 |

每四个 softmax/correction warp 可以看成一个 128-thread warpgroup。128 个线程与
一个 stage 的 128 个 Query rows 对应，所以 softmax 的基本 ownership 是“一线程负责一行”，
而不是一个 warp 合作处理一行。


## 2. Tile 层次与 CTA ownership

源码里出现的 tile 至少有三个层次。先统一符号：

```text
M  = m_block_size      = 128
N  = n_block_size      = 128
D  = head_dim_padded
Dv = head_dim_v_padded
q  = q_stage           = 1 或 2
g  = cta_group_size    = 1 或 2
```

它们对应的定义位于
[flash_fwd_sm100.py:172](/Users/yangyixin03/Workspace/inference-learning/flash-attention/flash_attn/cute/flash_fwd_sm100.py:172)：

```python
self.cta_tiler    = (q * M, N, D)
self.mma_tiler_qk = (g * M, N, D)
self.mma_tiler_pv = (g * M, Dv, N)
```

### 2.1 Scheduler work tile

Scheduler 分配的 `work_tile.tile_idx` 包含：

```text
(m_block, head_idx, batch_idx, split_idx)
```

其中一个 `m_block` 对每个 CTA 包含 `q × M` 个 Query rows。若使用 2CTA，
同一个 cluster work tile 一共覆盖：

```text
每 CTA：q × M rows
每 cluster：g × q × M rows
```

| 配置 | 每 CTA 的 Query rows | 每 cluster 的 Query rows |
|---|---:|---:|
| 1CTA，`q=1` | 128 | 128 |
| 1CTA，`q=2` | 256 | 256 |
| 2CTA，`q=1` | 128 | 256 |
| 2CTA，`q=2` | 256 | 512 |

这里的 256 或 512 行是一个 scheduler work tile 的总覆盖范围，不是一次 UMMA 的
M shape。

### 2.2 Query stage

`q_stage` 是一个 CTA 同时维护多少套 Query tile 和 S/P/O 状态：

```text
stage 0: M 个 Query rows
stage 1: M 个 Query rows
```

当 `q_stage=2` 时，代码会分别发出 stage 0 和 stage 1 的 QK/PV。它不是把两个
stage 合成一次更大的 UMMA。这样做的目的，是让 stage 0 使用 Tensor Core 时，
stage 1 可以做 softmax，反之亦然。

### 2.3 单次 QK UMMA tile

QK 的联合 MMA tile 是：

```text
Q: (gM, D)
K: (N, D)
S: (gM, N)
```

也就是：

```text
(gM, D) × (D, N) → (gM, N)
```

1CTA 时 `g=1`，结果 S 是 `(128,N)`；2CTA 时联合结果是
`(256,N)`，但每个 CTA 的 TMEM 只保存属于自己的 128 行。

### 2.4 单次 PV UMMA tile

源码将 PV 的 tiler 写成 `(gM,Dv,N)`，因为对 GEMM 而言：

```text
M 维 = Query rows
N 维 = 输出 Dv
K 维 = KV block 的 N
```

对应数学形状：

```text
P: (gM, N)
V: (N, Dv)
O: (gM, Dv)
```

P 是 TS-UMMA 的 TMEM A operand；V 是 SMEM B operand；结果累加到 TMEM O。

### 2.5 2CTA 如何切联合 tile

2CTA 模式下：

```text
CTA0: V coordinate = 0
CTA1: V coordinate = 1
```

kernel 用 block index 得到 `mma_tile_coord_v`：

```python
mma_tile_coord_v = bidx % size(tiled_mma_qk.thr_id.shape)
is_leader_cta = mma_tile_coord_v == 0
```

然后取得本 CTA 的 MMA participant：

```python
thr_mma_qk = tiled_mma_qk.get_slice(mma_tile_coord_v)
thr_mma_pv = tiled_mma_pv.get_slice(mma_tile_coord_v)
```

见
[flash_fwd_sm100.py:869](/Users/yangyixin03/Workspace/inference-learning/flash-attention/flash_attn/cute/flash_fwd_sm100.py:869)
和
[flash_fwd_sm100.py:1046](/Users/yangyixin03/Workspace/inference-learning/flash-attention/flash_attn/cute/flash_fwd_sm100.py:1046)。

`thr_id.shape` 描述一次 tiled MMA 需要几个 CTA participant。1CTA 时只有一个
participant；2CTA 时有两个。这里的 `thr_id` 不是普通 CUDA thread ID，而是
MMA topology 中的 participant ID。

`cta_layout_vmnk` 则描述 CTA cluster 如何映射到 MMA 的四维坐标：

```text
V：同一条 MMA instruction 的 CTA participant
M：M 方向的 MMA repeat/tile
N：N 方向的 MMA repeat/tile
K：K 方向的 MMA repeat/tile
```

本 kernel 的 cluster shape 是 `(2,1,1)` 或 `(1,1,1)`，主要沿 V 维区分
CTA0/CTA1。写成 VMNK 是因为这是通用 MMA topology 的坐标顺序，不是 Attention
张量的 V、M、N、K 四个数据轴。

2CTA 的 ownership 可以概括为：

```text
联合 QK/PV 的 M = 256

CTA0 本地拥有前 128 个 M rows 的 S/P/O
CTA1 本地拥有后 128 个 M rows 的 S/P/O

两个 CTA 各加载 B operand 的本地 contribution
2CTA UMMA 将两边 contribution 作为一个联合 operand 使用
```

只有 leader CTA 的 MMA warp 进入发射 QK/PV 的主循环：

```python
if process_tile and is_leader_cta:
    ...
```

但 CTA1 并不空闲。它仍然：

- 加载自己的 Q/K/V contribution；
- 对自己的 128 行 S 做 softmax；
- 将自己的 P 写入本地 TMEM；
- 修正自己的 O；
- 写回自己的 128 行输出。

## 3. SMEM 与 TMEM 如何组织

理解存储布局时必须分开三件事：

1. 数学上的逻辑 shape；
2. 每个 CTA 实际拥有的本地 contribution；
3. CuTe layout 对物理地址做的 swizzle 和层次化重排。

后文写 `(M,D)`，首先表示逻辑内容，不表示地址一定是
`base + m*D + d`。

### 3.1 SMEM 中有哪些数据

SMEM tensor view 在
[flash_fwd_sm100.py:519](/Users/yangyixin03/Workspace/inference-learning/flash-attention/flash_attn/cute/flash_fwd_sm100.py:519)
创建。一个 CTA 的主要 SMEM 内容是：

| Buffer | 每 CTA 的逻辑内容 | Stage 数 | 用途 |
|---|---|---:|---|
| `sQ` | 每 stage 为 `(M,D)` | `q_stage` | QK 的 A operand |
| `sK` | K 的本地 B contribution | `kv_stage` | QK 的 B operand |
| `sV` | V 的本地 B contribution | `kv_stage` | PV 的 B operand |
| `sO` | 每 stage 为 `(M,Dv)` | `q_stage` | TMEM O 到 GMEM 的中转 |
| `sScale` | 每 stage 两个长度 M 的 FP32 向量 | `q_stage` | scale、row sum、row max |

在 1CTA 模式中，一个 K stage 逻辑上覆盖 `(N,D)`，一个 V stage 覆盖
`(N,Dv)`。在 2CTA 模式中，每个 CTA 只加载联合 B operand 的一半 contribution：

```text
QK B operand:
    cluster: K  = (N,D)
    per CTA:    约 (N/2,D)

PV B operand 采用 MN-major/transposed view:
    cluster: V^T-like = (Dv,N)
    per CTA:           约 (Dv/2,N)
```

这里的“前一半/后一半”是逻辑 ownership。实际地址经过 CuTe layout 和 swizzle，
不能据此假设物理上就是两个连续矩形。

SMEM 容量计算直接体现了 2CTA 对 K/V contribution 的切分：

```python
smem_size_kv_per_stage =
    max(N * D * sizeof(K), N * Dv * sizeof(V))
    // cta_group_size
```

见
[flash_fwd_sm100.py:351](/Users/yangyixin03/Workspace/inference-learning/flash-attention/flash_attn/cute/flash_fwd_sm100.py:351)。

### 3.2 Layout 为什么不是普通二维数组

Q/K 使用 K-major，V 使用 MN-major：

```python
q_major_mode = K
k_major_mode = K
v_major_mode = MN
```

K-major 表示 head-dimension/K 方向适合作为 UMMA 描述符的主 方向；MN-major
用于把 V 按 PV 的 B operand 方式解释。随后
`make_smem_layout_a/b` 会生成：

```text
ComposedLayout
    = outer hierarchical layout
    + inner swizzle
```

outer layout 描述 tile、MMA atom 和 stage 的层次关系；inner swizzle 改变低位地址，
使 TMA/UMMA 访问合法并减少 bank conflict。阅读 kernel 数据流时通常只需要追踪
逻辑 shape、stage index 和 base pointer，不必手算每个元素的物理地址。

### 3.3 K/V 共用同一块物理 SMEM

`SharedStorage` 只为 K/V 申请了一个大 buffer：

```python
sK: MemRange[..., cosize(sK_layout)]
```

kernel 随后在同一个 iterator 上创建两种 view：

```python
sK = storage.sK.get_tensor(...)
sV = make_tensor(recast_ptr(sK.iterator, ...), sV_layout.outer)
```

因此 `sK` 和 `sV` 不是两块独立 allocation，而是同一组 bytes 的两种解释：

```text
sK view：K-major
sV view：PV B operand 所需的 MN-major
```

`pipeline_kv` 的 producer state 每装一次 K 或 V 都前进一步：

```text
K0 → V0 → K1 → V1 → K2 → V2 → ...
```

所以 `kv_stage` 是 K/V 事件共同使用的 ring 深度，不是“有 kv_stage 个 K 加
kv_stage 个 V”。某一时刻，不同 ring slot 可以分别装着 K 和 V；当 index 绕回，
旧 slot 必须先被 MMA release 才能覆盖。

`kv_stage` 根据剩余 SMEM 容量动态计算，而不是固定为 2：

```text
先扣除 sQ 和 sO
再用剩余容量容纳尽可能多的 K/V ring stage
最大限制为 32 stages
```

特定 `D=192、Dv=128、kv_stage=3` 配置会启用
`uneven_kv_smem`。它把大小不同的 K/V stage 交错压紧，并在访问中间 stage 时
根据 phase 修正地址。这个优化只改变 ring slot 的物理地址，不改变
`wait K → QK → release K → wait V → PV → release V` 的同步协议。

### 3.4 sO 和 sScale

`sO` 是输出写回的 decoupling buffer：

```text
TMEM O
    ↓ correction 读取、归一化、转换 dtype
SMEM sO
    ↓ epilogue/TMA store
GMEM O
```

有了 `sO`，correction 不必等 GMEM store 完整结束才处理下一块；它只需要等
epilogue 确认已经读完相应的 `sO[stage]`。

`sScale` 包含：

```text
q_stage × M 个 scale / row_sum
q_stage × M 个 row_max
```

中间迭代主要使用前一部分保存 `acc_scale`；最终阶段复用为 row sum，并在需要
LSE 或 learnable sink 时同时保存 row max。

### 3.5 TMEM 的基本形状

kernel 通过 MMA warp 申请 SM100 可用的全部 TMEM columns：

```python
tmem.allocate(get_max_tmem_alloc_cols("sm_100"))
```

可以把每个 CTA 的 allocation 近似画成：

```text
128 lanes × 512 columns
每个 cell 为 32 bit
```

对当前 tile，128 个 M rows 主要映射到 128 条 lane，S 的 N 维和 O 的 Dv 维主要
映射到 columns。准确 lane permutation 仍由 `tStS.layout`、`tOtO.layout`
决定，不能把它当成普通 row-major 数组。

### 3.6 S、P、O 的 TMEM column 规划

offset 在
[flash_fwd_sm100.py:303](/Users/yangyixin03/Workspace/inference-learning/flash-attention/flash_attn/cute/flash_fwd_sm100.py:303)
定义：

```text
S0 offset = 0
S1 offset = N

P stage offset = S stage offset + N/2

O0 offset = 2N
O1 offset = 2N + Dv
```

对于 `N=128、Dv=128、q_stage=2`：

```text
column
0          64        128       192       256       384       512
│-----------│----------│----------│----------│---------│---------│

S0 FP32:
[======================]                              [0,128)

P0 BF16/FP16:
           [===========]                              [64,128)

S1 FP32:
                       [======================]       [128,256)

P1 BF16/FP16:
                                  [===========]       [192,256)

O0 FP32:
                                             [=======] [256,384)

O1 FP32:
                                                       [384,512)
```

S 和 O 是 FP32 accumulator，一个元素占一个 32-bit TMEM cell：

```text
S stage: 128 × 128 FP32 → 128 columns
O stage: 128 × 128 FP32 → 128 columns
```

P 是 BF16/FP16，一个 32-bit cell 可容纳两个元素：

```text
P stage: 128 × 128 × 16 bit → 64 columns
```

所以 P 可以放在对应 S 区域的后半部分。生命周期是：

1. QK 把完整 S 写入 TMEM；
2. softmax 把 S 的一个处理片段读入 registers；
3. 该部分 S 不再需要；
4. softmax 将低精度 P 写回同一 TMEM 区域；
5. PV 从 TMEM 读取 P；
6. pipeline 允许下一轮 QK 再覆盖该 stage。

这不是 S 和 P 同时占据同一地址，而是受同步保护的生命周期复用。

FP8 的 P 只需 32 columns；代码仍使用相同的 P 起始 offset，只是实际占用更少。

### 3.7 2CTA 的 TMEM 仍然是两块本地存储

2CTA 时不要把 TMEM 想成一块普通的 `256×512` 数组：

```text
CTA0 TMEM: 128 lanes × 512 columns
    保存 CTA0 的 128 行 S/P/O

CTA1 TMEM: 128 lanes × 512 columns
    保存 CTA1 的 128 行 S/P/O
```

2CTA UMMA 能联合访问 current CTA 和 peer CTA 的 TMEM，逻辑上得到：

```text
S_cluster: (256,N)
O_cluster: (256,Dv)
```

但 softmax、correction 和 epilogue 在各自 CTA 内只处理本地 128 行。

### 3.8 CuTe 名字怎么读

CuTe 变量名通常压缩了“partition family、存储空间、数据对象”。本文件中的
`tStS` 可以拆成：

```text
t  S  t  S
│  │  │  └─ 数据是 attention score S
│  │  └──── TMEM view
│  └─────── 属于 QK/S 这条 partition family
└────────── partition 后的 tensor view
```

常见变量可以按两条 GEMM 路径记忆：

| 名字 | 含义 |
|---|---|
| `thr_mma_qk` | 当前 CTA 在 QK tiled MMA 中的 participant |
| `tSrQ` | QK/S family 的 Q operand fragment/descriptor view |
| `tSrK` | QK/S family 的 K operand fragment/descriptor view |
| `tStS` | QK/S family 在 TMEM 中的 S accumulator |
| `thr_mma_pv` | 当前 CTA 在 PV tiled MMA 中的 participant |
| `tOrP` | PV/O family 中的 P operand fragment/descriptor view |
| `tOrV` | PV/O family 中的 V operand fragment/descriptor view |
| `tOtO` | PV/O family 在 TMEM 中的 O accumulator |

`tOrP` 中出现 `r` 不意味着 P 的主体物理存放在普通 registers。kernel 明确把
PV 的 A source 设为 TMEM；这里的对象是提供给 MMA 的 fragment/descriptor view，
实际 P payload 位于 TMEM。

## 4. Pipeline：同步的基本语言

这个 kernel 的同步不是“大家在同一个位置停下来”，而是“每个 buffer 的所有权
在 producer 和 consumer 之间循环转移”。

### 4.1 full、empty、phase、tail

```text
full:
    新数据已经完成，可以读取

empty:
    旧数据已经用完，可以覆盖

phase:
    同一个 barrier slot 当前属于哪一轮 generation

tail:
    producer 退出前，等待最后使用的 stage 被 consumer 释放
```

普通 pipeline 的一轮是：

```text
producer_acquire(empty)
    ↓ 等到 stage 可以覆盖
producer 发起写入
    ↓
异步操作真正完成 / producer_commit
    ↓ full
consumer_wait(full)
    ↓ 读取数据
consumer_release
    ↓ empty
```

每个 stage 有循环使用的 barrier slot。index 绕回后 phase 翻转，consumer 等待
指定 phase，便不会把上一轮遗留的 arrival 当作当前数据 ready。

### 4.2 Pipeline 总表

| 同步对象 | Producer | Consumer | Ready/full 条件 | Empty/reuse 条件 | 保护资源 |
|---|---|---|---|---|---|
| `pipeline_q` | Load | MMA | Q load 完成 | MMA 不再读 Q | `sQ[stage]` |
| `pipeline_kv` | Load | MMA | 当前 K 或 V load 完成 | MMA 不再读该 K/V | K/V SMEM ring |
| `pipeline_s_p_o` | MMA；反向由 Softmax+Correction | Softmax；反向到 MMA | QK 已完成 S | P 首段 ready 且 O safe | TMEM S/P/O |
| `pipeline_p_lastsplit` | Softmax | PV UMMA | P 尾段 ready | 当前实现不用 empty | TMEM P 尾段 |
| `pipeline_o_acc` | MMA | Correction | 最后一轮 PV 完成 | 当前实现不用 empty | 最终 TMEM O |
| `sm_stats_barrier` | Softmax | Correction | scale/max/sum 已写入 | — | `sScale` ready |
| `pipeline_sm_stats` | Softmax | Correction | full 路径未使用 | Correction 已读完 | `sScale` 复用 |
| `pipeline_o_epi` | Correction | Epilogue | `sO` 已写好 | Epilogue 已读完 | `sO[stage]` |
| CLC pipeline | Scheduler warp | 工作 warps | work tile response ready | 所有人已读取 response | 调度 response |

这些 barrier 的 SMEM storage 位于
[flash_fwd_sm100.py:693](/Users/yangyixin03/Workspace/inference-learning/flash-attention/flash_attn/cute/flash_fwd_sm100.py:693)，
pipeline 对象创建于
[flash_fwd_sm100.py:928](/Users/yangyixin03/Workspace/inference-learning/flash-attention/flash_attn/cute/flash_fwd_sm100.py:928)。

### 4.3 Q pipeline

Load 在覆盖 `sQ[stage]` 前等待 empty：

```python
pipeline_q.producer_acquire_w_index_phase(stage, phase)
```

TMA 路径把 full mbarrier 地址交给 TMA；transaction bytes 完成后 full 才满足。
非 TMA 路径先提交 cp.async group，再把 mbarrier arrival 与这些 cp.async 的完成关联。

MMA 使用 Q 前：

```python
pipeline_q.consumer_wait_w_index_phase(stage, mma_q_consumer_phase)
```

同一个 Q stage 会参与该 work tile 的所有 QK，因此不能在第一次 QK 后立即释放。
MMA 走完整个 KV loop，确认不会再读 Q，才：

```python
pipeline_q.consumer_release_w_index(stage)
```

这解释了为什么 Q 的生命周期覆盖整个 KV 内层循环，而 K/V 只覆盖一次 QK 或 PV。

### 4.4 K/V pipeline

K/V 共用一条 producer state：

```text
producer:
    acquire slot
    load K
    advance
    acquire next slot
    load V
    advance
```

MMA 侧严格匹配：

```text
wait K → QK → release K
wait V → PV → release V
```

ring 允许 Load 比 MMA 提前多个 stage，但 producer 不能追上尚未 release 的 slot。
因此 `kv_stage` 决定最多能缓存多少个尚未消费的 K/V 事件。

### 4.5 `pipeline_s_p_o`：一个 barrier 承载两种方向

这是整段代码最关键、也最容易误读的同步对象。

full 方向是标准的 MMA → Softmax：

```text
QK UMMA 完成 S
    ↓ pipeline_s_p_o.full
Softmax 可以读取 S
```

MMA 在每个 QK 后：

```python
pipeline_s_p_o.producer_commit_w_index(stage)
```

Softmax 在读 `tStS` 前：

```python
pipeline_s_p_o.consumer_wait_w_index_phase(stage, phase)
```

empty 方向却不是简单的“Softmax 已经读完 S”。MMA 发起 PV 之前调用：

```python
pipeline_s_p_o.producer_acquire_w_index_phase(stage, phase)
```

这个 acquire 必须收齐两组 arrival：

```text
Softmax arrival:
    P 的首段已经写好，PV 有足够数据可以启动

Correction arrival:
    旧 O 已完成 rescale，或者最终 O 已被读完
    本轮 PV 可以安全写入/累加 O
```

所以准确语义是：

```text
pipeline_s_p_o.empty
    = P-first-split-ready
      AND O-rescaled-or-safe
```

第一轮还没有旧 O，correction loop 会为每个 stage 预先 release 一次，表示
“本轮无需修正，O 已经安全”。中间轮在 `correction_rescale` 完成后 release；
一个 work tile 的最终 O 被 correction 读走后再 release，为下一 work tile 复用
TMEM O 做准备。

### 4.6 P 为什么分两次通知

`split_P_arrive` 默认为 `3N/4` 并向 32 对齐；`N=128` 时是 96。
Softmax 不等整个 P 都写完才唤醒 PV：

```text
P columns 0..95 写完
    ↓
等待这些 TMEM stores 完成
    ↓
pipeline_s_p_o consumer_release
    ↓
只要 correction 也已经 release，PV 就可以启动

P columns 96..127 继续写
    ↓
等待尾部 TMEM stores 完成
    ↓
pipeline_p_lastsplit producer_commit
```

PV 的底层实现先发出首段对应的 MMA K-slices，执行到分界点时直接等待
`pipeline_p_lastsplit.full`，然后继续剩余 K-slices。这样：

```text
PV 前半
    与
Softmax 生成 P 尾段
```

可以真正重叠。

尾段通知前还有：

```python
sync_warp()
with elect_one():
    producer_commit(...)
```

`sync_warp` 确保该 warp 的所有 lane 都完成自己的 P store；`elect_one` 只选择
一个 lane 发一次 barrier arrival。它不是新的等待条件，只是避免 32 次重复 arrival。

### 4.7 Softmax statistics 与 correction

Softmax 计算新的 row max 后得到 `acc_scale`，写入 `sScale`。它随后用
`sm_stats_barrier.arrive_w_index(stage*4 + warp_idx)` 通知对应的 correction warp。

每个 NamedBarrier 的参与数是 64：

```text
一个 32-thread softmax warp
+
对应的一个 32-thread correction warp
```

Correction 调用 `arrive_and_wait_w_index`，等对应 softmax warp 写好 stats 后读取
`sScale`。因此这里没有把整个 softmax warpgroup 和 correction warpgroup
锁成一个大 barrier。

`pipeline_sm_stats` 的 full 路径在当前代码中没有使用；它主要负责反向压力：

```text
Correction 读完 sScale
    ↓ consumer_release(empty)
Softmax 下一轮 producer_acquire
    ↓
允许覆盖同一 sScale stage
```

中间迭代的 correction 逻辑是：

```text
等待 acc_scale ready
    ↓
若任意 lane 需要 rescale
    ↓
TMEM O → registers → 乘 acc_scale → TMEM O
    ↓
确认 TMEM stores 完成
    ↓
release pipeline_s_p_o
```

若所有行的 scale 都是 1，correction 可以跳过实际乘法，但仍必须 release，
否则 MMA 会永远等待 O-safe 条件。

### 4.8 最终 O 与 epilogue

`pipeline_o_acc` 只表示最后一轮 PV 的 O 已完成：

```text
MMA final PV
    ↓ pipeline_o_acc.full
Correction final wait
```

中间轮 correction 没有等待这个 pipeline，因为代码利用了更强的已有顺序：
当下一轮 softmax stats 已发布时，排在它之前的旧 O UMMA 已经完成。最终一轮后
不再有下一次 QK/softmax 事件可间接证明 O ready，所以必须单独通知。

Correction 最终读取：

```text
row_sum、row_max
TMEM O
```

然后执行：

```text
O_final = O_acc / row_sum
```

并结合 V descale、空行处理、类型转换，将结果写入 `sO[stage]`。

若 epilogue 是独立 warp，使用标准 `pipeline_o_epi`：

```text
Correction producer_acquire(empty)
    ↓
TMEM O → registers → sO
    ↓ producer_commit(full)
Epilogue consumer_wait(full)
    ↓
sO → GMEM
    ↓ consumer_release(empty)
```

若 correction warps 兼任 epilogue，则 `pipeline_o_epi=None`。所有 correction
warps 写完自己负责的 `sO` 后执行 CTA NamedBarrier，再直接 cooperative store
到 GMEM。

## 5. 各阶段如何重叠

### 5.1 先看一张角色时间线

下面是概念时间线，不表示每段宽度相等：

```text
时间 ─────────────────────────────────────────────────────────────→

Load        Q0 Q1 K0 V0 | K1 V1 | K2 V2 | ...

MMA         QK0 QK1     | PV0 QK0' | PV1 QK1' | PV0' QK0'' | ...

Softmax0        S0→P0   |              S0'→P0' | ...

Softmax1           S1→P1|                 S1'→P1' | ...

Correction             first-O-safe | rescale O0/O1 | ...

Epilogue                                             final O → GMEM
```

这里：

- `QK0/QK1` 是 query stage 0/1 对当前 K block 的 QK；
- 撇号表示下一个 KV block；
- MMA 轨道中 QK 和 PV 串行交错，因为它们使用同一 Tensor Core；
- Softmax、Correction、Load 使用其他执行资源，可以与 MMA 重叠。

### 5.2 Prologue

Load role 的开头顺序是：

```text
load K0
load Q stage 0
load Q stage 1
load V0
继续预取后续 K/V，直到 kv ring 产生背压
```

MMA role 等待 Q/K ready 后，对两个 Query stage 发出：

```text
QK(stage 0, K0) → S0
QK(stage 1, K0) → S1
```

每个 S 完成后独立通知对应 Softmax warpgroup。两个 Q stage 都消费完 K0 后，
MMA 才 release K0；Q0/Q1 则继续保留，因为后续所有 K block 仍需使用。

Correction 在进入循环时先为两个 stage 发布 O-safe。原因是第一轮 PV 使用
`zero_init=True` 创建 O，不存在需要预先缩放的旧 accumulator。

### 5.3 稳定态中的 Tensor Core 排列

对每个中间 KV block，MMA 的实际顺序近似是：

```text
wait V_j

stage 0:
    wait P0_j prefix + O0 safe
    issue PV0_j
    wait K_{j+1}
    issue QK0_{j+1}

stage 1:
    wait P1_j prefix + O1 safe
    issue PV1_j
    release V_j
    issue QK1_{j+1}

release K_{j+1}
```

因此 MMA 时间线是：

```text
PV0_j → QK0_{j+1} → PV1_j → QK1_{j+1}
```

这种排列有三个效果：

1. QK 生成下一轮 S 后，softmax 可以尽早开始；
2. 两个 softmax warpgroups 分别处理 stage 0/1，不必等全部 QK 完成；
3. correction 可以在 Tensor Core 处理另一个 stage 时修正旧 O。

### 5.4 四种 overlap

#### Load 与计算

Load warp 沿 K/V ring 提前搬运数据。只要还有 empty slot，它不必等 MMA 当前
计算完成；MMA 只在将要读取某个 slot 时等待对应 full。

#### QK/PV 与 Softmax

某 stage 的 S 一旦完成，Softmax 就可以读取它。与此同时 MMA 可以：

- 处理另一个 Query stage；
- 做前一个 KV block 的 PV；
- 做下一个 KV block 的 QK。

#### Softmax 与 Correction

Softmax 在 registers 中继续计算 exp 和 P 时，Correction 可以根据刚发布的
`acc_scale` 缩放旧 O。两者最终在 `pipeline_s_p_o.empty` 汇合：

```text
P prefix ready
AND
O safe
```

#### P 尾段与 PV 前半

Softmax 发布 P prefix 后继续写 tail；MMA 已开始 PV 的前半 K-slices。只有执行到
tail 对应的 K-slices 时，PV 才等待 `pipeline_p_lastsplit`。

### 5.5 哪些事情不能重叠

不能因为看到很多 pipeline 就认为所有阶段能任意并行：

- 同一 stage、同一 KV block 的 `QK → Softmax → PV` 数学依赖不能打破；
- QK 与 PV 都使用 Tensor Core，只能在 MMA 时间线上交错，不能同时占用同一资源；
- Correction 必须在下一次 PV 写 O 前完成旧 O 的 rescale；
- 同一个 SMEM/TMEM 地址只有在上一 generation release 后才能覆盖。

kernel 的优化目标不是消除这些依赖，而是用另一个 Query stage、另一个 KV block
或另一类执行单元填补等待空隙。

### 5.6 Epilogue overlap

最终 PV 完成后，Correction 读取 TMEM O、归一化并写入 `sO`。独立 Epilogue
warp 随后将 `sO` 写到 GMEM。

TMA O 路径会先为两个 Query stage 发出 store，再调用：

```python
cp_async_bulk_wait_group(..., read=True)
```

`read=True` 在这里关心的是 TMA 已经读完源 SMEM。只要 TMA 不再读取
`sO[stage]`，Epilogue 就可以 release empty，让 Correction 复用该 stage；
它不表示输出已经对所有全局内存观察者完全可见。

## 6. 初始化、完成、可见性与退出

Pipeline barrier、异步引擎完成和 memory visibility 是不同问题。代码必须把它们
组合起来，才能得到正确的 producer-consumer handoff。

### 6.1 Pipeline 初始化

所有主要 pipeline 都以 `defer_sync=True` 创建。barrier 初始化后调用：

```python
pipeline_init_arrive(cluster_shape_mn=cta_layout_vmnk, is_relaxed=True)
```

这个 arrive 非阻塞，因此线程还能继续构造 SMEM tensor view、BlockInfo、
SeqlenInfo 和 mask。真正使用 TMEM 或 peer CTA barrier 前再：

```python
pipeline_init_wait(cluster_shape_mn=cta_layout_vmnk)
```

见
[flash_fwd_sm100.py:1028](/Users/yangyixin03/Workspace/inference-learning/flash-attention/flash_attn/cute/flash_fwd_sm100.py:1028)。

1CTA 时它完成 CTA 内 rendezvous；2CTA 时还保证 peer CTA 的 barrier storage
已经初始化，避免向尚未初始化的远端 mbarrier 发送 arrival。

### 6.2 TMEM allocation 与 free

TMEM 由 MMA warp 分配，但 Softmax 和 Correction 都需要同一个 pointer：

```text
MMA warp:
    allocate TMEM
    wait_for_alloc
    retrieve_ptr

Softmax/Correction:
    wait_for_alloc
    retrieve_ptr
```

`retrieve_ptr` 本身只是读取已经发布的 pointer；真正的同步发生在
`wait_for_alloc`。

退出时反向进行：

```text
Softmax 完成全部 work tile → tmem_alloc_barrier.arrive
Correction 完成全部 work tile → tmem_alloc_barrier.arrive

MMA:
    relinquish_alloc_permit
    tmem_alloc_barrier.arrive_and_wait
    free TMEM
```

MMA 必须等所有 TMEM 用户声明以后不再访问，才能 free。2CTA 时
`TmemAllocator` 还使用专用 cluster mbarrier 协调 CTA pair 的反分配。

对应代码位于
[flash_fwd_sm100.py:884](/Users/yangyixin03/Workspace/inference-learning/flash-attention/flash_attn/cute/flash_fwd_sm100.py:884)
和
[flash_fwd_sm100.py:1195](/Users/yangyixin03/Workspace/inference-learning/flash-attention/flash_attn/cute/flash_fwd_sm100.py:1195)。

### 6.3 commit 不等于完成

非 TMA Q/K/V 路径中的：

```python
cp_async_commit_group()
```

只把之前发出的 cp.async 收进一个 group，并不等待数据到达 SMEM。随后
`arrive_cp_async_mbarrier` 把 full arrival 与这些 copy 的完成关联；MMA 的
consumer wait 才观察到“数据真的可以读”。

TMA 路径类似，只是 full mbarrier 通过 transaction byte count 跟踪完成。Load
发出 TMA 后可以继续，consumer 仍必须等 full。

UMMA 也是异步的。`PipelineUmmaAsync.producer_commit` 的意义不是“指令已经发出”，
而是把此前 UMMA 的完成连接到相应 mbarrier；Softmax/Correction 等到的应是结果
可消费，而不是 MMA warp 执行到了某一行 Python 代码。

### 6.4 两种名字相似但语义不同的 fence

Softmax 写 P、Correction 写回 rescaled O 后调用：

```python
fence_view_async_tmem_store()
```

虽然名字里有 fence，这里它承担的是 TMEM store completion wait。只有本线程此前
发出的 TMEM stores 完成，代码才发布 P-ready 或 O-safe arrival。

Correction 将普通 register 数据写入 `sO` 后调用：

```python
fence_view_async_shared()
```

它建立 generic SMEM write 与 async proxy read 之间的顺序和可见性，本身不是
线程 rendezvous，也不等待某个异步引擎完成。后面的 pipeline commit 或 CTA
NamedBarrier 才负责“其他角色何时可以继续”的执行同步。

### 6.5 Tail 在等待什么

producer 可能已经完成循环，但最后几个 ring slot 仍被 consumer 使用。直接退出会
留下尚未完成的 empty arrival。因此代码在角色循环末尾排空：

- KV 使用 `pipeline_kv.producer_tail`；
- Q 用最后一次 `producer_acquire` 实现等价 tail；
- Softmax stats 等待 Correction 释放最后的 `sScale`；
- Correction 等待 Epilogue 释放最后的 `sO`；
- CLC scheduler 调用自己的 `producer_tail`。

tail 等待的是“最后一批 buffer 已经被 consumer 释放”，不是一个覆盖所有 TMA、
UMMA 和 store 的通用完成指令。

`pipeline_s_p_o` 不需要额外 tail，因为循环末尾没有悬空的 acquire；
`pipeline_o_acc` 没有 producer-acquire/consumer-release 的复用协议，只是一条
单向的 final-O-ready 通知。

### 6.6 同步作用域

| 同步机制 | 作用域 | 用途 |
|---|---|---|
| Cluster-aware pipeline | CTA cluster | 连接 2CTA UMMA 与两个 CTA 的非 MMA 角色 |
| `pipeline_init_arrive/wait` | CTA 或 cluster | barrier 初始化 rendezvous |
| 2CTA TMEM dealloc mbarrier | CTA pair | 联合 TMEM 生命周期结束 |
| NamedBarrier | CTA | stats、TMEM pointer、直接 epilogue |
| `fence_view_async_shared` | CTA shared proxy scope | SMEM visibility/order |
| `sync_warp` | 单 warp | P tail signal 前 lane 收敛 |
| `elect_one` | 单 warp 的一个 lane | 只发一次 arrival/commit |

所谓“UMMA bridge 的非 MMA 一侧跨越整个 CTA cluster”，意思是：

```text
MMA side:
    由 leader 发出一次 2CTA UMMA，并向 cluster-aware barrier 发布完成

non-MMA side:
    CTA0 的 softmax/correction
    +
    CTA1 的 softmax/correction
    都必须贡献各自 arrival
```

不是某个 warp 或 thread 横跨两个 CTA。每个 CTA 仍有自己的线程、SMEM 和
NamedBarrier；cluster-aware pipeline 通过 peer barrier address 和 arrival mask
把两边连接起来。

## 7. 把完整依赖链串起来

前面的内容最终可以归结为七步：

1. Scheduler 为所有角色提供同一份
   `(m_block,head_idx,batch_idx,split_idx)`。
2. Load 一次性装入本 work tile 的 Q，并通过 K/V ring 持续预取 KV block。
3. MMA 等 Q/K full，执行 QK；S 完成后立即唤醒对应 Softmax。
4. Softmax 读取 S、更新在线统计量、发布 correction stats，并分两段写 P。
5. P prefix ready 与 O safe 在 `pipeline_s_p_o.empty` 汇合，MMA 开始 PV；
   P tail 通过另一条 barrier 在 PV 内部按需等待。
6. 中间轮将 PV 与下一块 K 的 QK 交错；最终 PV 通过 `pipeline_o_acc`
   单独通知 Correction。
7. Correction 完成最终归一化并写 `sO`，Epilogue 写 O 到 GMEM；LSE 由
   Correction 根据最终 row max/row sum 独立写回。所有角色随后 drain pipeline，
   最后才释放 TMEM。

整条同步依赖可以压缩为：

```text
Q/K load full
      │
      ▼
   QK UMMA
      │ S ready
      ▼
   Softmax ── stats ready ──► Correction
      │                           │
      │ P prefix ready            │ O rescaled/safe
      └────────────┬──────────────┘
                   │ pipeline_s_p_o.empty
                   ▼
                PV UMMA ◄──── P tail ready
                   │
                   │ final O ready
                   ▼
               Correction
                   │
                   ▼
                  sO
                   │
                   ▼
             Epilogue → GMEM
```

## 8. 配置分支

### 8.1 `q_subtile_factor` 与 `kv_subtile_factor`

这两个参数用于 block-sparse 元数据粒度与 kernel 物理 tile 粒度不一致的情况：

```text
sparse Q block size  = q_subtile_factor  × M
sparse KV block size = kv_subtile_factor × N
```

例如 sparse metadata 的一个 Q block 覆盖多个 128-row kernel tile，
`q_subtile_factor` 表示需要拆成多少个物理 Q subtile；KV 同理。

它们不会把一次 UMMA 的 M/N shape 放大。一次 QK/PV 仍使用前文的
`M=128、N=128` 物理 tile，只是 block-sparse iterator 要把一个粗粒度逻辑 block
展开成多个 kernel subtile，并正确计算 mask、block count 和物理索引。

### 8.2 `paged_kv_non_tma`

`paged_kv_non_tma=True` 使：

```python
self.use_tma_KV = False
```

原因不是“paged KV 一定不能使用 TMA”，而是选择了 paged KV 的软件寻址路径：

```text
load page-table entry
    ↓
PagedKVManager 计算物理 page 地址
    ↓
多个 load threads 用 cp.async 搬 K/V
```

相对 TMA 路径，它需要更多普通线程参与地址计算和数据搬运，因而 warp 分配和
register budget 会调整。但 `pipeline_kv` 的语义不变：

```text
producer 等 empty
→ async load
→ copy completion 使 full 满足
→ MMA wait/read/release
```

当前 non-TMA paged KV 路径还要求 head dimension 已对齐，并且 non-TMA Q load
只支持 1CTA。

### 8.3 CLC scheduler

CLC 解决的是“下一个 work tile 是什么”，不搬运 Q/K/V：

```text
CLC scheduler warp
    ↓ 发起硬件 cluster launch-control query
CLC response buffer
    ↓ full
cluster 中的工作 warps 读取 tile coordinate
    ↓ empty
scheduler 可以复用 response stage
```

默认第 15 个 empty warp 可变成 CLC scheduler warp。它独立预取下一 work tile，
让数据/计算角色完成当前 tile 时，下一份调度结果已经准备好。

CLC 只在 TMA KV 且没有 `overlap_sO_sQ` 时启用；不满足组合条件时，即使请求
`use_clc_scheduler`，构造函数也会回退到其他 scheduler。

### 8.4 `q_stage=1`

`q_stage=1` 时：

- 每 CTA 只维护一个 128-row Query tile；
- Softmax 1 warps 被移除或转给 load；
- 只有一套 S/P/O stage；
- pipeline 仍使用 full/empty/phase，只是没有 stage 0/1 ping-pong。

数据依赖没有变化，但可用于掩盖 Tensor Core、Softmax 和 Correction 延迟的
Query-level 并行度更低。

### 8.5 1CTA 与 2CTA

```text
1CTA:
    g = 1
    MMA M = 128
    所有 pipeline participant 都在一个 CTA

2CTA:
    g = 2
    联合 MMA M = 256
    每 CTA 拥有 128 行本地结果
    UMMA bridge pipeline 的非 MMA arrival count 覆盖两个 CTA
```

NamedBarrier、`sync_warp` 和普通 SMEM fence 不会因为启用 2CTA 自动变成
cluster barrier。

### 8.6 输出不能使用 TMA 时

`use_tma_O=False` 时，不再保留独立 epilogue warp。Correction warps 写完
`sO` 后在 CTA NamedBarrier 汇合，再用普通 vectorized store 写 GMEM。

这种路径常见于某些 PackGQA、SplitKV 或 varlen-Q 配置，因为输出 tile 不能用
一个规则的 TMA tensor map 表示。

### 8.7 可选的 S0/S1 sequence barrier

源码保留了让 Softmax stage 0/1 在 exp/P 区域交替的
`pipeline_s0_s1_sequence`，但当前：

```python
self.s0_s1_barrier = False
```

所以它不是主执行路径的一部分。阅读默认 kernel 时，不应把它加入必要同步链。

## 10. Tensor 与同步速查

| Tensor/View | 每 CTA 典型逻辑 shape | 位置 | Producer | Consumer |
|---|---:|---|---|---|
| Q stage | `(M,D)` | SMEM | Load | QK UMMA |
| K contribution | 1CTA `(N,D)`；2CTA 约 `(N/2,D)` | SMEM K/V ring | Load | QK UMMA |
| V contribution | 1CTA `(Dv,N)` view；2CTA 约 `(Dv/2,N)` | SMEM K/V ring | Load | PV UMMA |
| `tStS` | `(M,N)` | TMEM | QK UMMA | Softmax |
| Softmax fragment | 一线程负责一行的片段 | Registers | TMEM load | Softmax ALU/MUFU |
| P stage | `(M,N)`，低精度 | TMEM，复用 S 区域 | Softmax | PV UMMA |
| `tOtO` | `(M,Dv)` FP32 | TMEM | PV UMMA | Correction |
| `sScale` | 两组长度 M 的 FP32 向量/stage | SMEM | Softmax | Correction |
| `sO` | `(M,Dv)` | SMEM | Correction | Epilogue |
| O tile | `(M,Dv)` | GMEM | Epilogue | 后续算子 |

最后用六句话概括整个 kernel：

```text
work tile 决定一组 Query rows，q_stage 决定同时保留几组 128-row tile。
2CTA UMMA 联合计算 256 行，但每个 CTA 只拥有本地 128 行 S/P/O。
Q/K/V 在 SMEM，S/P/O accumulator 在 TMEM，Softmax 临时值在 registers。
full 表示数据可读，empty 表示地址可覆盖，phase 区分循环复用的 generation。
稳定态把 PV_j 与 QK_{j+1} 交错，并与 Load、Softmax、Correction 并行。
Epilogue 用 sO 将 TMEM 生命周期与异步 GMEM store 解耦。
```
